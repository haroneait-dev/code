Un skill est fait pour être partagé : committé dans un dépôt, publié en plugin, synchronisé depuis claude.ai. Tout ce qu'il contient doit donc être considéré comme public. Cette page montre comment un skill peut utiliser des secrets sans les contenir, et sans que Claude les voie.

## La règle : aucune valeur de secret dans le skill

Trois raisons :

1. **Le corps du skill entre dans le contexte** du modèle dès l'invocation, comme toute la conversation.
2. **Git garde tout** : un secret committé reste dans l'historique. Il faut le révoquer, pas seulement le supprimer.
3. **La distribution le copie** chez chaque utilisateur du plugin ou du dépôt.

Le `SKILL.md` ne doit mentionner que des **noms** de variables, jamais leurs valeurs. Le frontmatter n'a pas de champ `env` : la déclaration des variables requises se fait en prose dans le corps.

## Piège : les commandes injectées

La syntaxe `` !`commande` `` exécute la commande **avant** que Claude lise le skill et insère sa sortie dans le contexte. Une ligne comme celle-ci envoie donc votre token au modèle :

```markdown
Token actuel : !`echo $SLACK_BOT_TOKEN`
```

N'injectez jamais de commande qui affiche un secret, un fichier `.env` ou la sortie de `env`. Même prudence avec la sortie d'erreur : avec le shell `bash` par défaut, stderr est fusionné dans le texte injecté.

## Le bon modèle : un script qui lit l'environnement

Isolez l'appel authentifié dans un script. Le skill appelle le script, le script lit le secret dans son environnement, et seul le résultat (succès ou message d'erreur nettoyé) revient dans la conversation.

```markdown
---
name: notifier-slack
description: Envoie un message dans le canal Slack de l'équipe. À utiliser quand l'utilisateur demande de prévenir l'équipe.
disable-model-invocation: true
allowed-tools: Bash(node ${CLAUDE_SKILL_DIR}/scripts/notifier.mjs *)
---

Lancez `node ${CLAUDE_SKILL_DIR}/scripts/notifier.mjs "<message>"`.

Variables requises (à définir par l'utilisateur, jamais à afficher) :
- `SLACK_BOT_TOKEN`
- `SLACK_CHANNEL_ID`

Si le script signale une variable manquante, arrêtez-vous et dites à l'utilisateur
de la définir. Ne lisez pas les fichiers `.env`.
```

```js
// scripts/notifier.mjs
const token = process.env.SLACK_BOT_TOKEN;
const channel = process.env.SLACK_CHANNEL_ID;
if (!token || !channel) {
  console.error("Variable manquante : SLACK_BOT_TOKEN ou SLACK_CHANNEL_ID");
  process.exit(1);
}
const res = await fetch("https://slack.com/api/chat.postMessage", {
  method: "POST",
  headers: { Authorization: `Bearer ${token}`, "Content-Type": "application/json" },
  body: JSON.stringify({ channel, text: process.argv[2] ?? "" }),
});
const data = await res.json();
console.log(data.ok ? "Message envoyé" : `Erreur Slack : ${data.error}`);
```

Le script n'affiche jamais le token, même en cas d'erreur.

## Où ranger les secrets

Du plus sûr au moins sûr :

1. **Gestionnaire de secrets** (1Password CLI, Doppler, AWS Secrets Manager, Vault) : le script récupère la valeur au moment de l'appel.
2. **Trousseau du système** : `security find-generic-password -w -s mon-service` sur macOS, `secret-tool lookup service mon-service` sous Linux.
3. **Variables d'environnement** exportées dans votre shell avant de lancer `claude`.
4. **Fichier `.env.local`** ignoré par Git, lu par le script uniquement.

Évitez d'écrire des secrets dans le bloc `env` de `.claude/settings.json` : ce fichier est committé. Le `settings.local.json` n'est pas committé, mais reste en clair sur disque.

## Empêcher Claude de lire les fichiers sensibles

Ajoutez des règles de refus dans vos settings pour que les outils de fichiers de Claude ne puissent pas lire vos secrets :

```json
{
  "permissions": {
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)"
    ]
  }
}
```

Un fichier `.claudeignore` n'a aucun effet : seules les règles `Read` de refus comptent. Elles protègent les outils de fichiers, pas un `cat .env` via Bash : le bac à sable (`/sandbox`) et des règles `Bash` de refus complètent la protection.

## Plugins : `userConfig` avec `sensitive`

Si vous distribuez le skill dans un plugin, déclarez les secrets dans `userConfig`. Claude Code les demande à l'activation, masque la saisie et stocke les valeurs `sensitive` dans le stockage sécurisé, pas dans `settings.json`.

```json
{
  "name": "notifications-equipe",
  "userConfig": {
    "slack_token": {
      "type": "string",
      "title": "Token du bot Slack",
      "description": "Token xoxb avec le seul scope chat:write",
      "sensitive": true
    }
  }
}
```

Les hooks reçoivent la valeur dans `CLAUDE_PLUGIN_OPTION_SLACK_TOKEN`, et les serveurs MCP via `${user_config.slack_token}` dans leur configuration. Dans le contenu d'un skill, une valeur `sensitive` n'est **pas** substituée : elle est remplacée par un marqueur, justement pour ne pas atteindre le modèle. Les utilisateurs peuvent rouvrir la boîte de dialogue avec `/plugin configure <plugin>`.

## OAuth : préférez un serveur MCP

Pour les services OAuth (Google, Notion, Slack en tant qu'application), un serveur MCP distant gère l'authentification et le rafraîchissement des tokens hors du prompt. Connectez-le avec `claude mcp add --transport http …` puis authentifiez-vous dans `/mcp`. Votre skill appelle ensuite les outils `mcp__<serveur>__<outil>` sans jamais manipuler de secret.

## Limiter les dégâts en cas de fuite

- **Portée minimale** : token Slack limité à `chat:write`, token GitHub fine-grained restreint aux dépôts concernés, compte de service dédié pour Jira.
- **Rotation** : durée de vie courte et procédure de révocation documentée dans le README du skill (pas la valeur, l'URL de révocation).
- **Garde-fou automatique** : un hook `PreToolUse` sur `Bash` qui bloque les commandes contenant des motifs de secrets (`ghp_`, `xoxb-`, `AKIA`).
- **Scan avant commit** : `gitleaks`, `trufflehog` ou `git-secrets` en pre-commit et en CI.
