Voir un skill se déclencher prouve seulement que Claude l'a trouvé, pas qu'il fait ce que vous voulez. Un bon test mesure deux choses séparément : Claude l'invoque-t-il **quand il le faut** (et seulement à ce moment), et le résultat est-il **meilleur que sans le skill** ? Voici la boucle de travail recommandée, des tests manuels aux évaluations automatisées.

## Une boucle d'édition rapide

Claude Code surveille `~/.claude/skills/`, `.claude/skills/` et les dossiers ajoutés avec `--add-dir`. Une modification de `SKILL.md` est prise en compte **dans la session en cours**, sans redémarrage.

- Développez le skill dans son propre dépôt et reliez-le : `ln -s ~/code/mon-skill ~/.claude/skills/mon-skill`.
- Si vous créez un dossier `skills/` qui n'existait pas au lancement, tapez `/reload-skills`.
- Pour un skill de plugin, lancez `claude --plugin-dir ./mon-plugin`, puis `/reload-plugins` après chaque modification.

## Tester le déclenchement à la main

1. Ouvrez une **nouvelle session** : le contexte accumulé pendant l'écriture du skill masque les manques des instructions.
2. Formulez la demande comme un utilisateur, **sans nommer le skill** : « Qu'est-ce que j'ai changé ? » plutôt que « utilise summarize-changes ».
3. Vérifiez que Claude appelle le skill, puis testez une demande proche qui ne doit **pas** le déclencher.
4. En cas de doute, demandez « Quels skills sont disponibles ? » ou ouvrez `/skills`.

## Diagnostiquer un skill qui ne se déclenche pas

| Symptôme | Cause probable | Correction |
|---|---|---|
| Absent de `/skills` | Mauvais chemin ou dossier non surveillé | `.claude/skills/<nom>/SKILL.md`, puis `/reload-skills` |
| `/nom` marche, mais Claude ne l'utilise jamais seul | YAML invalide (le skill se charge sans métadonnées) ou `disable-model-invocation: true` | `claude --debug` pour voir l'erreur de parsing ; `claude plugin validate .claude/skills` |
| Rarement choisi | Description vague | Ajoutez ce que fait le skill **et** quand l'utiliser, avec les mots que l'utilisateur emploie |
| Choisi seulement sur certains fichiers | Champ `paths` trop restrictif | Élargissez les globs |
| Description coupée | Trop de skills : la liste dépasse son budget (1 % du contexte) | `/doctor`, `/skill-doctor`, passez des skills en `"name-only"` dans `skillOverrides` |
| Se déclenche trop souvent | Description trop large | Précisez-la, ou `disable-model-invocation: true` |

## Comparer avec et sans le skill

La méthode officielle est une **comparaison avec référence** : quelques prompts réalistes, chacun lancé dans une session neuve avec le skill, puis sans. Pour désactiver temporairement un skill personnel ou de projet :

```json
{
  "skillOverrides": {
    "mon-skill": "off"
  }
}
```

Le menu `/skills` le fait aussi : sélectionnez le skill, `Espace` pour changer d'état, `Échap` pour enregistrer dans `.claude/settings.local.json`.

Anthropic recommande de construire **au moins trois scénarios d'évaluation avant** d'écrire beaucoup d'instructions, et de tester avec les modèles que vous comptez utiliser (Haiku, Sonnet, Opus).

## Automatiser avec skill-creator

Le plugin `skill-creator` automatise cette boucle dans une conversation Claude Code :

```text
/plugin install skill-creator@claude-plugins-official
```

Demandez ensuite « évalue mon skill summarize-changes avec skill-creator ». Il :

- stocke les cas de test dans `evals/evals.json` dans le dossier du skill ;
- lance un subagent par cas pour partir d'un contexte propre ;
- note chaque assertion dans `grading.json` et agrège avec ou sans skill dans `benchmark.json` ;
- compare deux versions du skill en aveugle ;
- génère des prompts qui doivent ou non déclencher le skill, et propose des retouches de description.

## Automatiser avec `claude plugin eval`

Pour un skill livré dans un plugin (v2.1.269 et plus), `claude plugin eval` lance chaque cas dans une session non interactive isolée, avec et sans le plugin, et calcule l'apport (`Δ`).

```bash
claude plugin eval init          # Claude propose les cas et les graders
claude plugin eval .             # lance toute la suite
claude plugin eval . --case premier-cas --runs 1 --ablation none   # itération rapide
```

Un cas est un dossier sous `evals/` :

```markdown
<!-- evals/message-commit/prompt.md -->
---
max_turns: 10
allowed_tools: [Read, Glob, Grep, Skill]
---

Rédigez un message de commit : j'ai renommé getUser en fetchUser et mis à jour les trois appels.
```

```markdown
<!-- evals/message-commit/graders/skill-declenche.md -->
---
type: tool_used
tool: Skill
input_match: '"skill"\s*:\s*"(?:[\w-]+:)?message-commit"'
---
```

Chaque cas tourne trois fois par défaut, avec et sans plugin. Le résumé affiche `WITH`, `W/OUT` et `Δ`. Un `Δ` proche de zéro avec le grader `tool_used: Skill` en échec signifie presque toujours que la description n'est pas assez précise. La commande sort avec un code non nul sous le seuil (`--threshold`, 1.0 par défaut) : vous pouvez bloquer une CI dessus. Chaque exécution consomme de vrais appels au modèle.

Ajoutez `evals/results/` à votre `.gitignore`. Les deux formats (skill-creator et `claude plugin eval`) ne sont pas interchangeables.

## Mesurer l'usage réel

Une fois le skill déployé, `/skill-doctor` (v2.1.252 et plus) montre ce que chaque skill coûte en contexte et combien de fois il est invoqué. Un skill jamais utilisé est un candidat à la désactivation.
