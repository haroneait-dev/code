Un skill partagé devient une dépendance : le modifier change le comportement de Claude chez tous ceux qui l'utilisent. Le frontmatter de `SKILL.md` n'a **pas** de champ `version` reconnu par Claude Code. Le versioning se gère donc à deux niveaux : Git pour les skills de projet, le manifeste du plugin pour les skills distribués.

## Skill de projet : Git suffit

Un skill dans `.claude/skills/` est versionné avec le dépôt. Chaque développeur a la version de sa branche. Les bonnes pratiques habituelles s'appliquent : relecture en pull request, message de commit clair, et un test de déclenchement avant fusion (voir [Tester un skill](/wiki/skills/tester-skill)).

Si vous voulez tout de même tracer une version dans le fichier, utilisez `metadata`, que Claude Code ignore :

```yaml
---
name: generer-migration
description: Génère une migration SQL Supabase. À utiliser quand l'utilisateur modifie le schéma.
metadata:
  version: "2.1.0"
---
```

## Skill en plugin : comment Claude Code calcule la version

Pour un plugin installé depuis une marketplace, Claude Code calcule une version et ne remplace la copie en cache que si elle change. Ordre de résolution :

1. le champ `version` de `plugin.json` ;
2. sinon le champ `version` de l'entrée dans `marketplace.json` ;
3. sinon une valeur dérivée de la source :

| Source | Version par défaut |
|---|---|
| `github`, `url`, `git-subdir` | SHA du commit (12 caractères) |
| Chemin relatif dans une marketplace Git | SHA du commit du dossier |
| `archive` | Empreinte SHA-256 (12 caractères) |
| `npm` ou dossier local hors Git | `unknown` |

Le piège classique : vous fixez `"version": "1.0.0"`, vous poussez des correctifs sans l'incrémenter, et `claude plugin update` répond `is already at the latest version (1.0.0)`. Vos utilisateurs gardent l'ancienne copie.

Deux stratégies valides :

- **SemVer explicite** : incrémentez `version` à chaque release (et utilisez `claude plugin validate --strict` en CI, qui signale une version manquante) ;
- **SHA automatique** : omettez `version` dans une marketplace Git, chaque commit devient une version.

## Quand incrémenter quoi (SemVer)

Pour un skill, le « contrat » est ce que l'utilisateur tape et ce qu'il obtient :

| Changement | Niveau |
|---|---|
| Reformulation, correction d'une étape, meilleur exemple | PATCH |
| Nouvel argument facultatif, nouveau fichier de référence, nouveau skill dans le plugin | MINOR |
| Renommage d'un skill ou du plugin, argument obligatoire ajouté ou supprimé, passage à `disable-model-invocation: true`, `allowed-tools` élargi, nouvelle variable d'environnement requise | MAJOR |

Règle simple : si un utilisateur peut être surpris ou bloqué après la mise à jour, c'est une version majeure. Élargir `allowed-tools` mérite aussi d'être signalé pour des raisons de sécurité.

## Éviter les ruptures

- **Ne renommez pas un plugin publié.** L'installation est enregistrée sous `nom@marketplace`. Si c'est inévitable, ajoutez une entrée `renames` dans `marketplace.json` pour migrer les installations existantes. Pour changer seulement le libellé, modifiez `displayName`.
- **Renommer un skill** change sa commande (`/plugin:ancien` devient `/plugin:nouveau`). Gardez l'ancien skill pendant une ou deux versions : un corps qui renvoie vers le nouveau nom et `disable-model-invocation: true` pour que Claude ne le choisisse plus de lui-même.
- **Arguments** : ajoutez plutôt des arguments facultatifs ; un placeholder nommé sans valeur devient une chaîne vide.
- **Documentez** chaque release dans un `CHANGELOG.md` à la racine du plugin, avec une section « Ruptures » en tête des versions majeures.

## Étiqueter les releases

Si d'autres plugins dépendent du vôtre avec une plage de versions (champ `dependencies` de `plugin.json`), ces plages se résolvent sur des tags Git. Créez-les avec :

```bash
claude plugin tag --push
```

La commande crée un tag `{nom}--v{version}` et le pousse sur `origin`.

## Canaux stable et bêta

Claude Code n'a pas de notion de canal. Pour proposer deux pistes, hébergez **deux marketplaces** aux `name` différents, dont les entrées pointent vers des refs différentes du même plugin :

```json
{
  "name": "acme-stable",
  "owner": { "name": "Acme" },
  "plugins": [
    {
      "name": "generateur-migrations",
      "source": { "source": "github", "repo": "acme/generateur-migrations", "ref": "stable" }
    }
  ]
}
```

Une seconde marketplace `acme-beta` pointe vers `"ref": "main"`. Chaque utilisateur ajoute celle qu'il veut. Donnez aux deux refs des `version` différentes dans `plugin.json` (ou omettez `version`) : une ref qui avance sans changement de version laisse les utilisateurs sur la copie en cache.

## Comment les utilisateurs reçoivent la mise à jour

- **À la demande** : `claude plugin update generateur-migrations@acme-stable`.
- **Automatiquement** : l'auto-update est désactivé par défaut pour une marketplace tierce. L'utilisateur l'active dans `/plugin` > **Marketplaces**, ou l'admin via `"autoUpdate": true` dans les managed settings.

Avant chaque release, relancez votre suite d'évaluations (`claude plugin eval .`) pour détecter les régressions, y compris après la sortie d'un nouveau modèle.
