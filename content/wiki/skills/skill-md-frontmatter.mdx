Le frontmatter de `SKILL.md` décide **qui** peut invoquer le skill, **quand** Claude le charge et **avec quels droits**. Les champs inventés sont ignorés en silence : Claude Code ne signale pas une clé inconnue. Cette page liste uniquement les champs documentés officiellement.

## Les règles de base

- Le frontmatter est lu seulement si la **première ligne** du fichier est `---`.
- Tous les champs sont facultatifs dans Claude Code. `description` est le seul vivement recommandé.
- Les noms de champs utilisent des tirets (`allowed-tools`), sauf `when_to_use`.
- Les booléens acceptent `true`/`false`, mais aussi `yes`, `no`, `on`, `off`, `1`, `0`.
- Si le YAML ne se parse pas, le skill se charge quand même **sans aucun champ** : `/nom` fonctionne, mais Claude ne peut plus le déclencher seul.

## Tableau de référence

| Champ | Rôle |
|---|---|
| `name` | Nom affiché dans le menu `/`. Par défaut : le nom du dossier |
| `description` | Ce que fait le skill et quand l'utiliser. Sert à Claude pour décider de le charger |
| `when_to_use` | Contexte de déclenchement en plus (phrases types). Ajouté à la description |
| `argument-hint` | Indice affiché à l'autocomplétion, ex. `[numero-issue]` |
| `arguments` | Arguments positionnels nommés, utilisables en `$nom` dans le corps |
| `disable-model-invocation` | `true` : seul vous pouvez l'invoquer (`/nom`) |
| `user-invocable` | `false` : seul Claude peut l'invoquer ; masqué du menu `/` |
| `allowed-tools` | Outils autorisés sans demande de permission pendant le tour d'invocation |
| `disallowed-tools` | Outils retirés à Claude tant que le skill est actif |
| `model` | Modèle à utiliser pendant le tour (ou pour le subagent en `context: fork`) |
| `effort` | Niveau d'effort : `low`, `medium`, `high`, `xhigh`, `max` |
| `context` | `fork` : exécute le skill dans un subagent isolé |
| `agent` | Type de subagent pour `context: fork` (`Explore`, `Plan`, `general-purpose` ou personnalisé) |
| `background` | Avec `context: fork` : `false` pour attendre le résultat dans le même tour |
| `hooks` | Hooks enregistrés quand le skill est invoqué |
| `paths` | Globs : Claude ne charge le skill automatiquement que sur les fichiers correspondants |
| `shell` | `bash` (défaut) ou `powershell` pour les commandes injectées |
| `metadata` | Table libre pour vos propres outils ; ignorée par Claude Code |
| `license` | Licence (spec Agent Skills) ; acceptée mais sans effet |
| `compatibility` | Prérequis d'environnement, 500 caractères max (spec Agent Skills) ; sans effet |

Il n'existe **pas** de champs `version`, `author`, `tags`, `trigger`, `env`, `mcp`, `subagents`, `extends` ou `deprecated` dans la spécification. Si vous voulez stocker une version ou un auteur, mettez-les dans `metadata`.

## `description` et `when_to_use` : le déclenchement

Claude choisit un skill en comparant votre demande à sa description. Règles officielles :

- dire **ce que fait** le skill **et quand** l'utiliser ;
- écrire à la troisième personne (« Génère… », pas « Je peux… ») ;
- mettre le cas d'usage principal en premier : `description` + `when_to_use` sont tronqués à **1 536 caractères** dans la liste des skills ;
- pour un skill destiné aussi à claude.ai ou à l'API : 1 024 caractères maximum, pas de balises XML.

```yaml
description: Génère des migrations Drizzle à partir d'un schéma SQL existant. À utiliser quand l'utilisateur modifie une table ou demande une migration.
when_to_use: "Exemples : « ajoute une colonne email », « crée la table commandes »."
```

## Qui peut invoquer le skill

| Frontmatter | Vous (`/nom`) | Claude | Description dans le contexte |
|---|---|---|---|
| (défaut) | Oui | Oui | Toujours |
| `disable-model-invocation: true` | Oui | Non | Non |
| `user-invocable: false` | Non | Oui | Toujours |

Utilisez `disable-model-invocation: true` pour tout ce qui a des effets de bord (`/deploy`, `/commit`) : vous ne voulez pas que Claude décide seul de déployer. Ce réglage empêche aussi le préchargement dans un subagent.

## `allowed-tools` : une pré-autorisation, pas une restriction

C'est le contresens le plus fréquent. `allowed-tools` **n'interdit rien** : tous les outils restent disponibles. Il autorise les outils listés sans demande de permission, **pendant le tour** où le skill est invoqué. L'autorisation tombe dès votre message suivant.

```yaml
allowed-tools: Bash(git add *) Bash(git commit *) Bash(git status *)
```

Le format accepte une chaîne séparée par des espaces ou des virgules, ou une liste YAML. La syntaxe est celle des règles de permission : `Bash(npm test *)` autorise les commandes qui commencent par `npm test`.

Pour **retirer** des outils, utilisez `disallowed-tools` :

```yaml
disallowed-tools: AskUserQuestion WebFetch
```

Attention : un skill de projet applique son `allowed-tools` même dans un dossier non approuvé. Relisez ce champ dans les dépôts que vous clonez.

## `arguments` et substitutions

```yaml
---
name: migrer-composant
description: Migre un composant d'un framework à un autre
arguments: [composant, source, cible]
argument-hint: "[composant] [source] [cible]"
disable-model-invocation: true
---

Migrez le composant $composant de $source vers $cible en conservant les tests.
```

`/migrer-composant SearchBar Vue React` remplace les trois variables. Sans `arguments`, utilisez `$ARGUMENTS` (tout le texte), `$0`, `$1`… Autres substitutions utiles : `${CLAUDE_SKILL_DIR}`, `${CLAUDE_PROJECT_DIR}`, `${CLAUDE_SESSION_ID}`, `${CLAUDE_EFFORT}`.

## `context: fork` et `agent`

```yaml
---
name: audit-securite
description: Audite le module d'authentification
context: fork
agent: Explore
---

Analysez `src/auth/` et listez les failles avec fichier et ligne.
```

Le contenu du skill devient le prompt d'un subagent qui **ne voit pas** votre conversation. Le subagent tourne en arrière-plan par défaut ; `background: false` fait attendre son résultat. Réservez `context: fork` aux skills qui contiennent une vraie tâche, pas de simples conventions.

## `model` et `effort`

```yaml
model: sonnet
effort: high
```

Le changement vaut pour le tour en cours et n'est pas enregistré dans vos settings. `inherit` garde le modèle actif. Un modèle exclu par la politique de l'organisation (`availableModels`) est ignoré.

## `paths` : limiter le déclenchement automatique

```yaml
paths:
  - "app/api/**/route.ts"
  - "supabase/migrations/*.sql"
```

Claude ne charge le skill de lui-même que lorsqu'il travaille sur des fichiers correspondants. Même format que les règles par chemin de la mémoire.

## `hooks`

```yaml
hooks:
  PreToolUse:
    - matcher: "Bash"
      hooks:
        - type: command
          command: "${CLAUDE_SKILL_DIR}/scripts/verifier.sh"
```

Les hooks d'un skill sont enregistrés à l'invocation et restent actifs **jusqu'à la fin de la session**. Ajoutez `once: true` sur un hook pour qu'il soit retiré après sa première exécution réussie.

## Portabilité hors de Claude Code

Pour un skill téléversé sur claude.ai, via l'API Skills ou empaqueté avec `package_skill.py`, seuls six champs sont admis : `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`. Tout autre champ provoque une erreur bloquante (`Unexpected key(s) in SKILL.md frontmatter`). Sur ces surfaces, `name` et `description` sont obligatoires, `name` fait 64 caractères maximum et ne peut contenir « anthropic » ni « claude ».

## Exemple complet

```yaml
---
name: verifier-env
description: Vérifie que chaque variable process.env utilisée dans le code figure dans .env.example. À utiliser avant un déploiement ou quand l'utilisateur parle de variables d'environnement.
allowed-tools: Read Grep Bash(grep *)
paths: "**/*.ts, .env.example"
metadata:
  version: "1.2.0"
  owner: "equipe-plateforme"
---

1. Cherchez toutes les occurrences de `process.env.` dans `app/` et `lib/`.
2. Comparez avec les clés de `.env.example`.
3. Listez les clés manquantes et les clés inutilisées, sans jamais afficher de valeur.
```
