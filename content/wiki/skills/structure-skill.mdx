Un skill Claude Code est un **dossier sur disque** : un fichier `SKILL.md` obligatoire, plus des fichiers d'appui facultatifs. Pas de build, pas de manifeste binaire, tout se versionne avec Git. Voici ce qu'on y met et où le ranger.

## Arborescence type

```text
generer-migration/
├── SKILL.md              # obligatoire : frontmatter + instructions
├── reference.md          # documentation détaillée, lue à la demande
├── exemples.md           # exemples, lus à la demande
├── templates/
│   └── migration.sql     # modèle à copier
└── scripts/
    └── valider.py        # script exécuté, son code n'entre pas dans le contexte
```

Seul `SKILL.md` est obligatoire. Le nom du dossier devient la commande : ce skill s'invoque avec `/generer-migration`, sauf si le champ `name` du frontmatter en fixe une autre.

## Le fichier SKILL.md

Il contient deux parties : un frontmatter YAML entre deux lignes `---` (la première ligne du fichier doit être `---`), puis les instructions en Markdown.

```markdown
---
name: generer-migration
description: Génère une migration SQL Supabase à partir d'une modification de schéma. À utiliser quand l'utilisateur ajoute une table, une colonne ou une politique RLS.
allowed-tools: Bash(python3 *) Read Write
---

# Générer une migration

1. Lisez le schéma actuel dans `supabase/migrations/`.
2. Partez du modèle [templates/migration.sql](templates/migration.sql).
3. Écrivez la migration dans `supabase/migrations/<horodatage>_<nom>.sql`.
4. Validez avec `python3 ${CLAUDE_SKILL_DIR}/scripts/valider.py <fichier>`.

Pour les politiques RLS complexes, lisez [reference.md](reference.md).
```

Dans Claude Code, tous les champs du frontmatter sont facultatifs, mais `description` est fortement recommandé : c'est lui qui permet à Claude de décider quand charger le skill. La liste complète est dans l'article [Frontmatter de SKILL.md](/wiki/skills/skill-md-frontmatter).

## Les fichiers d'appui : la divulgation progressive

Le principe central des skills est la **divulgation progressive** (progressive disclosure), en trois niveaux :

| Niveau | Quand c'est chargé | Contenu |
|---|---|---|
| 1. Métadonnées | Toujours | Nom et description |
| 2. Instructions | Quand le skill est invoqué | Corps de `SKILL.md` |
| 3. Ressources | Seulement si Claude les lit | Fichiers de référence, modèles ; les scripts sont exécutés et seule leur sortie entre dans le contexte |

Conséquences pratiques :

- gardez `SKILL.md` **sous 500 lignes** et déplacez le détail dans des fichiers séparés ;
- citez chaque fichier depuis `SKILL.md` avec un lien relatif et dites **quand** le lire ;
- restez à **un niveau** de référence : `SKILL.md` pointe vers `reference.md`, mais évitez que `reference.md` pointe vers un troisième fichier ;
- préférez un script pour les opérations déterministes (validation, conversion) : c'est plus fiable et moins coûteux que de laisser Claude réécrire le code.

## Référencer les scripts de façon robuste

Le répertoire courant de la session ne correspond pas au dossier du skill. Utilisez les variables substituées par Claude Code :

| Variable | Valeur |
|---|---|
| `${CLAUDE_SKILL_DIR}` | Dossier qui contient le `SKILL.md` |
| `${CLAUDE_PROJECT_DIR}` | Racine du projet |
| `${CLAUDE_PLUGIN_ROOT}` | Racine du plugin (skills de plugin uniquement) |

Astuce : utilisez la même variable dans `allowed-tools` et dans le corps. Le script s'exécute alors sans demande de permission.

```yaml
allowed-tools: Bash(python3 ${CLAUDE_SKILL_DIR}/scripts/valider.py *)
```

La règle doit correspondre exactement à la commande que le corps demande de lancer.

## Où placer le dossier

| Emplacement | Chemin | Portée |
|---|---|---|
| Personnel | `~/.claude/skills/<nom>/SKILL.md` | Tous vos projets sur cette machine |
| Projet | `.claude/skills/<nom>/SKILL.md` | Ce dépôt (à committer pour l'équipe) |
| Imbriqué | `<sous-dossier>/.claude/skills/<nom>/SKILL.md` | Chargé quand Claude travaille dans ce sous-dossier |
| Plugin | `<plugin>/skills/<nom>/SKILL.md` | Partout où le plugin est activé, en `/plugin:nom` |
| Entreprise | Dossier des managed settings | Tous les postes de l'organisation |
| Compte claude.ai | Skills activés sur votre compte | Sessions Cowork, cloud et terminal connectées à ce compte |

Claude Code remonte aussi les dossiers parents jusqu'à la racine du dépôt : un skill défini à la racine d'un monorepo reste disponible quand vous lancez `claude` dans `packages/front/`. Un dossier de skill peut être un lien symbolique.

Deux noms sont réservés : `synced` (utilisé pour les skills synchronisés depuis claude.ai) et `anthropic-skills`.

## Conventions de nommage

- **Dossier et `name`** : minuscules, chiffres et tirets, 64 caractères maximum. Les mots réservés « anthropic » et « claude » sont refusés sur claude.ai et l'API.
- Un nom qui décrit l'action : `generer-migration` plutôt que `helper` ou `utils`.
- **Fichiers** : barres obliques `/` dans les chemins, jamais de `\` Windows.

## Vérifier la structure

Il n'existe pas de linter dédié aux skills, mais la CLI des plugins vérifie le frontmatter :

```bash
claude plugin validate .claude/skills      # skills du projet
claude plugin validate ~/.claude/skills    # skills personnels
```

Ensuite, dans une session, `/skills` liste les skills chargés et leur source. Si votre YAML est invalide, le skill se charge quand même mais sans métadonnées : lancez `claude --debug` pour voir l'erreur.
