Un `SKILL.md` n'est pas une documentation d'API : c'est un jeu d'instructions pour Claude. Le générer entièrement depuis des commentaires de code produit en général un skill verbeux et peu utile. En revanche, plusieurs parties se prêtent bien à l'automatisation : le premier brouillon, les fichiers de référence, le catalogue de vos skills et les contrôles avant fusion. Cette page montre quoi automatiser, et quoi garder à la main.

## Ce qui doit rester écrit à la main

- **La `description`** : c'est elle qui déclenche le skill. Elle doit dire ce que fait le skill et quand l'utiliser, avec les mots de vos utilisateurs. Aucun outil ne connaît ce contexte mieux que vous.
- **La procédure** dans le corps de `SKILL.md` : quelques étapes impératives, sous 500 lignes, avec les consignes essentielles en haut (elles survivent mieux à la compaction).

## Le premier brouillon : demandez à Claude

La méthode recommandée par Anthropic est de développer un skill **avec** Claude : une instance vous aide à rédiger, une autre (session neuve) l'utilise sur de vraies tâches. Le plugin `skill-creator` outille cette démarche :

```text
/plugin install skill-creator@claude-plugins-official
```

Demandez ensuite par exemple : « Crée un skill qui génère nos migrations Supabase à partir de ce que nous venons de faire. » Il propose la structure, le frontmatter et des cas de test, puis peut affiner la description en mesurant le taux de déclenchement.

Pour un projet entier, `/run-skill-generator` écrit un skill `.claude/skills/run-<nom>/` qui enregistre comment lancer votre application, et `/verify` consigne sa propre recette dans `.claude/skills/verify/SKILL.md`. Ce sont deux exemples de skills générés par Claude Code lui-même.

## Générer les fichiers de référence depuis le code

C'est là que la génération depuis TSDoc ou JSDoc a du sens. Si votre skill pilote une bibliothèque interne, produisez sa référence d'API avec un outil classique, puis placez-la dans un fichier que le skill lit **seulement si besoin** (niveau 3 de la divulgation progressive).

```bash
npx typedoc --plugin typedoc-plugin-markdown \
  --out .claude/skills/client-interne/reference \
  src/client/index.ts
```

Dans `SKILL.md`, ne recopiez pas la référence, pointez vers elle :

```markdown
## Référence

Pour la signature exacte d'une fonction du client, lisez le fichier
correspondant dans [reference/](reference/). Ne lisez que ce dont vous avez besoin.
```

Quelques règles issues des bonnes pratiques officielles :

- un seul niveau de renvoi depuis `SKILL.md` ;
- une table des matières en tête des fichiers de référence longs ;
- pas d'information datée (« avant août 2026… ») sans la ranger dans une section « Anciennes méthodes ».

## Générer un catalogue de vos skills

Avec des dizaines de skills, un README listant chacun avec sa description évite les doublons. Un petit script suffit :

```js
// scripts/catalogue-skills.mjs
import { readdir, readFile, writeFile } from "node:fs/promises";
import { parse } from "yaml";

const dir = ".claude/skills";
const lignes = ["| Skill | Description | Invocation |", "|---|---|---|"];

for (const nom of (await readdir(dir)).sort()) {
  let texte;
  try {
    texte = await readFile(`${dir}/${nom}/SKILL.md`, "utf8");
  } catch {
    continue;
  }
  const match = texte.match(/^---\n([\s\S]*?)\n---/);
  const fm = match ? parse(match[1]) ?? {} : {};
  const invocation = fm["disable-model-invocation"] ? "manuelle" : "auto + manuelle";
  lignes.push(`| \`/${fm.name ?? nom}\` | ${fm.description ?? "(aucune)"} | ${invocation} |`);
}

await writeFile(`${dir}/README.md`, lignes.join("\n") + "\n");
```

Le `README.md` à la racine de `.claude/skills/` n'est pas un skill (pas de `SKILL.md`) : Claude Code l'ignore.

## Contrôler en CI

Combinez la validation officielle et vos propres règles :

```yaml
# .github/workflows/skills.yml (extrait)
- run: npm install -g @anthropic-ai/claude-code
- run: claude plugin validate .claude/skills
- run: node scripts/catalogue-skills.mjs && git diff --exit-code .claude/skills/README.md
- run: node scripts/verifier-skills.mjs
```

`claude plugin validate` signale les frontmatters qui ne se parsent pas. Votre script `verifier-skills.mjs` peut ajouter des règles maison :

- `description` présente et sous 1 024 caractères (limite de claude.ai et de l'API) ;
- `name` en minuscules, chiffres et tirets, 64 caractères maximum ;
- `SKILL.md` sous 500 lignes ;
- uniquement des champs officiels (Claude Code ignore en silence une clé mal orthographiée, comme `allowed_tools` au lieu de `allowed-tools`) ;
- pour un skill destiné à claude.ai : uniquement `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`.

Pour un skill distribué en plugin, ajoutez `claude plugin validate --strict` et une suite `claude plugin eval` (voir [Tester un skill](/wiki/skills/tester-skill)).

## README humain contre SKILL.md

| | README.md | SKILL.md |
|---|---|---|
| Lecteur | Développeurs qui découvrent le skill | Claude |
| Contenu | Installation, prérequis, exemples, changelog | Description de déclenchement, procédure impérative |
| Ton | Explicatif | Consignes courtes et vérifiables |

Ne fusionnez pas les deux : chaque ligne de `SKILL.md` coûte des tokens à chaque invocation.
