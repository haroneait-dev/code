Claude intègre ses propres protections, mais elles ne remplacent pas la politique de modération de votre application. Cet article explique les trois façons dont l'API refuse un contenu, comment les gérer proprement dans le code, puis comment ajouter vos propres garde-fous et une traçabilité exploitable pour le RGPD, le DSA ou l'AI Act.

## Les couches de protection côté Anthropic

1. **L'entraînement du modèle.** Claude est entraîné (notamment via l'approche Constitutional AI) à refuser les demandes dangereuses. Ces refus arrivent comme une réponse texte normale.
2. **Les classifieurs de sécurité.** Sur les modèles récents (Fable 5.1, Fable 5, Opus 5.5, Opus 5, Sonnet 5.5), des classifieurs peuvent interrompre une réponse. L'API renvoie alors `stop_reason: "refusal"`.
3. **La validation d'entrée.** Certaines requêtes sont rejetées avant le modèle, avec une erreur HTTP 400.
4. **La politique d'usage.** La [Usage Policy](https://www.anthropic.com/legal/aup) d'Anthropic définit ce qui est interdit, quel que soit votre prompt système.

| Type de refus | Ce que vous recevez | Quand |
|---|---|---|
| Refus du modèle | Réponse texte standard | Le modèle décline lui-même |
| Refus d'un classifieur | HTTP 200, `stop_reason: "refusal"` | Pendant la génération, y compris en streaming |
| Validation d'entrée | Erreur HTTP 400 | Avant la génération |

## Lire un refus de classifieur

Un refus de classifieur n'est **pas une erreur HTTP**. Un monitoring basé uniquement sur les taux d'erreur ne le verra pas. La réponse contient un objet `stop_details` :

```json
{
  "role": "assistant",
  "content": [],
  "stop_reason": "refusal",
  "stop_details": {
    "type": "refusal",
    "category": "cyber",
    "explanation": "This request was declined because it could enable cyber harm."
  }
}
```

Catégories documentées : `cyber`, `bio`, `frontier_llm`, `reasoning_extraction` et `general_harms`. Les champs `category` et `explanation` peuvent valoir `null` : branchez votre logique sur `stop_reason`, pas sur la catégorie, et prévoyez votre propre message pour l'utilisateur.

Trois règles pratiques :

- **Jetez toute sortie partielle.** Un refus peut arriver en plein streaming, après quelques tokens.
- **Ne renvoyez pas la même conversation au même modèle.** Retirez ou reformulez le tour qui a déclenché le refus, ou réinitialisez le contexte.
- **Comptez les refus comme un signal à part** dans vos tableaux de bord, y compris dans les résultats de la Batch API (un refus y apparaît comme un résultat réussi).

## Gérer le refus dans le code

```python
import anthropic

client = anthropic.Anthropic()

def ask(messages):
    response = client.messages.create(
        model="claude-sonnet-5-5",
        max_tokens=1024,
        messages=messages,
    )
    if response.stop_reason == "refusal":
        details = response.stop_details
        category = getattr(details, "category", None)
        log_refusal(category)  # votre journalisation
        return "Je ne peux pas répondre à cette demande. Reformulez-la ou contactez le support."
    return response.content[0].text
```

Pour les faux positifs (un travail légitime de cybersécurité ou de biologie peut déclencher un classifieur), l'API propose en bêta un **repli serveur** : avec `fallbacks: "default"` et l'en-tête bêta `server-side-fallback-2026-07-01`, la requête refusée est relancée sur le modèle recommandé pour cette catégorie. Ce repli n'existe pas sur Bedrock, Google Cloud ni Foundry ; utilisez-y le middleware des SDK.

**Facturation** : un refus survenu avant toute sortie est facturé seulement pour certaines catégories (`bio`, `frontier_llm`, `reasoning_extraction` en septembre 2026). Il compte toujours dans vos limites de débit.

## Vos garde-fous applicatifs

Les protections d'Anthropic couvrent les abus graves, pas vos règles métier (mentions de concurrents, conseils juridiques, promesses commerciales, ton de marque). Ajoutez :

- **Un filtre d'entrée** : un petit modèle rapide (par exemple Claude Haiku 4.5) classe la demande avant l'appel principal. Contraignez sa réponse avec des sorties structurées pour obtenir un booléen exploitable.
- **Un filtre de sortie** : le même principe appliqué à la réponse, selon vos critères métier.
- **Une politique de repli** : message générique, escalade vers un humain, ou blocage temporaire des utilisateurs récidivistes.

Exemple de filtre d'entrée inspiré de la documentation officielle :

```python
SCREEN_PROMPT = """Un utilisateur a soumis ce contenu :
<content>
{content}
</content>

Ce contenu concerne-t-il des activités dangereuses, illégales ou explicites ?"""

screen = client.messages.create(
    model="claude-haiku-4-5-20251001",
    max_tokens=100,
    messages=[{"role": "user", "content": SCREEN_PROMPT.format(content=user_input)}],
    output_config={
        "format": {
            "type": "json_schema",
            "schema": {
                "type": "object",
                "properties": {"is_harmful": {"type": "boolean"}},
                "required": ["is_harmful"],
                "additionalProperties": False,
            },
        }
    },
)
```

Des classifieurs open source spécialisés (par exemple Llama Guard) sont une alternative quand vous voulez un filtre auto-hébergé.

## Journalisation et audit

Pour démontrer un dispositif de modération traçable, conservez, avec une durée de rétention définie :

- un identifiant ou un hash de la requête (pas forcément le texte complet, par minimisation) ;
- le verdict de vos filtres et la règle appliquée ;
- le `stop_reason` et la catégorie éventuelle renvoyés par Claude ;
- l'identifiant de requête de l'API, utile si vous contactez le support ;
- l'action prise côté application.

Stockez ces journaux hors du contexte conversationnel et documentez-les dans votre registre de traitements.

## Tests adversariaux continus

- Constituez un corpus versionné de prompts sensibles (abus connus et cas métier limites).
- Rejouez-le en CI à chaque changement de modèle ou de prompt système.
- Mesurez à la fois les contenus qui passent à tort et les refus injustifiés : un filtre trop strict dégrade l'expérience autant qu'un filtre trop laxiste.
