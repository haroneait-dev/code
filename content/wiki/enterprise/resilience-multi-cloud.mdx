Les modèles Claude sont servis par plusieurs canaux : l'API Claude d'Anthropic, Amazon Bedrock (et Claude Platform on AWS), Google Cloud (Agent Platform, ex-Vertex AI) et Microsoft Foundry. Pour un service critique, s'appuyer sur deux canaux au lieu d'un seul limite l'impact d'une panne régionale ou d'un pic de saturation. Cet article montre comment concevoir ce failover sans doubler la facture.

## Ce que le multi-cloud apporte (et ce qu'il n'apporte pas)

Bénéfices réels :

- **Découplage des incidents** : une saturation de l'API Claude n'affecte pas forcément Bedrock, et inversement.
- **Contrôle de la région** : Bedrock et Google Cloud fixent la région par l'endpoint, ce qui aide pour la résidence des données (voir [Sovereign hosting](/wiki/enterprise/sovereign-hosting)).
- **Achats** : consommer Claude sur un engagement cloud existant (AWS, GCP, Azure).

Limites à connaître avant de vous lancer :

- **Pas de SLA magique.** Votre disponibilité dépend des contrats de chaque fournisseur et de la qualité de votre bascule. Ne promettez pas « 99,99 % » sans l'avoir mesuré.
- **Parité des fonctionnalités imparfaite.** Certaines fonctions bêta (outils serveur, en-têtes `anthropic-beta`, paramètre `inference_geo`) n'existent que sur l'API Claude ou arrivent plus tard chez les partenaires.
- **Identifiants de modèles différents.** Bedrock utilise des IDs préfixés (et souvent des profils d'inférence), Google Cloud ses propres noms. Gardez une table de correspondance.
- **Caches séparés.** Le prompt caching n'est pas partagé entre fournisseurs : après une bascule, les premiers appels repartent sans cache et coûtent plus cher.

## Topologie de référence

Un routeur applicatif (dans votre code ou dans une gateway) choisit un fournisseur primaire et bascule sur le secondaire en cas d'échec. Le secondaire doit être **réellement opérationnel** : quotas demandés, modèles activés dans la console, identifiants testés. Un fournisseur « déclaré » mais jamais appelé échouera le jour de la panne.

| Canal | Région | Auth | Rôle typique |
|---|---|---|---|
| API Claude | Mondiale, ou `inference_geo: "us"` | Clé API Console | Primaire (nouveautés en premier) |
| Amazon Bedrock | Région AWS choisie | IAM / clé Bedrock | Secondaire, ou primaire si exigence AWS |
| Google Cloud Agent Platform | Région GCP choisie | IAM GCP | Secondaire, ou primaire UE |
| Microsoft Foundry | Région Azure | Clé ou Entra ID | Option pour les organisations Azure |

## Implémenter le failover en Python

Le SDK Python officiel fournit un client par canal (`Anthropic`, `AnthropicBedrock`, `AnthropicVertex`) avec la même interface `messages.create`. Le point important : **ne basculer que sur les erreurs transitoires** (surcharge, 5xx, 429, réseau). Une erreur 400 indique un problème dans votre requête, elle échouera partout.

```python
import anthropic
from anthropic import Anthropic, AnthropicBedrock, AnthropicVertex

# Remplacez les IDs par ceux activés dans chaque console (ils diffèrent selon le fournisseur).
PROVIDERS = [
    ("claude_api", Anthropic(max_retries=2),
     "claude-sonnet-5-5"),
    ("bedrock", AnthropicBedrock(aws_region="eu-west-3", max_retries=1),
     "ID_DU_MODELE_OU_PROFIL_BEDROCK"),
    ("vertex", AnthropicVertex(region="europe-west1", project_id="mon-projet", max_retries=1),
     "ID_DU_MODELE_GOOGLE_CLOUD"),
]

TRANSIENT = (
    anthropic.APIConnectionError,   # réseau, timeout
    anthropic.RateLimitError,       # 429
    anthropic.InternalServerError,  # 5xx, dont 529 overloaded
)

def create_with_failover(messages, max_tokens=1024):
    last_error = None
    for name, client, model in PROVIDERS:
        try:
            response = client.messages.create(
                model=model, max_tokens=max_tokens, messages=messages
            )
            return name, response
        except TRANSIENT as err:
            last_error = err
            continue  # fournisseur suivant
        # Les autres erreurs (400, 401, 403...) remontent immédiatement.
    raise RuntimeError(f"Tous les fournisseurs ont échoué : {last_error}")
```

Les SDK réessaient déjà automatiquement (2 fois par défaut, avec backoff). Réduisez `max_retries` sur les canaux de secours pour ne pas empiler les délais.

## Circuit breaker et détection de panne

Plutôt que d'envoyer des requêtes payantes de « ping » toutes les 15 secondes, surveillez les **erreurs réelles** :

- Comptez les erreurs transitoires par fournisseur sur une fenêtre glissante (par exemple 1 minute).
- Au-delà d'un seuil, ouvrez le circuit : le fournisseur est sauté pendant 30 à 60 secondes.
- Laissez ensuite passer une requête de test (*half-open*). Si elle réussit, refermez le circuit.
- Abonnez votre astreinte à la page de statut officielle d'Anthropic et à celles de vos clouds.

```python
import time

class CircuitBreaker:
    def __init__(self, threshold=5, cooldown_s=45):
        self.threshold, self.cooldown_s = threshold, cooldown_s
        self.failures, self.opened_at = 0, None

    def available(self):
        if self.opened_at is None:
            return True
        return time.monotonic() - self.opened_at > self.cooldown_s  # half-open

    def record(self, ok):
        if ok:
            self.failures, self.opened_at = 0, None
        else:
            self.failures += 1
            if self.failures >= self.threshold:
                self.opened_at = time.monotonic()
```

## Coûts : les pièges du failover

- **Double facturation** : une requête qui a expiré côté client peut quand même avoir été traitée (et facturée) par le premier fournisseur. Fixez des timeouts réalistes, surtout en streaming.
- **Perte du cache** : prévoyez un surcoût temporaire après chaque bascule (pas de cache chaud chez le secondaire).
- **Tarifs différents** : chaque cloud applique ses propres prix régionaux. L'option `inference_geo: "us"` de l'API Claude est facturée 1,1 fois le tarif standard.
- **Cache applicatif** : pour les requêtes répétitives (classification, FAQ), un cache Redis devant le routeur évite des appels, quel que soit le fournisseur.

## Et pour Claude Code ?

Claude Code ne bascule pas tout seul d'un fournisseur cloud à l'autre. Vous disposez de deux leviers :

- **Repli de modèle** : `--fallback-model sonnet,haiku` (ou le réglage `fallbackModel`) bascule vers un autre modèle quand le modèle principal est surchargé ou indisponible.
- **Gateway** : pointer Claude Code vers une gateway LLM (`ANTHROPIC_BASE_URL`) qui, elle, gère le routage multi-fournisseurs. Changer de fournisseur se fait alors côté gateway, sans toucher aux postes. Voir [Gestion des clés API et gateways](/wiki/enterprise/api-gateways).

Si vous déployez via un cloud, épinglez les versions avec `ANTHROPIC_DEFAULT_OPUS_MODEL`, `ANTHROPIC_DEFAULT_SONNET_MODEL` et `ANTHROPIC_DEFAULT_HAIKU_MODEL` : sans cela, les alias suivent le défaut intégré de Claude Code, qui peut ne pas être activé sur votre compte.

## Checklist avant la mise en production

1. Les modèles sont activés et les quotas validés sur chaque canal.
2. La table de correspondance des IDs de modèles est versionnée.
3. Le failover est testé régulièrement (coupure volontaire du primaire en préproduction).
4. Les logs indiquent quel fournisseur a servi chaque requête.
5. Le budget prévoit le surcoût d'une bascule prolongée.
