Claude Code fonctionne dès que vous lancez `claude` dans un dossier. Mais il devient nettement plus fiable quand le dépôt lui donne le bon contexte : vos commandes, vos conventions et vos limites. Ce guide liste les fichiers à préparer et ce qu'il faut committer ou non.

## Les fichiers qui comptent

| Fichier | Rôle | À committer ? |
|---|---|---|
| `CLAUDE.md` (ou `.claude/CLAUDE.md`) | Instructions permanentes lues à chaque session | Oui |
| `CLAUDE.local.md` | Vos notes personnelles pour ce projet | Non (`.gitignore`) |
| `.claude/settings.json` | Permissions, hooks, variables d'environnement, plugins de l'équipe | Oui |
| `.claude/settings.local.json` | Vos réglages personnels pour ce projet | Non (Claude Code l'exclut de git quand il le crée) |
| `.mcp.json` (racine du projet) | Serveurs MCP partagés avec l'équipe | Oui, sans secret en clair |
| `.claude/rules/*.md` | Règles ciblées par type de fichier ou dossier | Oui |
| `.claude/skills/`, `.claude/agents/` | Skills et sous-agents du projet | Oui |

Si votre dépôt a déjà un `AGENTS.md` (utilisé par d'autres agents de code) et pas de `CLAUDE.md`, Claude Code le lit directement depuis septembre 2026.

## Démarrer avec `/init`

Le plus simple est de laisser Claude Code proposer une première version :

```text
/init
```

Claude analyse le dépôt et rédige un `CLAUDE.md` avec les commandes de build, de test et les conventions qu'il détecte. Si le fichier existe déjà, `/init` propose des améliorations au lieu de l'écraser. Avec la variable `CLAUDE_CODE_NEW_INIT=1`, `/init` devient un parcours interactif qui peut aussi préparer des skills et des hooks.

## Écrire un `CLAUDE.md` efficace

Le `CLAUDE.md` doit contenir ce que vous répéteriez sinon à chaque prompt. La documentation recommande de rester **sous 200 lignes** : un fichier trop long coûte du contexte et est moins bien suivi.

```markdown
# Mon projet

## Stack
- Next.js App Router + TypeScript
- Supabase (auth + Postgres)

## Commandes
- `npm run dev` : serveur local
- `npm test -- --run` : tests en mode CI (pas de watch)
- `npm run lint:fix` : correction ESLint avant commit

## Conventions
- Composants en PascalCase, hooks en camelCase
- Pas de `any` en TypeScript
- Tests Vitest dans `__tests__/`

## À éviter
- Ne pas modifier `lib/legacy/` (en cours de suppression)
- Ne jamais committer directement sur `main`
```

Lister les commandes exactes évite que Claude tente `yarn dev` ou `pnpm test` au hasard. Pour aller plus loin (imports `@chemin`, hiérarchie des fichiers), voyez [Le fichier CLAUDE.md](/wiki/demarrer/claude-md).

> Le `CLAUDE.md` est un contexte, pas une règle appliquée de force. Pour interdire réellement une action, utilisez une règle de permission `deny` ou un hook `PreToolUse`.

## Cibler des règles avec `.claude/rules/`

Pour des consignes qui ne concernent qu'une partie du code, créez un fichier dans `.claude/rules/` avec un champ `paths`. Il ne se charge que lorsque Claude travaille sur les fichiers correspondants :

```markdown
---
paths:
  - "app/api/**/*.ts"
---

# Règles des routes API
- Toujours vérifier le jeton Supabase avant toute écriture.
- Répondre en JSON avec un champ `error` en cas d'échec.
```

Cela garde le `CLAUDE.md` principal court.

## Configurer les permissions du projet

Le fichier `.claude/settings.json` pré-autorise les commandes courantes et bloque ce qui est sensible. Ajoutez la ligne `$schema` pour avoir l'autocomplétion dans VS Code ou Cursor :

```json
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": [
      "Bash(npm run lint)",
      "Bash(npm run test *)",
      "Bash(git status)",
      "Bash(git diff *)"
    ],
    "ask": [
      "Bash(git push *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)"
    ]
  }
}
```

Points à connaître :

- l'ordre d'évaluation est **deny, puis ask, puis allow** : une règle `deny` l'emporte toujours ;
- la syntaxe actuelle est `Bash(npm run test *)` (l'ancienne forme `Bash(npm run test:*)` reste acceptée) ;
- les règles `allow` d'un `.claude/settings.json` committé ne s'appliquent qu'après que vous avez accepté la boîte de dialogue de confiance du dossier ;
- un fichier `.claudeignore` n'a aucun effet : utilisez des règles `Read(...)` en `deny`.

Détails : [Permissions et sandbox](/wiki/demarrer/permissions-sandbox).

## Le `.gitignore`

```gitignore
# Claude Code (fichiers personnels)
.claude/settings.local.json
CLAUDE.local.md

# Secrets
.env
.env.local
.env.*.local
.envrc
```

Claude Code ajoute lui-même `.claude/settings.local.json` à vos exclusions git globales la première fois qu'il écrit ce fichier. L'ajouter au `.gitignore` reste une bonne précaution si vous le créez à la main.

## Ajouter des serveurs MCP partagés

Les serveurs MCP de l'équipe se déclarent dans **`.mcp.json` à la racine du projet**. La façon la plus sûre de le remplir est la commande dédiée :

```bash
claude mcp add --transport http --scope project notion https://mcp.notion.com/mcp
```

Le fichier généré ressemble à ceci. Les secrets passent par des variables d'environnement, jamais en clair :

```json
{
  "mcpServers": {
    "notion": {
      "type": "http",
      "url": "https://mcp.notion.com/mcp"
    },
    "api-interne": {
      "type": "http",
      "url": "${API_BASE_URL:-https://api.example.com}/mcp",
      "headers": {
        "Authorization": "Bearer ${API_KEY}"
      }
    }
  }
}
```

Chaque développeur doit approuver les serveurs d'un `.mcp.json` au premier lancement. Vérifiez l'état avec `/mcp`. Voir [Installer un serveur MCP](/wiki/mcp/installer-serveur-mcp).

## Automatiser avec des hooks

Les hooks lancent une commande shell à des moments précis. Exemple : formater automatiquement chaque fichier modifié.

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "npx prettier --write \"$(jq -r '.tool_input.file_path')\"" }
        ]
      }
    ]
  }
}
```

Le hook reçoit en JSON sur l'entrée standard les détails de l'outil appelé : ici `jq` en extrait le chemin du fichier modifié. Voir [Introduction aux hooks](/wiki/hooks/introduction-hooks).

## Une structure de dossiers lisible

Claude se repère mieux dans un dépôt prévisible :

- un dossier par responsabilité (`app/`, `components/`, `lib/`) ;
- des noms explicites (`user-profile.tsx` plutôt que `up.tsx`) ;
- un `README.md` à jour, que Claude lit aussi.

```text
mon-app/
├── CLAUDE.md
├── .mcp.json
├── .claude/
│   ├── settings.json
│   ├── rules/
│   └── skills/
├── app/
├── components/
├── lib/
└── tests/
```

## Script d'installation pour les nouveaux venus

```bash
#!/usr/bin/env bash
set -e
command -v claude >/dev/null || curl -fsSL https://claude.ai/install.sh | bash
command -v jq >/dev/null || echo "Installez jq pour les hooks du projet"
echo "Prêt. Lancez : claude"
```

## Vérifier la configuration

```text
/status     # méthode de connexion et fichiers de réglages chargés (« Setting sources »)
/memory     # fichiers CLAUDE.md et mémoire chargés
/mcp        # état des serveurs MCP
/doctor     # diagnostic (réglages invalides, installation)
```

En dehors d'une session, `claude doctor` liste aussi les entrées de réglages rejetées. Pour auditer la qualité de vos instructions, utilisez `/doctor prompt-audit`.
