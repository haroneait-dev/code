Claude Code peut lire vos fichiers, les modifier et lancer des commandes shell. Deux mécanismes complémentaires encadrent ces capacités : les **permissions** décident si une action peut avoir lieu (seule, après confirmation, ou jamais), et le **sandbox** impose au niveau du système d'exploitation les fichiers et domaines réseau que les commandes shell peuvent atteindre.

## Les modes de permission

| Mode | Ce qui passe sans demander | Pour quoi faire |
|---|---|---|
| `default` (affiché « Manual ») | Les lectures uniquement | Tout valider vous-même, travail sensible |
| `acceptEdits` | Lectures, modifications de fichiers et commandes de fichiers courantes (`mkdir`, `touch`, `mv`, `cp`) | Itérer sur du code que vous relisez |
| `plan` | Lectures (Claude explore et propose un plan sans modifier vos sources) | Analyser avant de modifier |
| `auto` | Tout, avec un classifieur qui vérifie chaque action en arrière-plan | Tâches longues, moins d'interruptions |
| `dontAsk` | Lectures et outils pré-autorisés ; tout le reste est refusé | CI et scripts verrouillés |
| `bypassPermissions` | Tout | Conteneurs et VM isolés uniquement |

**`auto` est le mode de départ** des sessions interactives dans le terminal et dans VS Code : d'abord pour les offres Pro, Max et Team (août 2026), puis pour tous les comptes depuis la v2.1.283. Le classifieur bloque par défaut les actions risquées : `curl | bash`, envoi de données sensibles vers l'extérieur, déploiements en production, `git push --force`, `git reset --hard`, suppression massive, `terraform destroy`, affichage d'un secret dans la conversation, etc.

### Changer de mode

- **Pendant la session** : `Shift+Tab` fait défiler les modes (depuis `auto` : `default`, puis `acceptEdits`, puis `plan`, puis retour à `auto`). Le mode actif s'affiche sous la zone de saisie.
- **Au démarrage** : `claude --permission-mode plan` (fonctionne aussi avec `-p`).
- **Par défaut** : la clé `permissions.defaultMode` dans vos réglages.

```json
{
  "permissions": {
    "defaultMode": "acceptEdits"
  }
}
```

`dontAsk` n'apparaît jamais dans le cycle `Shift+Tab` : il se choisit avec `--permission-mode dontAsk`. `bypassPermissions` n'y apparaît que si vous avez lancé Claude Code avec `--dangerously-skip-permissions` (ou équivalent).

> `bypassPermissions` désactive presque toutes les vérifications, y compris l'écriture dans `.git` et `.claude`. Réservez-le à un conteneur ou une VM jetable, sans accès à vos identifiants. Pour bloquer ce mode dans une organisation : `"disableBypassPermissionsMode": "disable"` dans les réglages gérés.

## Les règles allow, ask et deny

Par-dessus le mode, vous ajoutez des règles fines dans `.claude/settings.json` (partagé), `.claude/settings.local.json` (personnel) ou `~/.claude/settings.json` (tous vos projets) :

```json
{
  "permissions": {
    "allow": [
      "Bash(npm test *)",
      "Bash(git status)",
      "Bash(git diff *)"
    ],
    "ask": [
      "Bash(git push *)"
    ],
    "deny": [
      "Bash(sudo *)",
      "Read(./.env)",
      "Read(./.env.*)",
      "Edit(//etc/**)"
    ]
  }
}
```

Ce qu'il faut savoir :

- **Ordre d'évaluation : deny, puis ask, puis allow.** La première règle qui correspond décide. Une règle `allow` plus précise ne peut pas annuler un `deny`.
- **Les `deny` s'appliquent dans tous les modes**, même `bypassPermissions`.
- **Syntaxe Bash** : `*` est un joker. `Bash(npm test *)` couvre `npm test` avec ou sans arguments. L'ancienne écriture `Bash(npm test:*)` reste équivalente.
- **Chemins** : `Edit(/src/**)` est relatif au projet, `Read(~/Documents/*.pdf)` au dossier personnel, et `Edit(//etc/**)` est un chemin absolu (deux barres obliques).
- **Write n'a pas de règles de chemin** : utilisez `Edit(...)`, qui couvre tous les outils de modification. Une règle `Read(...)` en `deny` bloque aussi l'écriture au même endroit.
- **Limite** : les règles `Read` et `Edit` s'appliquent aux outils de Claude et aux commandes shell reconnues (`cat`, `sed`, redirections), mais pas à un script Python ou Node qui ouvre des fichiers lui-même. Pour une vraie barrière, activez le sandbox.

Pour consulter et modifier les règles sans éditer de JSON, tapez `/permissions`. Le panneau indique de quel fichier vient chaque règle. Quand vous répondez « Yes, and don't ask again » à une demande, la règle est enregistrée dans `.claude/settings.local.json`.

## Le sandbox Bash

Le sandbox est une barrière appliquée par le système d'exploitation autour des commandes shell que Claude lance (Bash, PowerShell, Monitor) et de leurs processus enfants. Il est **désactivé par défaut**.

| Accès | Par défaut dans le sandbox |
|---|---|
| Écriture | Dossier de travail, dossier temporaire, dossiers ajoutés (`--add-dir`) ; les fichiers de configuration de Claude Code (`.claude/`, `.mcp.json`, `.git/hooks`, `.bashrc`…) restent protégés |
| Lecture | La majeure partie de la machine, y compris `~/.ssh` (à restreindre avec `denyRead`) |
| Réseau | Aucune sortie directe : tout passe par un proxy qui vérifie chaque domaine |

### Plateformes

- **macOS** : utilise Seatbelt, intégré au système. Rien à installer.
- **Linux et WSL2** : nécessite `bubblewrap` et `socat` (`sudo apt-get install bubblewrap socat`). Sur Ubuntu 24.04 et plus, un profil AppArmor peut être nécessaire.
- **Windows natif** : pas de sandbox. Utilisez WSL2.

### Activer le sandbox

Dans une session :

```text
/sandbox
```

Le panneau propose deux modes : **auto-allow** (les commandes sandboxées passent sans demande, puisque le système les contient) ou **regular permissions** (les demandes habituelles restent). Le choix est enregistré dans `.claude/settings.local.json`. Pour tous vos projets, mettez la configuration dans `~/.claude/settings.json` :

```json
{
  "sandbox": {
    "enabled": true,
    "allowUnsandboxedCommands": false,
    "filesystem": {
      "allowWrite": ["~/.kube", "/tmp/build"],
      "denyRead": ["~/.aws/credentials"]
    },
    "network": {
      "allowedDomains": ["registry.npmjs.org", "github.com"]
    },
    "excludedCommands": ["docker compose *"]
  }
}
```

- `allowUnsandboxedCommands: false` active le **mode strict** : Claude ne peut plus relancer une commande hors du sandbox après un échec.
- `excludedCommands` sort certaines commandes du sandbox (elles repassent alors par les permissions classiques). Gardez des motifs étroits.
- `failIfUnavailable: true` empêche Claude Code de démarrer si le sandbox ne peut pas s'activer (sinon il exécute sans sandbox).

### Vérifier qu'il fonctionne

Demandez à Claude (et non via `!`, qui s'exécute hors sandbox) de lancer `touch ~/sandbox-probe`. La commande doit échouer avec `Operation not permitted` (macOS) ou `Read-only file system` (Linux). Si Claude propose de la relancer hors sandbox, refusez.

### Ce que le sandbox ne couvre pas

Les outils Read, Edit, WebFetch, les hooks, les serveurs MCP locaux et la commande de status line s'exécutent hors sandbox : ils obéissent aux règles de permission. Pour tout isoler, lancez Claude Code lui-même dans un conteneur ou une VM.

## Recommandations par contexte

| Contexte | Configuration conseillée |
|---|---|
| Développement local courant | Mode `auto` ou `acceptEdits`, quelques `allow`, `deny` sur les secrets |
| Projet sensible | Mode `default`, sandbox activé en mode strict, `denyRead` sur `~/.ssh` et `~/.aws` |
| CI / scripts | `--permission-mode dontAsk` avec des `allow` précis, dans un conteneur |
| Conteneur jetable sans secrets | `bypassPermissions` possible |

Pensez à relire régulièrement `.claude/settings.local.json` : les « don't ask again » s'y accumulent vite.
