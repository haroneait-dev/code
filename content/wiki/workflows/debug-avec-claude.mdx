Claude Code est très efficace en débogage, à condition de ne pas lui envoyer un simple « ça marche pas » avec un fichier. La méthode ci-dessous suit quatre étapes : reproduire, isoler, corriger, verrouiller. L'idée centrale : donner à Claude une vérification qu'il peut exécuter lui-même, pour qu'il itère jusqu'à ce qu'elle passe au lieu de s'arrêter quand « ça a l'air bon ».

## Donner le bon point de départ

Un bon premier message contient trois choses : la commande qui reproduit le problème, le message d'erreur complet et ce qui varie (toujours, parfois, seulement en production).

```text
`npm test -- invoices` échoue depuis ce matin avec :
TypeError: Cannot read properties of undefined (reading 'id')
    at buildInvoice (src/billing/invoice.ts:42:18)
Le bug est systématique en local. Il n'apparaissait pas avant le commit a1b2c3d.
Trouve la cause racine. Ne supprime pas l'erreur, ne mets pas de `?.` pour la masquer.
```

Collez l'erreur telle quelle (ou passez-la par un pipe : `npm test 2>&1 | claude -p "explique cette erreur"`). Pour un bug visuel, collez une capture d'écran. Pour un bug dans le navigateur, l'extension Claude in Chrome permet à Claude de lire la console et le DOM.

## Étape 1 : reproduire

Un bug qu'on ne reproduit pas ne se corrige pas, il se masque. Demandez d'abord un test qui échoue :

```text
1. Identifie la ligne exacte qui lève l'erreur.
2. Écris un test minimal qui reproduit le bug.
3. Lance-le et montre-moi qu'il échoue avec la même erreur qu'observée.
Ne propose aucun correctif avant que ce test échoue.
```

Si le test échoue autrement qu'en production, ce n'est pas le bon bug. Recommencez avant d'aller plus loin.

## Étape 2 : isoler la cause racine

Un modèle propose toujours une explication plausible, même fausse. Exigez plusieurs hypothèses et un moyen de trancher entre elles :

```text
Le test échoue sur `undefined.id`. Donne trois hypothèses distinctes
(données nulles en entrée, await manquant, état partagé entre tests…).
Pour chacune, propose UN log ou UN test qui la confirme ou l'écarte.
Lance-les et conclus à partir des sorties, pas de ton intuition.
```

Les outils qui aident à cette étape :

- **Le mode plan** (`Shift+Tab` jusqu'à « plan mode on ») : Claude lit et raisonne sans rien modifier. Idéal pour un bug dans un code que vous connaissez mal.
- **Les sous-agents** : « utilise un sous-agent pour retrouver tous les appelants de `buildInvoice` ». L'exploration se fait dans un contexte séparé et ne remplit pas votre conversation.
- **`git bisect`** quand vous savez qu'une version antérieure fonctionnait. Claude peut piloter la bissection avec `git bisect run npm test -- invoices`.
- **L'outil Monitor** pour un bug qui apparaît dans des logs : demandez « surveille la sortie de `npm run dev` et préviens-moi à la première erreur 500 ». Chaque événement arrive dans la conversation sans boucle d'attente.
- **`/btw`** pour une question annexe (« que fait ce flag de Postgres ? ») sans polluer le contexte.
- **Un niveau d'effort plus élevé** (`/effort high` ou `xhigh`) pour un bug qui demande un long raisonnement.

Pour activer des logs détaillés le temps de l'enquête, utilisez ce que votre projet prévoit (par exemple `DEBUG=app:* npm run dev` si vous utilisez la bibliothèque `debug`). Retirez-les avant le commit.

## Étape 3 : corriger, et seulement corriger

La tentation est de « nettoyer tant qu'on y est ». Le diff devient alors illisible et la revue difficile.

```text
Propose le diff MINIMAL qui fait passer le test de reproduction.
Pas de renommage, pas de refactor annexe.
Si tu vois d'autres améliorations, liste-les à part sans les appliquer.
```

Un correctif qui touche beaucoup de fichiers est un signal : soit le bug a plusieurs causes, soit le diagnostic est faux. Revenez à l'étape 2. Si Claude part dans une mauvaise direction, `Échap` l'arrête et `/rewind` (ou `Échap` deux fois) restaure le code et la conversation à un point antérieur. Après deux corrections ratées sur le même point, un `/clear` et un prompt de départ plus précis donnent presque toujours un meilleur résultat qu'une conversation encombrée.

## Étape 4 : valider et verrouiller

```bash
npm test               # toute la suite, pas seulement le nouveau test
npm run build
git diff --stat        # le diff reste ciblé
```

Demandez des preuves plutôt que des affirmations : la commande lancée et sa sortie. Puis faites relire le correctif par un regard neuf, qui n'a pas participé à l'enquête :

```text
/code-review
```

La revue tourne dans un sous-agent qui ne voit que le diff, pas le raisonnement qui y a mené. Pour une interface, la skill `/verify` lance l'application et observe le résultat réel.

Enfin, le message de commit :

```text
Résume en trois lignes : la cause racine (sans jargon), le correctif,
le test qui empêche la régression. Format Conventional Commits.
```

## Bugs intermittents

Les bugs qui apparaissent une fois sur dix demandent une autre approche :

```text
Le bug n'apparaît pas à chaque exécution. Avant de corriger :
1. Liste ce qui peut varier d'une exécution à l'autre (ordre des promesses,
   cache, fuseau horaire, état partagé entre tests, données aléatoires).
2. Propose trois hypothèses de condition de course.
3. Écris un test qui force l'ordre problématique, puis lance-le 50 fois
   pour mesurer la fréquence avant et après correctif.
```

Pour une chasse longue, un dynamic workflow peut lancer la suite en boucle et s'arrêter quand deux tours de suite ne trouvent rien de nouveau (« utilise un workflow pour trouver les tests instables… »).

## Pièges à éviter

- **Envoyer tout le dépôt.** Donnez la commande de reproduction et laissez Claude chercher ; il lit lui-même les fichiers utiles.
- **Accepter la première hypothèse.** Demandez-en plusieurs et un test pour chacune.
- **Sauter la reproduction.** Sans test qui échoue, rien ne prouve que le correctif marche.
- **Laisser masquer l'erreur.** `try/catch` vide, `?.` partout, test marqué `skip` : interdisez-le explicitement.
- **Confondre avec `/debug`.** Cette skill sert à diagnostiquer Claude Code lui-même (ses logs de session), pas votre application.

## Garder une trace

Notez la cause racine des bugs importants dans un dossier `docs/postmortems/`. Claude peut le consulter quand un symptôme ressemble à un incident passé, et une consigne dans `CLAUDE.md` (« avant de débugger, regarde docs/postmortems/ ») suffit à l'y inviter.
