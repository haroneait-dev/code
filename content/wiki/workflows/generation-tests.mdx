Écrire des tests est la tâche que tout le monde repousse, et Claude l'exécute bien, à condition de cadrer. Sans consignes, il produit des tests qui passent mais ne prouvent rien. Cet article montre comment obtenir une suite qui attrape les régressions, puis comment faire des tests la vérification qui guide tout le reste du travail de Claude.

## Pourquoi les tests comptent double avec un agent

La documentation officielle le dit en une phrase : donnez à Claude une vérification qu'il peut exécuter. Sans tests, Claude s'arrête quand le code « a l'air terminé », et c'est vous qui jouez le rôle de vérificateur. Avec une suite fiable, il travaille, lance la suite, lit le résultat et recommence jusqu'à ce qu'elle passe. Les tests ne servent donc pas seulement à protéger le code : ils rendent Claude autonome.

## Trois niveaux, trois objectifs

| Niveau | Périmètre | Outils typiques (JS/TS) | Quand l'exécuter |
| :- | :- | :- | :- |
| Unitaire | Une fonction pure, sans entrée-sortie | Vitest, Jest | À chaque modification |
| Intégration | Plusieurs modules, vraie base de test | Vitest + Supabase local ou Postgres de test | Avant chaque push |
| End-to-end | L'application complète dans un navigateur | Playwright | En CI, sur les parcours critiques |

Précisez toujours le niveau visé dans votre demande. Mélanger les niveaux donne des suites lentes et fragiles.

## Partir des conventions existantes

Claude lit vos fichiers de test existants pour en reprendre le style, le framework et les assertions. Commencez par lui faire trouver les trous :

```text
Trouve les fonctions de src/billing/ qui ne sont couvertes par aucun test.
Classe-les par risque (argent, authentification, données utilisateur d'abord).
```

Puis demandez les tests un module à la fois.

## Tests unitaires : viser les branches

Un bon test unitaire couvre les branches, les cas limites et les erreurs, pas seulement le cas nominal :

```text
Écris une suite Vitest pour `parseInvoiceAmount(input: string): number` :
1. Montant valide (« 12.50 »).
2. Virgule décimale française (« 12,50 »).
3. Montant négatif : doit lever InvalidAmountError.
4. Chaîne vide : doit lever une erreur.
5. « NaN », « Infinity », espaces seuls.
Un comportement par test, des noms de tests qui décrivent ce comportement.
Lance la suite et montre-moi la sortie.
```

```bash
npx vitest run --coverage   # nécessite @vitest/coverage-v8 (ou istanbul)
```

Regardez la couverture des branches sur les modules critiques. Une branche non couverte signale souvent un cas oublié, pas seulement un test manquant.

## Tests d'intégration : mocker les frontières seulement

Le piège : tout mocker pour aller vite. Le test passe alors que l'intégration réelle est cassée. La règle :

- mocker uniquement les frontières externes (HTTP tiers, paiement, e-mail) ;
- utiliser une vraie base de test (Supabase en local via sa CLI, ou un Postgres jetable) ;
- tester les chemins d'erreur autant que les chemins heureux.

```text
Écris un test d'intégration pour POST /api/wiki :
1. Crée un utilisateur de test authentifié.
2. Body valide : statut 201 et une ligne en base.
3. Sans en-tête Authorization : statut 401.
4. Body invalide : statut 400 avec un message explicite.
5. Vérifie qu'aucune ligne n'a été créée dans les cas 3 et 4.
```

## Tests end-to-end : peu nombreux mais critiques

Les tests E2E sont lents et coûteux à maintenir. Réservez-les aux parcours qui font vivre le produit : inscription, paiement, action principale.

```text
Écris un test Playwright pour le parcours d'inscription :
1. Visite /auth.
2. Clique sur « Continuer avec Google » (réponse OAuth simulée).
3. Vérifie la redirection vers /dashboard et le nom de l'utilisateur dans la barre de navigation.
Sélecteurs par rôle ou par `data-testid`, jamais par classe CSS.
```

```bash
npx playwright test
npx playwright show-report
```

## Écrire les tests avant le code

Pour une nouvelle fonctionnalité, inversez l'ordre. La documentation propose un schéma en deux sessions : une instance de Claude écrit les tests à partir de la spécification, une autre écrit le code qui les fait passer. Celle qui implémente ne peut pas « adapter » les tests à son code.

```text
Session A : écris les tests de la fonction de calcul de TVA d'après SPEC.md.
            Ne crée pas l'implémentation. Vérifie que les tests échouent.
Session B : implémente la fonction pour faire passer tests/tva.test.ts
            sans modifier le fichier de tests.
```

## Vérifier la qualité, pas la quantité

Une couverture de 100 % ne veut rien dire si les tests sont creux. Signaux d'alerte :

- un test sans assertion (il appelle juste la fonction) ;
- un test qui mocke la fonction qu'il est censé tester ;
- un test qui passe encore quand on vide le corps de la fonction ;
- un test qui dépend de l'ordre d'exécution ou de l'heure.

Faites relire la suite par un regard neuf, dans un sous-agent qui n'a pas écrit les tests :

```text
Utilise un sous-agent pour relire tests/billing/. Pour chaque test :
quelle régression réelle empêcherait-il ? Passerait-il encore si on supprimait
la logique métier ? Liste les tests à réécrire, sans les modifier.
```

Le test de mutation (Stryker en JavaScript) mesure cela automatiquement : il modifie le code et vérifie que la suite échoue.

## Faire des tests un garde-fou permanent

Trois niveaux de contrainte, du plus léger au plus strict :

1. **Dans le prompt** : « lance les tests et corrige jusqu'à ce qu'ils passent ».
2. **Pour toute la session** : `/goal la commande npm test passe sans échec`. Un évaluateur séparé vérifie la condition après chaque tour et Claude continue tant qu'elle n'est pas remplie.
3. **De façon déterministe** : un hook `Stop` qui lance la suite et empêche Claude de terminer son tour tant qu'elle échoue.

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/tests-ok.sh" }
        ]
      }
    ]
  }
}
```

```bash
#!/bin/bash
# .claude/hooks/tests-ok.sh : bloque la fin du tour si les tests échouent
if ! npx vitest run --reporter=dot > /tmp/vitest.log 2>&1; then
  echo "Les tests échouent. Corrige-les avant de terminer :" >&2
  tail -n 30 /tmp/vitest.log >&2
  exit 2   # seul le code 2 bloque ; 1 serait ignoré
fi
exit 0
```

Pour ne pas ralentir chaque modification, un hook `PostToolUse` avec `"async": true` peut lancer les tests liés aux fichiers modifiés en arrière-plan (`npx vitest related --run <fichier>`) et ne prévenir Claude qu'en cas d'échec.

## Brancher sur le quotidien et la CI

```bash
# Avant le commit : tests liés aux fichiers modifiés
npx vitest related --run $(git diff --name-only --cached)

# Avant le push : suite complète
npm test

# En CI : couverture + E2E
npm run test:coverage && npm run test:e2e
```

Un seuil de couverture minimal en CI sur les dossiers critiques (configurable dans Vitest avec `coverage.thresholds`) évite que la suite se dégrade au fil des mois.
