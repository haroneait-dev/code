Un assistant qui lit votre dépôt peut aussi lire vos secrets. Ce qu'il lit part dans le contexte envoyé au modèle, reste dans la transcription locale de la session et peut finir recopié dans un fichier ou une commande. La protection se fait en couches : règles `deny`, sandbox, environnement nettoyé, hook de détection et contrôle en CI.

## Les couches de protection en un coup d'œil

| Couche | Ce qu'elle bloque | Ce qu'elle ne bloque pas |
| :- | :- | :- |
| `permissions.deny` avec `Read(...)` | Outils de fichiers de Claude, `@fichier`, commandes Bash reconnues (`cat`, `head`, `tail`, `sed`, `tee`) et redirections | `grep -r` sans nommer le fichier, un script Python ou Node qui ouvre le fichier lui-même |
| Sandbox (`/sandbox`) | Accès au niveau du système pour toutes les commandes shell et leurs sous-processus | Les outils Read, Edit, WebFetch (gérés par les permissions), les hooks et serveurs MCP |
| `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` | Variables d'identifiants dans l'environnement des sous-processus | Les secrets stockés dans des fichiers |
| Hook `PreToolUse` | Une valeur qui ressemble à un secret dans une commande ou un fichier écrit | Un secret au format inconnu de vos motifs |
| Scan en pre-commit et en CI | Un secret sur le point d'être commité ou poussé | Un secret déjà envoyé au modèle |

Aucune couche ne suffit seule. Les deux premières sont prioritaires.

## Couche 0 : pas de secret dans le code

Tous les secrets vivent dans `.env`, `.env.local` ou un gestionnaire (1Password, Doppler, variables d'environnement Vercel, AWS Secrets Manager). Le `.gitignore` les exclut :

```gitignore
.env
.env.*
!.env.example
*.pem
*.key
credentials.json
secrets/
```

Gardez un `.env.example` avec des valeurs factices : Claude peut le lire pour comprendre quelles variables existent, sans voir les vraies valeurs. Vérifiez avec `git check-ignore -v .env`.

Un secret commité une seule fois reste dans l'historique git. Supprimer le fichier dans un nouveau commit ne suffit pas : révoquez la clé et remplacez-la.

## Couche 1 : interdire la lecture avec `permissions.deny`

C'est la configuration recommandée par la documentation officielle. Dans `.claude/settings.json` (partagé avec l'équipe) ou `~/.claude/settings.json` (pour vous) :

```json
{
  "permissions": {
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)",
      "Read(./config/credentials.json)",
      "Read(**/*.pem)",
      "Read(**/*.key)"
    ]
  }
}
```

Ce que font ces règles :

- les fichiers correspondants disparaissent des résultats de recherche et Claude ne peut pas les lire ;
- une règle `Read` interdit aussi `Edit` et `Write` sur le même chemin ;
- elles s'appliquent aux commandes Bash que Claude Code reconnaît (`cat .env`, `head .env`) et aux redirections (`< .env`) ;
- un nom de fichier seul suit la logique du `.gitignore` : `Read(.env)` correspond à tout `.env` du projet, à n'importe quelle profondeur.

Pour bloquer tous les fichiers dont le nom se termine par `.env` sauf un exemple, ajoutez une négation après la règle, dans la même liste : `"Read(*.env)"` puis `"Read(!sample.env)"`. Le fichier `.claudeignore` n'a aucun effet : déplacez ses entrées dans des règles `Read` en deny.

**La limite à connaître.** Ces règles ne s'appliquent pas à une commande qui lit sans nommer le fichier (`grep -r API_KEY .`) ni à un script qui ouvre le fichier lui-même (`node -e "console.log(require('fs').readFileSync('.env','utf8'))"`). Une règle `Bash(...)` en deny n'est pas une frontière non plus : `Bash(curl *)` n'arrête pas `/usr/bin/curl` ni `sh -c 'curl ...'`. Pour une garantie au niveau du système, il faut la sandbox.

## Couche 2 : la sandbox

La sandbox isole les commandes shell de Claude et tous les processus qu'elles lancent (macOS, Linux et WSL2 ; elle n'existe pas sous Windows natif). Elle est désactivée par défaut : lancez `/sandbox` ou mettez `sandbox.enabled` à `true`.

Par défaut, une commande sandboxée peut lire presque tout le disque, y compris `~/.ssh` et `~/.aws/credentials`. Déclarez donc explicitement ce qui doit être protégé avec le bloc `credentials` :

```json
{
  "sandbox": {
    "enabled": true,
    "filesystem": {
      "denyRead": ["./.env", "./.env.local", "./secrets"]
    },
    "credentials": {
      "files": [
        { "path": "~/.aws/credentials", "mode": "deny" },
        { "path": "~/.ssh", "mode": "deny" }
      ],
      "envVars": [
        { "name": "GITHUB_TOKEN", "mode": "deny" },
        { "name": "NPM_TOKEN", "mode": "deny" }
      ]
    }
  }
}
```

Dans `.claude/settings.json`, un chemin en `./` part de la racine du projet ; dans vos réglages utilisateur, il part de `~/.claude`. Avec `"mode": "deny"`, les fichiers sont illisibles dans la sandbox et les variables sont retirées de l'environnement de chaque commande. Il n'existe pas de liste par défaut : seul ce que vous listez est protégé.

**Le mode `mask`.** Si une commande doit s'authentifier sans voir la vraie valeur (par exemple `gh` ou `npm publish`), utilisez `"mode": "mask"` : la commande voit un jeton de remplacement, et le proxy de la sandbox substitue la vraie valeur uniquement sur les requêtes vers les hôtes autorisés. Le masquage exige `network.tlsTerminate`, des domaines dans `network.allowedDomains`, et n'est accepté que dans vos réglages utilisateur ou les réglages gérés, jamais dans les fichiers du dépôt. La fonctionnalité est récente : suivez la page Sandboxing pour la configuration exacte.

La sandbox limite aussi le réseau : une commande ne peut joindre que les domaines autorisés, ce qui coupe la plupart des tentatives d'exfiltration.

## Couche 3 : nettoyer l'environnement des sous-processus

Les secrets ne sont pas que dans des fichiers. Une clé chargée dans votre shell (`export STRIPE_SECRET_KEY=...`) est héritée par Claude Code, donc par chaque commande Bash, hook et serveur MCP local qu'il lance.

```bash
export CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1
claude
```

Avec cette variable, Claude Code retire des sous-processus les identifiants Anthropic et cloud, les variables qu'il reconnaît comme des identifiants et les jetons contenus dans les URL de registres de paquets. Le processus principal les garde pour ses appels API. Sous Linux, les commandes Bash tournent aussi dans un espace de PID isolé. Ne l'activez pas si un outil a réellement besoin de ces variables.

Bonne pratique complémentaire : ne chargez pas vos secrets de production dans le shell où vous lancez Claude. Utilisez `direnv` ou le gestionnaire de secrets uniquement dans les terminaux qui en ont besoin.

## Couche 4 : un hook `PreToolUse` qui détecte les secrets

Les règles précédentes protègent des fichiers connus. Un hook attrape une valeur secrète au moment où Claude s'apprête à l'utiliser : collée dans une commande, recopiée dans un fichier de config, écrite dans un test.

Dans `.claude/settings.json` :

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash|Write|Edit",
        "hooks": [
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/scan-secrets.sh" }
        ]
      }
    ]
  }
}
```

Le script `.claude/hooks/scan-secrets.sh` (rendez-le exécutable avec `chmod +x`) :

```bash
#!/usr/bin/env bash
# Bloque l'outil si son entrée contient un motif de secret connu.
input=$(cat)
payload=$(jq -r '.tool_input | tostring' <<<"$input")

patterns='sk-ant-[A-Za-z0-9_-]{20,}|sk_live_[A-Za-z0-9]{20,}|ghp_[A-Za-z0-9]{36}|github_pat_[A-Za-z0-9_]{50,}|xox[bpa]-[A-Za-z0-9-]{20,}|AKIA[0-9A-Z]{16}|-----BEGIN [A-Z ]*PRIVATE KEY-----'

if grep -Eq "$patterns" <<<"$payload"; then
  echo "Secret détecté dans l'entrée de l'outil. Utilisez une variable d'environnement ou un fichier .env ignoré par git." >&2
  exit 2
fi
exit 0
```

Le code de sortie 2 bloque l'appel d'outil et le message d'erreur est renvoyé à Claude, qui peut corriger son approche. Adaptez les motifs à vos fournisseurs. Pour une détection plus complète, appelez un outil spécialisé comme gitleaks ou trufflehog depuis le script.

Gardez en tête que les hooks s'exécutent hors de la sandbox, avec vos droits complets : relisez-les comme du code de production.

## Couche 5 : détection avant le commit et en CI

- **Pre-commit local** : gitleaks ou trufflehog sur les fichiers indexés, via un hook git ou `pre-commit`.
- **CI** : le même scan sur chaque PR, plus la détection de secrets de votre forge (GitHub Secret Scanning et push protection).
- **Pendant l'écriture** : le plugin officiel security-guidance (`/plugin install security-guidance@claude-plugins-official`) accepte des motifs maison dans `.claude/security-patterns.yaml`, par exemple des préfixes de clés internes, et demande à Claude de corriger ce qu'il vient d'écrire.

## Si un secret a été exposé

Considérez-le comme compromis dès que Claude l'a lu, même « juste pour déboguer » : il a été envoyé au modèle et figure dans la transcription locale de la session (`~/.claude/projects/`, conservée 30 jours par défaut, réglable avec `cleanupPeriodDays`).

1. Révoquez la clé et générez-en une nouvelle.
2. Redéployez les services qui l'utilisent.
3. Vérifiez les journaux d'accès du fournisseur pour la période concernée.
4. Supprimez la transcription de la session si votre politique l'exige.
5. Ajoutez la règle `deny` ou le motif qui aurait évité l'incident.
