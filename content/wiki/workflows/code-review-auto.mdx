Claude peut relire votre code à trois moments : pendant que vous travaillez (dans le terminal), juste avant le merge (revue approfondie dans le cloud) et sur chaque pull request (directement dans GitHub). Cet article présente les outils officiels de 2026 pour chacun de ces moments, comment les régler et ce qu'ils coûtent. Ils préparent la revue humaine, ils ne la remplacent pas.

## Quel outil pour quel moment ?

| Moment | Outil | Où ça tourne | Coût |
| :- | :- | :- | :- |
| Pendant le travail | `/code-review` | Votre session, en sous-agent d'arrière-plan | Inclus dans votre usage normal |
| Avant un merge important | `/code-review ultra` (alias `/ultrareview`) | Bac à sable cloud d'Anthropic | 3 essais gratuits (Pro, Max), puis environ 5 à 25 $ par revue |
| Sur chaque PR, sans maintenance | Code Review (application GitHub) | Infrastructure d'Anthropic | 15 à 25 $ par revue en moyenne, offres Team et Enterprise |
| Sur chaque PR, dans votre CI | GitHub Action `claude-code-action` | Vos runners GitHub | Tokens API (ou abonnement) + minutes GitHub |
| Passe sécurité ciblée | `/security-review` | Votre session | Inclus dans votre usage normal |

## `/code-review` : relire un diff en local

`/code-review` est une skill intégrée. Elle cherche d'abord les bugs de correction (et, selon le modèle et l'effort, des pistes de simplification). Elle tourne en sous-agent d'arrière-plan avec son propre contexte : votre conversation reste propre et les remarques arrivent quand la revue est finie. `/review` est un alias.

```text
/code-review                     # commits de la branche + modifications non commitées
/code-review 1234                # une pull request
/code-review main...ma-feature   # une plage de commits
/code-review high --fix          # plus de couverture, puis application des corrections
/code-review --comment 1234      # publie les remarques en commentaires inline sur la PR
/code-review --max-findings all  # toutes les remarques au lieu de la limite habituelle
```

Points à connaître :

- **Niveau d'effort.** En `low` et `medium`, la revue ne remonte que ce dont elle est sûre (moins de faux positifs). De `high` à `max`, elle couvre plus large mais peut inclure des remarques moins certaines. Sans niveau précisé, la commande réutilise le dernier niveau que vous avez tapé.
- **`--max-findings`** (version 2.1.288) fixe le nombre de remarques. La valeur est mémorisée jusqu'à `--max-findings default`.
- **`--fix` en arrière-plan** modifie vos fichiers hors des checkpoints : `/rewind` ne les annule pas, utilisez git.
- La revue lit votre `CLAUDE.md`, mais pas `REVIEW.md` (réservé au service Code Review).
- Claude peut lancer `/code-review` de lui-même si vous demandez « relis mes changements ». Pour l'en empêcher tout en gardant la commande, ajoutez dans vos réglages `"skillOverrides": { "code-review": "user-invocable-only" }`.
- `/simplify` est une autre skill : elle nettoie le code (réutilisation, simplification, efficacité) et applique les corrections, mais ne cherche pas de bugs.

## `/code-review ultra` : la revue profonde avant le merge

Ultrareview lance une flotte d'agents relecteurs dans un bac à sable cloud. Chaque remarque est reproduite et vérifiée indépendamment avant de vous être rapportée, ce qui donne un rapport plus court et plus fiable. Comptez 5 à 10 minutes, pendant lesquelles votre terminal reste libre.

```text
/code-review ultra                          # branche courante contre la branche par défaut
/code-review ultra develop                  # contre une autre base
/code-review ultra 1234 --post              # une PR GitHub, avec publication du rapport en commentaire
/code-review ultra vérifie mes changements d'auth   # une note en langage naturel
```

À savoir avant de l'adopter :

- Il faut un compte claude.ai (pas une simple clé API). Ultrareview n'est pas disponible sur Bedrock, Google Cloud (Agent Platform), Microsoft Foundry, ni pour les organisations en Zero Data Retention. Dans ces cas, la commande retombe sur une revue locale.
- Pro et Max : 3 revues gratuites, une seule fois par compte, puis facturation en crédits d'usage (environ 5 à 25 $ selon la taille). Une boîte de dialogue affiche l'estimation avant chaque lancement.
- Limite par défaut d'une revue de branche : 500 fichiers et 8 000 lignes modifiées.
- Claude ne lance jamais ultrareview de lui-même, et une tâche planifiée non plus.
- Pour un script ou la CI, utilisez la sous-commande, qui attend le résultat (`claude -p '/code-review ultra'` rend la main sans attendre) :

```bash
claude ultrareview 1234 --json --timeout 30 > findings.json
# code de sortie : 0 = revue terminée, 1 = échec ou délai dépassé, 130 = interrompue
```

## Code Review sur GitHub : la revue gérée par Anthropic

Code Review (préversion de recherche, offres Team et Enterprise) relit vos pull requests sans que vous écriviez de workflow. Plusieurs agents analysent le diff dans le contexte de tout le dépôt, une étape de vérification filtre les faux positifs, puis les remarques sont publiées en commentaires inline.

**Mise en place.** Un Owner de l'organisation Claude ouvre `claude.ai/admin-settings/claude-code`, installe l'application GitHub Claude et choisit les dépôts. Pour chaque dépôt, trois déclencheurs :

- **Once after PR creation** : une revue à l'ouverture de la PR (ou au passage en « ready for review ») ;
- **After every push** : une revue à chaque push, la plus complète et la plus chère ;
- **Manual** : rien d'automatique, on commente `@claude review` (une fois) ou `@claude review always` (puis à chaque push).

**Lire les résultats.** Chaque remarque porte une sévérité : 🔴 Important (à corriger avant le merge), 🟡 Nit (mineur), 🟣 Pre-existing (bug déjà présent, pas introduit par la PR). Le check run « Claude Code Review » se termine toujours en neutre : il ne bloque jamais un merge. Pour bloquer sur les remarques Important, lisez le résumé machine du check run dans votre propre CI (la documentation donne la commande `gh api` + `jq`).

**Régler ce qui est signalé avec `REVIEW.md`.** Ce fichier à la racine du dépôt est lu par les agents qui cherchent et vérifient les remarques. C'est le levier le plus efficace contre le bruit :

```markdown
# Instructions de revue

## Ce que « Important » veut dire ici
Réserver Important aux bugs qui cassent un comportement, exposent des données
ou empêchent un rollback : requêtes non filtrées par tenant, données personnelles
dans les logs, migrations non rétrocompatibles. Le style est au mieux un Nit.

## Limiter les nits
Au plus cinq Nits par revue. Au-delà, écrire « plus N points similaires » dans le résumé.

## Ne pas signaler
- Ce que la CI vérifie déjà : lint, formatage, erreurs de types
- Les fichiers générés sous `src/gen/` et les fichiers `*.lock`

## Toujours vérifier
- Chaque nouvelle route `/api/*` vérifie le token Supabase
- Toute affirmation sur un comportement cite un `fichier:ligne`
```

Votre `CLAUDE.md` est aussi lu : une violation nouvelle des règles qu'il contient remonte en Nit, et Claude signale quand une PR rend une consigne du `CLAUDE.md` obsolète.

**Coût.** 15 à 25 $ par revue en moyenne, facturés en crédits d'usage hors forfait. Un plafond mensuel se règle dans `claude.ai/admin-settings/usage`. Une PR venant d'un fork n'est relue que sur demande explicite (`@claude review`).

## La GitHub Action : la revue dans votre CI

Si vous voulez garder la main sur le prompt, le modèle et les déclencheurs, ou si vous n'êtes pas sur Team ou Enterprise, utilisez `anthropics/claude-code-action@v1`. Le plus simple : lancer `/install-github-app` dans Claude Code, qui installe l'application, enregistre le secret et prépare la PR avec les fichiers de workflow.

Workflow de revue officiel, qui exécute le plugin `code-review` sur chaque PR :

```yaml
# .github/workflows/claude-review.yml
name: Code Review
on:
  pull_request:
    types: [opened, synchronize, ready_for_review, reopened]

jobs:
  review:
    if: github.event.pull_request.draft == false
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: read
      issues: read
      id-token: write
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          plugin_marketplaces: "https://github.com/anthropics/claude-code.git"
          plugins: "code-review@claude-code-plugins"
          prompt: "/code-review:code-review --comment ${{ github.repository }}/pull/${{ github.event.pull_request.number }}"
          claude_args: '--allowedTools "mcp__github_inline_comment__create_inline_comment"'
```

Deux lignes comptent : `--comment` fait publier la revue sur la PR (sinon, elle reste dans les logs du job), et `claude_args` doit nommer l'outil de commentaire inline, sinon le serveur qui publie les commentaires ne démarre pas.

Pièges fréquents :

- Les anciennes entrées `command:` et `post_comment:` n'existent pas : on passe par `prompt` et `claude_args`.
- Avec un abonnement Claude, remplacez `anthropic_api_key` par `claude_code_oauth_token: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}` (jeton créé avec `claude setup-token`). Pour une organisation, préférez une clé API ou la fédération d'identité OIDC.
- Sur un dépôt public, GitHub ne transmet pas les secrets aux PR venant de forks : la revue ne tourne que sur les branches du dépôt.
- Limitez la dépense avec `--max-turns` dans `claude_args`, un `timeout-minutes` sur le job et les contrôles `concurrency` de GitHub.

## Ajouter une passe sécurité

`/security-review` analyse le diff entre votre branche et la branche par défaut d'`origin` (injections, authentification, exposition de données). Il lui faut un remote `origin`. Pour la sécurité, les autres couches sont décrites dans [Faux positifs en audit de sécurité](/wiki/workflows/faux-positifs-audit) : plugin security-guidance pendant l'écriture, plugin Claude Security pour un scan profond, Action `claude-code-security-review` en CI.

## Garder la revue utile

- **Commencez en mode manuel** (Code Review) ou sur un label, puis élargissez quand le signal est bon.
- **Mesurez** : notez sur une vingtaine de PR combien de remarques étaient justes. Sur Code Review, les réactions 👍 / 👎 sur chaque commentaire servent à cela, et le tableau `claude.ai/analytics/code-review` suit l'activité et le coût.
- **Ne chassez pas chaque remarque.** Un relecteur à qui l'on demande des problèmes en trouve toujours. Demandez de ne signaler que ce qui touche la correction ou les exigences.
- **Gardez un humain sur l'intention.** Claude vérifie que le code fait ce qu'il dit, pas qu'il fait ce que le produit attend.
