Un nouveau développeur passe ses premières semaines à reconstruire ce que l'équipe sait déjà. Claude Code peut réduire ce délai : il répond aux questions sur le code en lisant les fichiers, et un dépôt bien préparé lui donne le contexte que les anciens ont en tête. Il ne remplace pas le mentor, il lui évite les questions de surface.

## Ce que l'équipe prépare avant l'arrivée

### Un `CLAUDE.md` court et à jour

`CLAUDE.md` à la racine est chargé au début de chaque session. C'est le premier levier : un nouvel arrivant qui lance `claude` dans le dépôt a d'emblée un assistant briefé. (Si le dépôt n'a qu'un `AGENTS.md`, Claude Code le lit à la place.)

Pour démarrer, `/init` analyse le projet et génère un premier `CLAUDE.md`. Gardez ensuite ce qui n'est pas évident en lisant le code :

```markdown
# Projet Facturation

## Commandes
- `npm run dev` : serveur local (port 3000)
- `npm test -- src/billing` : tests d'un module
- `npm run db:reset` : base locale avec données de démo

## Architecture
- Next.js App Router ; API dans app/api/, logique métier dans lib/
- Supabase pour l'auth et la base ; toutes les routes API vérifient le token

## Conventions
- Pas de logique métier dans les composants React
- Une migration SQL par PR, jamais de modification d'une migration publiée

## Pièges connus
- Les montants sont en centimes (entiers), jamais en float
- Les tests e2e exigent `SUPABASE_URL` pointant vers la base locale
```

Les recommandations officielles insistent sur la concision : un `CLAUDE.md` trop long dilue les consignes importantes. Pour la documentation détaillée, faites des liens (`Voir docs/architecture.md pour le détail des flux`) ou déplacez les procédures dans des skills chargées à la demande. `/doctor` sait repérer et alléger un `CLAUDE.md` trop gros, et `/doctor prompt-audit` signale les consignes obsolètes ou contradictoires.

### Des réglages partagés dans le dépôt

Versionnez `.claude/settings.json` pour que le nouvel arrivant ait d'emblée les bonnes permissions, sans accumuler les demandes de validation ni ouvrir trop large :

```json
{
  "permissions": {
    "allow": ["Bash(npm test *)", "Bash(npm run lint)", "Bash(npm run dev)"],
    "deny": ["Read(./.env)", "Read(./.env.*)", "Bash(git push *)"]
  }
}
```

Les règles `allow` d'un dépôt ne s'appliquent qu'après que la personne a accepté la boîte de dialogue de confiance du dossier ; les règles `deny` et `ask` s'appliquent tout de suite. Si l'équipe utilise des serveurs MCP (Linear, Sentry, base de données), déclarez-les dans `.mcp.json` à la racine : chaque développeur les approuvera au premier lancement.

### Un guide généré avec `/team-onboarding`

Un membre de l'équipe qui utilise déjà Claude Code peut lancer `/team-onboarding`. Claude analyse ses sessions, commandes et serveurs MCP des 30 derniers jours et produit un guide en Markdown que le nouvel arrivant colle comme premier message pour être configuré rapidement. Sur les offres claude.ai Pro, Max, Team et Enterprise, la commande renvoie aussi un lien de partage que le collègue ouvre directement dans Claude Code. Relisez le guide avant de l'envoyer : il reflète les habitudes d'une personne, pas forcément les conventions de l'équipe.

## Premier jour : explorer en posant des questions

La documentation officielle le présente comme un usage efficace : posez à Claude les questions que vous poseriez à un collègue, sans technique de prompt particulière.

```text
Donne-moi une vue d'ensemble de ce dépôt : architecture, dossiers clés, flux principaux.
Explique le flux d'authentification, de la page de connexion jusqu'à la vérification du token côté API.
Pourquoi utilise-t-on Hono plutôt qu'Express dans server/ ?
Quels tests dois-je lancer si je modifie src/billing/ ?
Où est géré l'envoi des e-mails de facturation ?
```

Deux réglages aident à apprendre plutôt qu'à seulement recevoir des réponses :

- `/output-style explanatory` : Claude ajoute de courts blocs « Insight » qui expliquent ses choix et le code du dépôt.
- `/output-style learning` : Claude explique et vous laisse écrire vous-même de petits morceaux de code.

Pour les questions larges (« comment fonctionne la facturation ? »), Claude délègue souvent la lecture au sous-agent intégré Explore, qui parcourt les fichiers dans son propre contexte et ne renvoie qu'un résumé. Votre conversation reste légère.

## Des visites guidées réutilisables avec des skills

Plutôt que de réexpliquer le module d'authentification à chaque arrivée, écrivez-le une fois sous forme de skill. Les anciennes commandes de `.claude/commands/` fonctionnent toujours, mais les skills sont le format actuel.

```markdown
---
name: tour-auth
description: Visite guidée du module d'authentification pour un nouvel arrivant
disable-model-invocation: true
---

Fais une visite guidée du module d'authentification :
1. Lis lib/auth/, app/auth/callback/route.ts et middleware.ts.
2. Explique le flux complet en 6 étapes maximum, avec pour chaque étape
   le fichier et la fonction concernés (format `fichier:ligne`).
3. Liste les trois pièges que l'équipe a déjà rencontrés (voir docs/incidents/auth.md).
4. Termine par trois questions pour vérifier la compréhension, sans donner les réponses.
```

Enregistrez ce fichier sous `.claude/skills/tour-auth/SKILL.md` : le nouvel arrivant tape `/tour-auth`. `disable-model-invocation: true` réserve la skill à un appel explicite. Créez-en autant que de zones clés (`/tour-deploy`, `/tour-billing`). Pour partager ces skills entre plusieurs dépôts, regroupez-les dans un plugin d'équipe.

Un quiz fonctionne aussi très bien :

```text
Pose-moi 10 questions sur l'architecture de ce dépôt, une à la fois.
Corrige chaque réponse en citant les fichiers concernés.
```

## Une première PR dans la journée

Donnez un petit ticket dès le premier jour : un libellé, un log manquant, un test à écrire. Le but est de parcourir tout le circuit (branche, commit, CI, revue) en 24 heures. Claude aide à trouver le bon fichier et à respecter les conventions.

Avant de demander une revue humaine, le nouvel arrivant lance une revue automatique :

```text
/code-review
```

La skill relit les modifications de la branche dans un contexte séparé et remonte les bugs probables, en tenant compte du `CLAUDE.md`. Les relecteurs humains peuvent alors se concentrer sur le fond : l'intention métier, l'architecture, ce que Claude ne peut pas deviner.

## Faire évoluer le dispositif

- Notez les questions qui reviennent la première semaine : chacune signale un manque dans `CLAUDE.md` ou dans une skill.
- Demandez au nouvel arrivant de compléter lui-même `CLAUDE.md` à la fin de sa première semaine, avec ce qui lui a manqué.
- Mesurez quelques indicateurs simples : délai jusqu'à la première PR mergée, jusqu'à la première mise en production, nombre de questions posées sur Slack.
- Relancez `/doctor prompt-audit` de temps en temps : un `CLAUDE.md` faux est pire qu'un `CLAUDE.md` absent.
