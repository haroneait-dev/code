Données personnelles, santé, finance, secrets industriels : dès que votre projet en manipule, utiliser un assistant IA pose des questions juridiques et techniques. La règle générale tient en trois mots : minimiser, anonymiser, tracer. Cet article explique ce que Claude Code envoie et conserve, puis comment configurer un projet pour que les données réelles n'y entrent pas.

## Ce qui part, et où ça reste

Claude Code tourne sur votre machine, mais tout ce que Claude lit pour répondre (prompts, contenu des fichiers ouverts, sorties de commandes) est envoyé au modèle via l'API, chiffré en transit (TLS 1.2 ou plus). Conséquence directe : un fichier que Claude lit est un fichier envoyé.

**Côté Anthropic** (documentation officielle, octobre 2026) :

| Type de compte | Entraînement | Conservation |
| :- | :- | :- |
| Free, Pro, Max | Seulement si vous l'avez accepté dans vos réglages de confidentialité | 5 ans si l'entraînement est accepté, 30 jours sinon |
| Team, Enterprise, API (conditions commerciales) | Non, sauf adhésion volontaire (Development Partner Program) | 30 jours en standard |
| Enterprise avec Zero Data Retention | Non | Rien n'est conservé après la réponse, sauf obligation légale ou lutte contre les abus |

La Zero Data Retention (ZDR) n'est pas incluse dans l'offre Enterprise standard : elle est accordée organisation par organisation par Anthropic, après vérification d'éligibilité. Elle couvre l'inférence de Claude Code, pas le chat claude.ai, Cowork, ni les données traitées par des serveurs MCP ou outils tiers. Elle désactive aussi les fonctions qui stockent des données côté serveur, comme les sessions cloud. Sur Amazon Bedrock, Google Cloud ou Microsoft Foundry, ce sont les politiques de conservation de ces plateformes qui s'appliquent.

**Sur votre machine** : les transcriptions de session sont stockées en clair dans `~/.claude/projects/` pendant 30 jours par défaut, pour permettre `/resume`. Réduisez la durée avec `cleanupPeriodDays` dans vos réglages si des données sensibles risquent d'y passer.

**Deux envois à surveiller** :

- `/feedback` (et `/bug`, `/share`) envoie la conversation, code compris, conservée 5 ans. Désactivez-le avec `DISABLE_FEEDBACK_COMMAND=1` sur les postes concernés.
- La télémétrie OpenTelemetry de votre organisation n'inclut pas le texte des prompts par défaut. Les variables `OTEL_LOG_USER_PROMPTS`, `OTEL_LOG_TOOL_DETAILS` et `OTEL_LOG_RAW_API_BODIES` l'ajoutent : ne les activez que si votre collecteur est lui-même traité comme un stockage de données sensibles.

## Cartographier ce qui est sensible

Avant d'ouvrir Claude Code sur un projet, listez ce qui y circule :

- **Données personnelles directes** : nom, e-mail, téléphone, adresse, IP, numéro de sécurité sociale.
- **Données indirectement identifiantes** : combinaisons qui permettent de retrouver une personne (âge, code postal, profession).
- **Catégories particulières au sens du RGPD** (article 9) : santé, opinions politiques, convictions religieuses, orientation sexuelle, données biométriques.
- **Données financières** : IBAN, numéros de carte, transactions.
- **Secrets techniques** : clés API, jetons, certificats (voir [l'article dédié](/wiki/workflows/secrets-env)).
- **Informations confidentielles** : contrats, données clients sous accord de confidentialité, code propriétaire d'un tiers.

Pour chaque catégorie, décidez : autorisée en clair, autorisée seulement anonymisée, ou interdite à Claude.

## Garder les données réelles hors du contexte

### Travailler sur la structure, pas sur les valeurs

Neuf fois sur dix, pour déboguer, Claude a besoin de la forme des données, pas des vraies valeurs. Donnez-lui :

- le schéma de la base (`pg_dump --schema-only`) plutôt qu'un dump complet ;
- un exemple de payload avec des valeurs factices ;
- des jeux de données synthétiques générés avec Faker, ou Synthea pour des dossiers médicaux fictifs.

Pour des logs de production, masquez avant de les donner à Claude, par exemple avec Microsoft Presidio, qui détecte et remplace noms, e-mails, numéros de téléphone ou de carte. Mieux encore : demandez à Claude d'écrire le script de masquage, relisez-le, exécutez-le vous-même, puis donnez-lui le résultat.

### Interdire l'accès aux dossiers sensibles

Rangez exports, dumps et sauvegardes dans des dossiers identifiés, puis bloquez-les dans `.claude/settings.json` :

```json
{
  "permissions": {
    "deny": [
      "Read(./exports/**)",
      "Read(./dumps/**)",
      "Read(./backups/**)",
      "Read(**/*.sql.gz)",
      "Read(./.env)",
      "Read(./.env.*)"
    ]
  }
}
```

Ces règles bloquent les outils de fichiers de Claude et les commandes shell reconnues comme `cat` ou `head`. Elles n'arrêtent pas un script qui ouvre le fichier lui-même. Pour une garantie au niveau du système, activez la sandbox et ajoutez les mêmes dossiers dans `sandbox.filesystem.denyRead`.

### Bloquer l'accès direct à la base de production

Le risque le plus courant n'est pas un fichier, c'est une requête. Si Claude peut lancer `psql` avec une URL de production, il peut lire des millions de lignes personnelles en une commande. Réglages conseillés :

- ne chargez jamais d'URL de base de production dans le shell où tourne Claude ;
- activez `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` pour retirer les identifiants reconnus de l'environnement des commandes ;
- si Claude doit interroger une base, donnez-lui une copie anonymisée ou un utilisateur en lecture seule limité à quelques vues agrégées ;
- avec la sandbox, n'autorisez pas l'hôte de la base de production dans `network.allowedDomains`.

## Conformité : les points à vérifier

Ce qui suit n'est pas un avis juridique ; faites valider par votre DPO.

- **Base légale et information** : l'envoi de données personnelles à un sous-traitant d'IA doit reposer sur une base légale et figurer dans votre registre des traitements.
- **Contrat** : vérifiez l'accord de traitement des données (DPA) de votre fournisseur, qu'il s'agisse d'Anthropic ou d'une plateforme cloud.
- **Localisation** : si vos données doivent rester dans l'Union européenne, vérifiez pour chaque modèle les régions proposées par Bedrock, Google Cloud ou Microsoft Foundry ; les disponibilités changent.
- **Analyse d'impact** (AIPD, article 35 du RGPD) : recommandée avant d'introduire un agent IA sur un nouveau périmètre de données personnelles, obligatoire pour les traitements à risque élevé.
- **Secteurs régulés** : en France, l'hébergement de données de santé exige un hébergeur certifié HDS ; certains marchés publics demandent une qualification SecNumCloud. Vérifiez ce que couvre votre fournisseur avant de faire passer ces données par un modèle.
- **Violation** : une fuite de données personnelles se notifie à la CNIL dans les 72 heures (article 33). Prévoyez la procédure à l'avance.

## Cadrer les usages par rôle

Tout le monde n'a pas besoin du même accès. Une matrice simple, documentée dans un `DATA_POLICY.md` référencé par le `CLAUDE.md` :

| Profil | Ce que Claude peut voir |
| :- | :- |
| Développeurs | Code, schémas, données synthétiques |
| Support niveau 2 | Extraits anonymisés pour reproduire un bug |
| DPO, sécurité | Extraits réels, dans un environnement isolé et journalisé |

En entreprise, imposez les règles qui comptent avec les réglages gérés (managed settings) : les développeurs ne peuvent pas les assouplir dans leurs réglages personnels.

## Prouver ce qui a été fait

En cas de contrôle (CNIL, ISO 27001, SOC 2, HDS), vous devez pouvoir dire quelles données ont été envoyées, sur quelle base, combien de temps elles ont été conservées et quelles mesures de minimisation étaient en place. La télémétrie OpenTelemetry de Claude Code donne la trace des actions (commandes, fichiers, décisions de permission) par utilisateur. La mise en place est décrite dans [Audit trail](/wiki/workflows/audit-trail).
