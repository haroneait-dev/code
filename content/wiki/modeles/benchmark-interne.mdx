Les benchmarks publics donnent un repère pour comparer les modèles. Ils ne remplacent jamais une évaluation sur vos données : un modèle meilleur « en moyenne » peut être moins bon sur votre cas précis. Cette page explique comment lire les chiffres publiés et comment construire votre propre suite d'évaluation.

## Les benchmarks que vous croiserez

Les annonces de 2026 ont largement délaissé les tests de culture générale, devenus trop faciles, au profit de tâches agentiques longues.

| Benchmark | Ce qu'il mesure | À savoir |
|---|---|---|
| **Terminal-Bench** | Tâches réelles en ligne de commande (compiler, configurer, déboguer) | Très utilisé pour les agents de code. Plusieurs versions coexistent : comparez à version égale. |
| **SWE-bench Verified** | Corriger un vrai bug dans un dépôt Python à partir d'une issue GitHub | 500 tâches validées à la main. Proche de la saturation pour les modèles de pointe. |
| **OSWorld** | Utiliser un ordinateur (interface graphique) pour accomplir une tâche | Référence pour le computer use. |
| **Humanity's Last Exam (HLE)** | Questions expertes très difficiles | Résultats souvent donnés « avec outils » et « sans outils ». |
| **GDPval** | Tâches de travail de connaissance évaluées par des professionnels | Score parfois exprimé en Elo. |
| **MMLU, HumanEval** | Culture générale en QCM, petites fonctions Python (164 problèmes) | Saturés : utiles comme contrôle rapide, pas pour départager les modèles récents. |

Exemple de lecture : l'annonce d'Opus 5.5 donne 66,4 % sur Terminal-Bench 4.0 **en effort `xhigh`**, avec une erreur type d'environ 2,6 points. Sans l'effort et la marge d'erreur, le chiffre ne veut pas dire grand-chose.

## Les pièges de lecture

- **Le niveau d'effort.** Un même modèle donne des scores très différents en `medium` et en `max`, pour un coût très différent. Comparez à effort égal, ou comparez à coût égal.
- **L'outillage (scaffold).** Un score SWE-bench obtenu avec Claude Code n'est pas comparable à un score obtenu avec un autre harnais. Lisez les notes de méthodologie.
- **Les tentatives multiples.** Certains scores agrègent plusieurs essais ou une sélection du meilleur. Cherchez « pass@1 » ou le nombre d'essais.
- **La version du benchmark.** Terminal-Bench 2.x et 4.0, OSWorld et OSWorld 2.x ne sont pas interchangeables. SWE-bench Verified n'est pas SWE-bench complet.
- **La marge d'erreur.** Un écart de 1 ou 2 points est souvent dans le bruit.
- **La contamination.** Un benchmark public ancien peut se retrouver dans les données d'entraînement. Les jeux récents ou privés sont plus fiables.

## Construire votre propre suite d'évaluation

### 1. Collecter des cas réels

Rassemblez 30 à 100 cas issus de votre produit : tickets, requêtes d'utilisateurs, bugs déjà corrigés. Anonymisez, puis fixez pour chacun un attendu ou un critère de réussite. Incluez des cas limites et des cas où le modèle doit refuser ou demander une précision.

### 2. Choisir une métrique automatisable

| Type de sortie | Métrique |
|---|---|
| JSON, classification | Correspondance exacte, validation de schéma |
| Code | Le code compile et les tests passent |
| Texte libre | Grille notée par un modèle juge (LLM-as-judge), contrôlée par un échantillon humain |

### 3. Rejouer à chaque changement

Relancez la suite à chaque nouveau modèle, nouveau prompt ou changement d'effort. Gardez les résultats (CSV, table Postgres) pour suivre l'évolution.

```python
import json
import anthropic

client = anthropic.Anthropic()
cases = [json.loads(line) for line in open("evals/support.jsonl")]

def run(model: str, effort: str) -> float:
    ok = 0
    for case in cases:
        r = client.messages.create(
            model=model,
            max_tokens=300,
            output_config={"effort": effort},
            system="Classe le ticket : facturation, technique ou commercial. Un seul mot.",
            messages=[{"role": "user", "content": case["input"]}],
        )
        text = next(b.text for b in r.content if b.type == "text").strip().lower()
        ok += text == case["expected"]
    return ok / len(cases)

for effort in ["low", "medium", "high"]:
    print(effort, run("claude-sonnet-5-5", effort))
```

Ce petit balayage d'effort est le premier test à faire à chaque migration : la documentation d'Anthropic recommande de ne pas reprendre l'ancien réglage tel quel, car les niveaux sont recalibrés d'un modèle à l'autre.

### Outils utiles

- **promptfoo** : configuration YAML, comparaison de modèles et de prompts, adapté à la CI.
- **Inspect AI** (UK AI Security Institute) : framework d'évaluation open source.
- **Braintrust** et équivalents : interface de suivi des expériences.
- Un simple script avec le SDK, lancé en parallèle avec une limite de débit, suffit souvent pour commencer.
