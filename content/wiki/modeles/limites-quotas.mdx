L'API Claude applique deux types de limites à chaque organisation : un **plafond de dépense mensuel** et des **limites de débit** (requêtes et tokens par minute). Les connaître évite les erreurs `429` en production et aide à dimensionner vos traitements.

## Les paliers d'usage

Votre organisation est placée automatiquement sur un palier selon son historique d'usage et l'état du compte. Elle monte avec le temps, sans démarche particulière. Une organisation récente peut démarrer sur un palier d'évaluation, en dessous des limites standard, le temps de constituer un historique.

| Palier | Plafond de dépense mensuel |
|---|---|
| Start | 500 $ |
| Build | 1 000 $ |
| Scale | 200 000 $ |
| Custom | Aucun plafond, limites négociées avec l'équipe commerciale |

Vous voyez votre palier et vos limites dans la Console, page **Settings > Limits**. Pour aller plus haut, utilisez **Request rate limit increase** sur cette même page, ou le support pour un besoin urgent.

## Les limites de débit par modèle

Trois compteurs s'appliquent par modèle : requêtes par minute (RPM), tokens d'entrée par minute (ITPM) et tokens de sortie par minute (OTPM).

| Modèle | Start (RPM / ITPM / OTPM) | Build | Scale |
|---|---|---|---|
| Opus 5.5 | 1 000 / 2M / 400K | 5 000 / 5M / 1M | 10 000 / 10M / 2M |
| Sonnet 5.5 | 1 000 / 2M / 400K | 5 000 / 5M / 1M | 10 000 / 10M / 2M |
| Haiku 4.5 | 1 000 / 2M / 400K | 5 000 / 5M / 1M | 10 000 / 10M / 2M |
| Fable 5.x (limite commune 5 et 5.1) | 1 000 / 500K / 100K | 2 000 / 1,5M / 300K | 4 000 / 4M / 800K |

Ce sont des maximums, pas des garanties. Quelques règles utiles :

- **Algorithme du seau à jetons** : la capacité se recharge en continu, elle ne se remet pas à zéro chaque minute. Une rafale courte peut donc déclencher une `429` même sous la moyenne (60 RPM peut être appliqué comme 1 requête par seconde).
- **Le cache est gratuit pour l'ITPM** : sur presque tous les modèles, les tokens lus depuis le cache (`cache_read_input_tokens`) ne comptent pas dans l'ITPM. Avec 80 % de cache, une limite de 2M ITPM permet de traiter environ 10M tokens d'entrée par minute.
- **`max_tokens` ne pénalise pas l'OTPM** : seuls les tokens réellement générés comptent.
- **Limites par modèle** : vous pouvez utiliser plusieurs modèles en parallèle, chacun jusqu'à sa limite. Opus 5.5 et Sonnet 5.5 ont chacun leur propre compteur.
- **Limites d'accélération** : une hausse brutale de trafic peut déclencher des `429`. Montez en charge progressivement.

L'API Batch a ses propres limites (par exemple 100 000 requêtes par lot), indépendantes de celles du Messages API.

## Plafond de dépense atteint

Quand le plafond mensuel du palier est atteint, l'API répond `429` avec `error.details.error_code: "enforced_spend_limit_reached"` et **sans en-tête `retry-after`**. Réessayer ne sert à rien : l'accès reprend le 1er du mois suivant à 00:00 UTC, ou dès que vous passez à un palier supérieur.

Vous pouvez aussi fixer votre propre limite, plus basse, dans **Settings > Billing**. Quand elle est atteinte, l'API renvoie une erreur `400` (`invalid_request_error`). Des limites peuvent également être posées par workspace.

## Lire les en-têtes de réponse

Chaque réponse porte des en-têtes qui décrivent votre consommation :

| En-tête | Contenu |
|---|---|
| `retry-after` | Secondes à attendre avant de réessayer (sur une `429` de débit) |
| `anthropic-ratelimit-requests-limit` / `-remaining` / `-reset` | Requêtes |
| `anthropic-ratelimit-tokens-limit` / `-remaining` / `-reset` | Limite de tokens la plus contraignante en cours |
| `anthropic-ratelimit-input-tokens-limit` / `-remaining` / `-reset` | Tokens d'entrée |
| `anthropic-ratelimit-output-tokens-limit` / `-remaining` / `-reset` | Tokens de sortie |

Les valeurs `-reset` sont au format RFC 3339. Les valeurs `-remaining` des tokens sont arrondies au millier.

```ts
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic({ maxRetries: 3 }); // retries avec backoff intégrés

const { data, response } = await client.messages
  .create({
    model: "claude-sonnet-5-5",
    max_tokens: 512,
    messages: [{ role: "user", content: "Bonjour" }],
  })
  .withResponse();

const remaining = Number(response.headers.get("anthropic-ratelimit-input-tokens-remaining"));
const limit = Number(response.headers.get("anthropic-ratelimit-input-tokens-limit"));
if (remaining / limit < 0.1) {
  // ralentir la file d'attente avant de toucher la limite
}
```

## Gérer les 429

1. **Respectez `retry-after`** quand il est présent. Les SDK officiels réessaient déjà automatiquement avec un backoff exponentiel.
2. **Distinguez débit et dépense** : sans `retry-after` et avec `enforced_spend_limit_reached`, inutile de réessayer.
3. **Séparez les flux** : interactif d'un côté, traitements de fond de l'autre, avec une file à priorités.
4. **Basculez le hors ligne vers l'API Batch** : 50 % moins cher et limites séparées.
5. **Maximisez le cache** : c'est le moyen le plus simple d'augmenter votre débit utile.
