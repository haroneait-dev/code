Sur le code, une erreur de raisonnement au début se paie cher : mauvais diagnostic, patch à côté, tests qui passent par hasard. La réflexion de Claude (*thinking*) donne au modèle la place d'explorer et de vérifier avant d'agir. Cette page montre comment l'exploiter dans un agent de code avec les modèles actuels, où la réflexion se règle par l'**effort** et non plus par un budget de tokens.

## Pourquoi la réflexion aide sur le code

Quand il réfléchit, le modèle peut :

1. **Formuler plusieurs hypothèses** avant d'écrire une ligne.
2. **Vérifier la cohérence** entre les fichiers lus et le patch proposé.
3. **Anticiper les effets de bord** : autres appels de la fonction, tests existants.
4. **Changer d'avis** quand un résultat d'outil contredit son hypothèse.

Le dernier point repose sur la **réflexion entrelacée** : avec le mode adaptatif, Claude réfléchit aussi entre deux appels d'outils (lecture de fichier, exécution de tests), sans configuration supplémentaire.

Anthropic publie ses résultats de benchmark avec le niveau d'effort utilisé. Par exemple, l'annonce d'Opus 5.5 donne 66,4 % sur Terminal-Bench 4.0 en effort `xhigh`. Comparez toujours des chiffres obtenus au même effort et avec le même outillage. Voir [Benchmarks et évaluation](/wiki/modeles/benchmark-interne).

## Activer la réflexion dans un agent de code

Sur Opus 5.5 et Sonnet 5.5, la réflexion est active par défaut. Vous choisissez seulement l'effort.

```ts
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

const tools: Anthropic.Tool[] = [
  {
    name: "read_file",
    description: "Lit un fichier du dépôt",
    input_schema: { type: "object", properties: { path: { type: "string" } }, required: ["path"] },
  },
  {
    name: "run_tests",
    description: "Lance la suite de tests et renvoie la sortie",
    input_schema: { type: "object", properties: {} },
  },
];

const res = await client.messages.create({
  model: "claude-sonnet-5-5",
  max_tokens: 64000,
  output_config: { effort: "high" },
  system: "Vous êtes un agent de débogage. Lisez le code, formulez un diagnostic, proposez un patch unifié.",
  tools,
  messages: [{ role: "user", content: `Bug :\n${bugReport}` }],
});
```

Renvoyez les blocs `thinking` tels quels dans l'historique à chaque tour de la boucle d'outils : ils portent le raisonnement derrière les appels.

### Quel effort pour quelle tâche ?

| Tâche | Point de départ |
|---|---|
| Renommage, boilerplate, mise en forme | `low` |
| Correction ciblée avec un bon rapport de bug | `medium` |
| Bug difficile, plusieurs fichiers | `high` |
| Refactor large, session autonome de plus de 30 minutes | `xhigh` |
| Problème qui résiste à `xhigh` sur vos evals | `max` |

Sur Opus 5.5, l'effort par défaut est `medium`. Si une correction vous semble bâclée, montez l'effort avant de changer de modèle. Sur Sonnet 5.5, la documentation conseille `medium` pour les tâches agentiques bien spécifiées et `high` pour les plus longues, avec `max_tokens` à 128 000 et une réponse en streaming.

## Patterns qui marchent

### Planifier fort, exécuter léger

Faites produire un plan détaillé par Opus 5.5 en `high` ou `xhigh`, puis exécutez chaque étape avec Sonnet 5.5 en `medium`. Dans Claude Code, l'[advisor](/wiki/cli/effort-fast-advisor) automatise ce schéma : le modèle principal consulte un modèle plus fort aux moments clés.

### Relire son propre patch

Un second appel court sur le diff, avec une question précise (« Ce patch peut-il casser un autre appelant de `parseDate` ? »), attrape des régressions avant la CI. Un effort `medium` suffit souvent.

### Borner une boucle longue

Pour un agent autonome, combinez `max_tokens` (plafond par requête) et un task budget (enveloppe indicative pour toute la boucle, en bêta). Voir [Raisonnement adaptatif et effort](/wiki/modeles/adaptive-thinking-effort).

## Quand la réflexion n'aide pas

| Tâche | Pourquoi |
|---|---|
| Reformater du JSON | Tâche déterministe |
| Renommer une variable | Rien à raisonner |
| Générer un composant à partir d'une maquette très précise | Le modèle sait déjà quoi écrire |
| Compléter des types ou des DTO | Latence inutile |

Sur ces tâches, un effort `low` réduit la réflexion au minimum. Sur Sonnet 5.5, `thinking: {"type": "between_tools"}` supprime la réflexion préalable.

## Latence et coût

Plus l'effort est haut, plus le premier token de la réponse arrive tard et plus la facture monte : les tokens de réflexion sont facturés comme de la sortie, même quand leur texte est masqué. Il n'existe pas de chiffre de latence universel : mesurez sur vos requêtes, via `usage.output_tokens_details.thinking_tokens` et le temps jusqu'au premier token.

Pour un éditeur interactif (autocomplétion, suggestions en ligne), gardez un modèle rapide et un effort bas. Pour un agent qui travaille en arrière-plan, le temps de réflexion est rentable.

## Combiner réflexion et prompt caching

```ts
const res = await client.messages.create({
  model: "claude-sonnet-5-5",
  max_tokens: 64000,
  output_config: { effort: "medium" },
  system: [
    { type: "text", text: PROJECT_CONVENTIONS, cache_control: { type: "ephemeral" } },
  ],
  tools,
  messages,
});
```

Gardez le même effort pendant toute la conversation : un changement d'effort au niveau de la requête invalide le cache. Sur Sonnet 5.5, le préfixe minimal pour le cache est de 512 tokens.

## Bonnes pratiques

- **Affichez la réflexion en debug seulement**, avec `display: "summarized"`.
- **Ne demandez pas au modèle de recopier son raisonnement** dans la réponse : sur les modèles 5.5, cela peut déclencher un refus `reasoning_extraction`.
- **Faites un balayage d'effort** sur votre propre jeu de bugs avant de fixer un réglage en production.
