Un prompt qui marchait hier peut se comporter autrement demain. On parle de *model drift*. Avec Claude, la cause est rarement un changement caché du modèle : c'est le plus souvent un alias qui pointe vers un nouveau modèle, une migration, ou un retrait. Cette page explique d'où viennent ces écarts et comment s'en protéger.

## Comment fonctionnent les ID de modèles

| Génération | Format de l'ID | Exemple | Comportement |
|---|---|---|---|
| 4.6 et suivantes | Sans date | `claude-sonnet-5-5`, `claude-opus-5-5` | L'ID **est** l'instantané. Il ne change jamais. |
| Avant la 4.6 | Avec date | `claude-haiku-4-5-20251001` | Instantané figé. |
| Avant la 4.6 | Alias court | `claude-haiku-4-5` | Pointe vers le dernier instantané daté de cette version. |

Point important : un ID sans date comme `claude-sonnet-5-5` n'est **pas** un pointeur vers « la dernière version ». Anthropic ne modifie pas les poids ni la configuration d'un ID existant. Une nouvelle version sort toujours sous un nouvel ID.

Il n'existe pas d'alias `-latest` pour les modèles actuels. Si votre code en contient un, il date d'une ancienne génération.

## D'où viennent les écarts

1. **Un alias qui bouge.** Dans Claude Code, les alias `opus`, `sonnet` ou `best` suivent les nouvelles versions : depuis fin septembre 2026, `sonnet` désigne Sonnet 5.5 et `opus` Opus 5.5. Côté API, les alias courts d'avant la 4.6 peuvent aussi changer de cible.
2. **L'infrastructure de service.** Les poids sont figés, mais le routage, les classifieurs de sécurité ou la logique d'échantillonnage peuvent évoluer. La documentation reconnaît que cela peut produire de légères différences observables sur un même ID.
3. **Une migration de modèle.** Passer de Sonnet 5 à Sonnet 5.5 change le comportement : effort recalibré, nouvelles catégories de refus, outils forcés refusés, texte entre outils renvoyé en blocs `thinking`.
4. **Un retrait.** Après la date de retrait, les requêtes vers le modèle échouent. Exemples : Opus 4 et Sonnet 4 retirés le 15 juin 2026, Opus 4.1 le 5 août 2026, Sonnet 4.5 prévu le 30 novembre 2026.
5. **Vos propres changements** : prompt système, outils, effort, version de SDK. C'est souvent la vraie cause.

## Épingler le bon modèle

En production, utilisez un ID complet et stockez-le en configuration :

```ts
// À éviter : alias de Claude Code ou alias court d'avant la 4.6
model: "sonnet"
model: "claude-haiku-4-5"

// À faire : ID figé, lu depuis la configuration
model: process.env.CLAUDE_MODEL_ID ?? "claude-sonnet-5-5"
```

Dans Claude Code, pour figer le modèle d'une équipe, indiquez un ID complet dans les réglages (`"model": "claude-sonnet-5-5"`) plutôt qu'un alias.

Sur Amazon Bedrock et Google Cloud, les dates de retrait sont fixées par le fournisseur cloud et peuvent différer de celles de l'API Claude.

## Suivre les retraits

- Anthropic prévient par e-mail au moins **60 jours** avant le retrait d'un modèle public.
- La page [Model deprecations](https://platform.claude.com/docs/en/about-claude/model-deprecations) liste les statuts (Active, Legacy, Deprecated, Retired) et les remplaçants conseillés.
- Pour savoir où vous utilisez encore un ancien modèle : Console, page **Usage**, bouton **Export**, puis filtrez le CSV par modèle et par clé API.
- Dans Claude Code, `/claude-api migrate` aide à appliquer une migration (changement d'ID et paramètres incompatibles) sur toute une base de code.

## Construire des tests de régression

Une suite de régression pour LLM ressemble à une suite de tests classique :

1. **Jeu de référence** : 30 à 100 cas représentatifs, avec un attendu ou un critère.
2. **Plusieurs métriques** : correspondance exacte pour le JSON, tests fonctionnels pour le code, modèle juge pour le texte libre.
3. **Instantané des sorties** : gardez les réponses du modèle de référence pour comparer deux versions de façon lisible.
4. **Exécution automatique** : à chaque modification de prompt, et à chaque migration de modèle.

Outils : promptfoo, Inspect AI, ou un script maison avec le SDK et des snapshots de test. Voir [Benchmarks et évaluation](/wiki/modeles/benchmark-interne).

## Détecter un écart en production

- **Journalisez** pour chaque appel : ID du modèle, effort, longueur de sortie, `stop_reason`, nombre d'appels d'outils, latence.
- **Suivez des agrégats** : longueur moyenne, taux de `refusal`, part de `max_tokens`, part de tokens de réflexion (`usage.output_tokens_details.thinking_tokens`).
- **Relisez un échantillon** à la main chaque semaine.

Une règle simple : si la longueur moyenne des réponses ou le taux de refus change de plus de 20 % sur une semaine sans changement de votre côté, ouvrez une enquête.

## Plan de migration

1. Lancer la suite de régression sur l'ancien et le nouveau modèle.
2. Comparer qualité, coût, latence et refus. Refaire un balayage d'effort.
3. Corriger les prompts qui régressent.
4. Déployer derrière un drapeau de fonctionnalité, par paliers (1 %, 10 %, 100 %).
5. Garder l'ancien modèle en repli tant qu'il n'est pas retiré.
