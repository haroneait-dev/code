Dès qu'un projet compte plus de deux hooks, plusieurs scripts écoutent le même événement : un formateur et un linter sur `PostToolUse`, un garde de sécurité sur `PreToolUse`, un logger partout. Un point surprend souvent : Claude Code **ne les enchaîne pas** dans l'ordre du fichier. Cette page explique ce qui se passe vraiment et comment construire une chaîne fiable.

## Règle n° 1 : les hooks correspondants tournent en parallèle

Pour un événement donné, Claude Code sélectionne tous les groupes dont le `matcher` correspond, puis lance **tous** leurs handlers **en même temps**. L'ordre de déclaration dans `settings.json` ne garantit aucun ordre d'exécution.

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/format.sh" },
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/lint.sh" }
        ]
      },
      {
        "matcher": "*",
        "hooks": [
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/log.sh", "async": true }
        ]
      }
    ]
  }
}
```

Après un `Edit`, `format.sh`, `lint.sh` et `log.sh` démarrent simultanément. Si `lint.sh` lit le fichier pendant que `format.sh` le réécrit, le résultat est imprévisible. Préfixer les scripts par `01-`, `02-` ne change rien.

Autres règles utiles :

- **Dédoublonnage** : un handler identique défini dans plusieurs fichiers de réglages ne tourne qu'une fois. La copie d'un plugin ou d'une skill reste en revanche distincte.
- **Matchers** : `"*"`, `""` ou absence de matcher = tout. `Edit|Write` (ou `Edit, Write`) = liste exacte. Tout autre caractère fait passer en expression régulière JavaScript non ancrée : `Edit.*` attrape aussi `NotebookEdit`, écrivez `^Edit$` pour une correspondance stricte.
- **Filtre `if`** : sur les événements d'outil, un handler peut porter un champ `if` en syntaxe de règle de permission (`"Bash(git *)"`, `"Edit(*.ts)"`) pour ne démarrer que dans les cas utiles. Ce filtre est « au mieux » : pour une interdiction stricte, utilisez les règles de permission.

## D'où viennent les hooks

Les hooks s'**additionnent** entre sources au lieu de se remplacer :

| Source | Emplacement |
|---|---|
| Utilisateur | `~/.claude/settings.json` |
| Projet partagé | `.claude/settings.json` |
| Projet local | `.claude/settings.local.json` |
| Organisation | réglages gérés (`managed-settings.json`, MDM, console) |
| Plugin | `hooks/hooks.json` du plugin |
| Skill ou sous-agent | frontmatter, actif seulement pendant leur exécution |

Côté administration : `allowManagedHooksOnly` (réglage géré) bloque les hooks utilisateur, projet, local et plugin, sauf ceux des plugins imposés par l'organisation. `"disableAllHooks": true` coupe temporairement tous les hooks, mais seul ce réglage posé au niveau géré désactive les hooks gérés.

## Comment Claude Code combine les résultats

Comme les hooks tournent en parallèle, Claude Code ne « transmet » rien de l'un à l'autre : il **agrège** leurs sorties.

### Décisions `PreToolUse`

Si plusieurs hooks `PreToolUse` renvoient des décisions différentes, la priorité est :

```
deny  >  defer  >  ask  >  allow
```

Un seul `deny` suffit donc à bloquer l'appel, quel que soit l'ordre d'arrivée. Un `exit 2` est traité comme un `deny` : le contenu de `stderr` sert de motif pour Claude. Les règles `deny` et `ask` de vos permissions restent évaluées même si un hook renvoie `allow`.

### Contexte ajouté

Quand plusieurs hooks renvoient `additionalContext` pour le même événement, Claude reçoit **toutes** les valeurs.

### Modification de l'entrée

`updatedInput` remplace l'objet d'entrée complet de l'outil. La documentation ne définit pas de fusion entre plusieurs hooks qui modifient la même entrée : ne confiez cette tâche qu'à **un seul** hook par outil.

### Codes de sortie

| Code | Effet |
|---|---|
| `0` | Succès. Le JSON sur `stdout` est interprété s'il est présent. |
| `2` | Erreur bloquante, sur les événements qui le permettent (`PreToolUse`, `UserPromptSubmit`, `Stop`, `SubagentStop`, `PreCompact`, `ConfigChange`, etc.). `stderr` est transmis à Claude. |
| Autre | Erreur non bloquante : l'action continue. |

Un `exit 2` **n'interrompt pas** les autres hooks : ils sont déjà lancés. Un hook qui modifie le dépôt dans `PreToolUse` peut donc agir alors qu'un autre hook bloque l'appel. Gardez les hooks `PreToolUse` sans effet de bord.

Sur `PostToolUse`, l'outil a déjà tourné : `decision: "block"` ne l'annule pas, il ajoute votre `reason` à côté du résultat pour que Claude corrige le tir.

## Obtenir un vrai pipeline : le dispatcher

Quand l'ordre compte (formater **puis** linter), déclarez **un seul** handler qui appelle les étapes l'une après l'autre :

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/post-edit.sh", "timeout": 120 }
        ]
      }
    ]
  }
}
```

```bash
#!/usr/bin/env bash
# .claude/hooks/post-edit.sh : formatage puis lint, dans cet ordre
set -uo pipefail

input=$(cat)
file=$(jq -r '.tool_input.file_path // empty' <<<"$input")
[ -z "$file" ] && exit 0

case "$file" in
  *.ts|*.tsx|*.js|*.jsx) ;;
  *) exit 0 ;;
esac

# Étape 1 : formatage (un échec ne bloque pas la suite)
npx prettier --write "$file" >/dev/null 2>&1 || true

# Étape 2 : lint, sur le fichier déjà formaté
if ! out=$(npx eslint "$file" 2>&1); then
  jq -n --arg r "ESLint signale des erreurs dans $file :
$out" '{decision: "block", reason: $r}'
  exit 0
fi
exit 0
```

Avantages : ordre garanti, un seul point d'entrée à tester (`echo '{...}' | .claude/hooks/post-edit.sh`), et un `timeout` global maîtrisé. Rendez le script exécutable avec `chmod +x`.

## Partager de l'état entre hooks

Chaque handler reçoit le même JSON sur `stdin` et ne peut pas modifier celui des autres. Pour partager de l'état :

- **Fichier indexé par session** : écrivez sous un dossier nommé d'après `session_id`. Comme les hooks tournent en parallèle, n'utilisez ce fichier qu'entre événements successifs (un `PreToolUse` qui prépare, un `PostToolUse` qui lit), jamais entre deux hooks du même événement.
- **Variables pour les commandes Bash** : un hook `SessionStart` (ainsi que `Setup`, `CwdChanged` et `FileChanged`) peut ajouter des lignes `export` dans le fichier désigné par `CLAUDE_ENV_FILE`. Utilisez `>>` pour ne pas écraser ce qu'ont écrit d'autres hooks.

```bash
#!/usr/bin/env bash
# PreToolUse : mémorise l'heure de début de chaque appel
input=$(cat)
sid=$(jq -r '.session_id' <<<"$input")
tid=$(jq -r '.tool_use_id' <<<"$input")
dir="${TMPDIR:-/tmp}/claude-hooks/$sid"
mkdir -p "$dir"
date +%s > "$dir/$tid.start"
exit 0
```

Un hook `PostToolUse` lit ensuite `$dir/$tid.start` pour calculer la durée de l'appel.

## Hooks lents : `async` et `asyncRewake`

- `"async": true` lance le hook en arrière-plan sans bloquer Claude (le `timeout` n'est alors pas appliqué). Idéal pour la journalisation ou les notifications.
- `"asyncRewake": true` tourne aussi en arrière-plan, mais réveille Claude si le script sort en `2` : sa sortie est présentée comme un rappel système. Pratique pour une suite de tests longue qui doit signaler un échec.

Délais par défaut : 600 s pour les hooks `command`, `http` et `mcp_tool` (30 s sur `UserPromptSubmit`), 30 s pour `prompt`, 60 s pour `agent`. Fixez un `timeout` explicite sur tout hook qui appelle le réseau.

## Déboguer l'ordre réel

Lancez `claude --debug` puis lisez `~/.claude/debug/<session-id>.txt` (ou choisissez le fichier avec `--debug-file <chemin>`) : chaque exécution de hook y est journalisée avec son événement et son résultat. `CLAUDE_CODE_DEBUG_LOG_LEVEL=verbose` ajoute le détail des correspondances de matchers. `/hooks` affiche la configuration active, toutes sources confondues.

## Anti-patterns

- **Compter sur l'ordre du fichier** : il n'en a aucun. Un dispatcher si l'ordre compte.
- **Deux hooks qui écrivent le même fichier** sur le même événement : condition de course garantie.
- **Effets de bord dans `PreToolUse`** : l'appel peut être refusé par un autre hook lancé en parallèle.
- **Plusieurs `updatedInput` sur le même outil** : comportement non défini.
- **Hook bloquant et lent** : passez-le en `async` s'il n'a pas besoin de bloquer.
