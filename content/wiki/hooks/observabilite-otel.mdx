Dès qu'un agent Claude Code tourne pour une équipe, en CI ou sur la durée, il faut mesurer ce qu'il fait : coûts, tokens, outils utilisés, durées, blocages. Claude Code exporte nativement ces données en OpenTelemetry (OTel). Les hooks ne remplacent pas cette télémétrie : ils la complètent avec vos propres données (ticket, résultat de tests, règle métier déclenchée).

## Commencer par la télémétrie native

Tout se règle par variables d'environnement, dans votre shell ou dans le bloc `env` des settings (gérés de préférence, pour une flotte) :

```bash
export CLAUDE_CODE_ENABLE_TELEMETRY=1
export OTEL_METRICS_EXPORTER=otlp          # otlp, prometheus, console, none
export OTEL_LOGS_EXPORTER=otlp             # otlp, console, none
export OTEL_EXPORTER_OTLP_PROTOCOL=grpc    # obligatoire : pas de valeur par défaut
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
export OTEL_EXPORTER_OTLP_HEADERS="Authorization=Bearer votre-token"
claude
```

Pour vérifier : la métrique `claude_code.session.count` doit apparaître au démarrage, et l'événement `claude_code.user_prompt` après un premier prompt. Si rien n'arrive, lancez `claude --debug-file /tmp/claude.log` et cherchez les lignes `[3P telemetry]`.

### Ce que vous obtenez

| Signal | Exemples |
|---|---|
| Métriques | `claude_code.cost.usage` (USD), `claude_code.token.usage`, `claude_code.lines_of_code.count`, `claude_code.commit.count`, `claude_code.pull_request.count`, `claude_code.active_time.total` |
| Événements (logs) | `user_prompt`, `api_request`, `api_error`, `tool_result`, `tool_decision`, `compaction`, `subagent_completed` |
| Événements de hooks | `hook_registered`, `hook_execution_start`, `hook_execution_complete` |
| Traces (bêta) | span racine `claude_code.interaction`, enfants `claude_code.llm_request` et `claude_code.tool` |

Chaque événement porte `prompt.id`, qui relie tout ce qu'a produit un même prompt, et des attributs standard (`session.id`, `user.account_uuid`, `organization.id`, `user.email` si disponible…).

### Observer vos hooks sans écrire de code

Les événements dédiés aux hooks répondent déjà à la plupart des questions :

- `claude_code.hook_registered` : un événement par hook configuré au démarrage, avec `hook_event`, `hook_type` (`command`, `http`, `mcp_tool`, `prompt`, `agent`) et `hook_source` (`userSettings`, `projectSettings`, `policySettings`, `pluginHook`…). Idéal pour inventorier les hooks d'une flotte.
- `claude_code.hook_execution_complete` : par passage, `hook_name` (par exemple `PreToolUse:Write`), `num_hooks`, `num_success`, `num_blocking`, `num_non_blocking_error`, `num_cancelled` et `total_duration_ms`.

Avec ces deux événements, vous suivez la latence de vos hooks, leur taux d'erreur et le nombre d'actions bloquées par une politique, sans toucher aux scripts.

### Les traces

Le traçage est en bêta et désactivé par défaut :

```bash
export CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1
export OTEL_TRACES_EXPORTER=otlp
```

Chaque prompt ouvre un span `claude_code.interaction` ; les requêtes au modèle et les outils en sont les enfants, et les spans des sous-agents s'imbriquent sous l'outil `Agent`. Un span `claude_code.hook` existe aussi, mais seulement avec le traçage « détaillé » (`ENABLE_BETA_TRACING_DETAILED=1` et `BETA_TRACING_ENDPOINT`), qui change la destination des données : lisez la documentation avant de l'activer.

Quand le traçage est actif, les commandes lancées par les outils `Bash` et `PowerShell` reçoivent une variable `TRACEPARENT` : un script instrumenté peut rattacher ses propres spans à la trace de l'outil.

### Confidentialité

Par défaut, Claude Code n'exporte ni le texte des prompts, ni les réponses, ni les arguments des outils : seulement des longueurs et des métadonnées. Chaque contenu s'active explicitement :

| Variable | Ajoute |
|---|---|
| `OTEL_LOG_USER_PROMPTS=1` | Texte des prompts |
| `OTEL_LOG_ASSISTANT_RESPONSES=1` | Texte des réponses |
| `OTEL_LOG_TOOL_DETAILS=1` | Commandes Bash, arguments d'outils, noms de skills et de serveurs MCP |
| `OTEL_LOG_TOOL_CONTENT=1` | Contenu des sorties d'outils dans les spans (traçage requis) |

Ces données partent uniquement vers votre collecteur, jamais vers Anthropic. Activez-les en connaissance de cause : une commande Bash peut contenir un secret.

## Compléter avec des hooks

Les hooks servent quand vous voulez une donnée que la télémétrie ne connaît pas : le ticket associé, le résultat d'un `npm test`, la règle de sécurité qui a bloqué, le nom du client. La clé est de **corréler** vos enregistrements avec les événements natifs :

| Champ du hook | Attribut OTel correspondant |
|---|---|
| `prompt_id` | `prompt.id` sur tous les événements |
| `tool_use_id` | `tool_use_id` sur `tool_result` et `tool_decision` |
| `session_id` | `session.id` |

### Écrire dans un tampon local

N'appelez pas votre backend directement depuis un hook bloquant : la latence réseau s'ajouterait à chaque outil. Écrivez une ligne JSON dans un fichier, et laissez un agent de collecte (OpenTelemetry Collector avec le récepteur `filelog`, Vector, Fluent Bit) l'expédier.

```bash
#!/bin/bash
# .claude/hooks/emit.sh : un enregistrement par événement
mkdir -p "$HOME/.claude/telemetry"
jq -c --arg ts "$(date -u +%FT%TZ)" --arg host "$(hostname)" '{
  ts: $ts, host: $host,
  event: .hook_event_name, session_id, prompt_id, tool_use_id,
  tool: .tool_name, agent: .agent_type,
  duration_ms, error,
  bash: (if .tool_name == "Bash" then (.tool_input.command | .[0:200]) else null end)
} | with_entries(select(.value != null))' >> "$HOME/.claude/telemetry/hooks.jsonl"
exit 0
```

```json
{
  "hooks": {
    "PostToolUse":        [{ "matcher": "*", "hooks": [{ "type": "command", "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/emit.sh", "args": [], "async": true }] }],
    "PostToolUseFailure": [{ "matcher": "*", "hooks": [{ "type": "command", "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/emit.sh", "args": [], "async": true }] }],
    "Stop":               [{ "hooks": [{ "type": "command", "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/emit.sh", "args": [], "async": true }] }]
  }
}
```

`"async": true` sort l'écriture du chemin critique. Le script tronque la commande Bash à 200 caractères : appliquez la même discipline de rédaction que pour la télémétrie native, et filtrez les secrets avant export.

### Un hook HTTP vers votre propre service

Si vous avez déjà un service d'ingestion, un hook `http` envoie le JSON de l'événement en POST, sans script :

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "*",
        "hooks": [
          {
            "type": "http",
            "url": "https://ingest.exemple.internal/claude-hooks",
            "timeout": 5,
            "headers": { "Authorization": "Bearer $INGEST_TOKEN" },
            "allowedEnvVars": ["INGEST_TOKEN"]
          }
        ]
      }
    ]
  }
}
```

Le service doit répondre vite par un 2xx (corps vide). Une erreur réseau n'interrompt pas Claude, mais un hook `http` est synchrone : un service lent ralentit chaque outil. Côté entreprise, `allowedHttpHookUrls` limite les URL autorisées.

## Langfuse, Phoenix et autres outils LLM

Les plateformes d'observabilité orientées LLM, comme Langfuse ou Arize Phoenix, acceptent des traces OpenTelemetry. La voie la plus simple consiste à envoyer les traces natives de Claude Code vers un OpenTelemetry Collector, puis à le configurer pour exporter vers ces outils en OTLP. Vérifiez dans leur documentation l'URL d'ingestion OTLP et l'authentification attendues. Gardez les hooks pour les attributs métier que vous voulez joindre aux mêmes `session.id` et `prompt.id`.

## Tableaux de bord utiles

- Coût et tokens par utilisateur, équipe (`OTEL_RESOURCE_ATTRIBUTES=team.id=...`) ou dépôt.
- Durée p95 de chaque hook (`hook_execution_complete.total_duration_ms`) et nombre de blocages (`num_blocking`).
- Taux d'échec par outil (`tool_result` avec `success: "false"`).
- Top des commandes Bash (avec `OTEL_LOG_TOOL_DETAILS=1`).
- Erreurs d'API par type, à croiser avec un hook `StopFailure`.
