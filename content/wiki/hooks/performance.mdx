Un hook synchrone retarde l'action qu'il encadre. Un `PostToolUse` de 2 secondes sur chaque édition, c'est 2 secondes de plus par fichier modifié, et un `UserPromptSubmit` lent retarde chaque prompt. Cet article montre comment mesurer, réduire le nombre d'exécutions et sortir les tâches longues du chemin critique.

## Mesurer avant d'optimiser

### Avec la télémétrie native

Si vous activez OpenTelemetry (`CLAUDE_CODE_ENABLE_TELEMETRY=1` et un exportateur de logs), Claude Code émet un événement `claude_code.hook_execution_complete` à chaque passage, avec `hook_event`, `hook_name` (par exemple `PostToolUse:Write`), `num_hooks` et `total_duration_ms`. C'est la mesure la plus fiable, sans modifier vos scripts (voir [Hooks pour l'observabilité](/wiki/hooks/observabilite-otel)).

### Avec un wrapper

Sans télémétrie, enveloppez le script :

```bash
#!/bin/bash
# .claude/hooks/timed.sh <nom> <script> : mesure la durée d'un hook
NAME="$1"; shift
START=$(date +%s%N)
"$@"
CODE=$?
MS=$(( ($(date +%s%N) - START) / 1000000 ))
printf '{"hook":"%s","ms":%d,"exit":%d}\n' "$NAME" "$MS" "$CODE" \
  >> "$CLAUDE_PROJECT_DIR/.claude/hook-metrics.jsonl"
exit "$CODE"
```

```json
{
  "type": "command",
  "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/timed.sh",
  "args": ["format", "${CLAUDE_PROJECT_DIR}/.claude/hooks/format.sh"]
}
```

Le script mesuré hérite du stdin du wrapper. Après quelques sessions, calculez le 95e centile par hook :

```bash
jq -s 'group_by(.hook) | map({hook: .[0].hook, n: length,
  p95: (map(.ms) | sort | .[(length * 0.95 | floor)])})' .claude/hook-metrics.jsonl
```

`date +%s%N` fonctionne avec GNU coreutils ; sur un macOS ancien, installez `coreutils` (`gdate`).

## Lancer moins de hooks

Le hook le plus rapide est celui qui ne démarre pas.

1. **Un `matcher` précis** : `"Edit|Write"` plutôt que `"*"` sur `PostToolUse`. Sans matcher, le hook tourne aussi après chaque `Read`, `Grep` ou `Glob`.
2. **Le champ `if`** : il filtre sur les arguments avant de lancer le processus. `"if": "Edit(*.ts)"` évite de démarrer le script pour un fichier Markdown, et `"if": "Bash(git push *)"` ne lance le contrôle que sur les pushs.

```json
{
  "matcher": "Edit|Write",
  "hooks": [
    {
      "type": "command",
      "if": "Edit(*.ts)",
      "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/lint-ts.sh",
      "args": []
    }
  ]
}
```

`if` ne s'applique qu'aux événements d'outils (`PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PermissionRequest`, `PermissionDenied`). Sur un autre événement, un hook avec `if` ne tourne jamais.

3. **Le bon événement** : pour une action qui dépend du lot complet d'outils (relancer les tests une fois après plusieurs éditions parallèles), `PostToolBatch` s'exécute une seule fois par lot, là où `PostToolUse` se déclenche pour chaque outil.

## Fixer des timeouts réalistes

Le `timeout` s'exprime en secondes. Les valeurs par défaut sont larges : 600 s pour `command`, `http` et `mcp_tool`, ramenées à 30 s sur `UserPromptSubmit`, `PreModelSwitch` et `PostModelSwitch`, et à 10 s sur `MessageDisplay`. Les hooks `prompt` ont 30 s, les hooks `agent` 60 s, et `SessionEnd` un budget partagé de 1,5 s.

```json
{
  "type": "command",
  "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/format.sh",
  "args": [],
  "timeout": 10
}
```

À l'expiration, le hook est annulé et sa sortie ignorée. Sur `PreToolUse`, cela signifie que l'appel continue sans décision : un timeout serré sur un hook de sécurité peut ouvrir une brèche. Réglez-le assez haut pour que le contrôle aboutisse, et rendez le contrôle rapide.

## Sortir les tâches longues du chemin critique

### `async: true`

Un hook `command` avec `"async": true` démarre en arrière-plan et Claude continue aussitôt. Quand il se termine, ses champs `additionalContext` et `systemMessage` sont transmis à Claude au tour suivant.

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/run-tests-async.sh",
            "args": [],
            "async": true
          }
        ]
      }
    ]
  }
}
```

Limites : un hook async ne peut plus rien bloquer ni décider (`decision`, `permissionDecision`, `continue` sont ignorés), son `timeout` n'est pas appliqué, chaque déclenchement crée un processus distinct (pas de déduplication) et, en mode `-p`, les hooks encore actifs sont tués à la fin.

### `asyncRewake: true`

Variante pour les vérifications longues dont l'échec doit être signalé : le hook tourne en arrière-plan et, s'il sort en `exit 2`, Claude est réveillé immédiatement, même si la session est inactive. Son stderr (ou stdout si stderr est vide) lui est présenté comme un rappel système. Le `timeout` reste appliqué.

```json
{
  "type": "command",
  "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/integration-tests.sh",
  "args": [],
  "asyncRewake": true,
  "timeout": 900
}
```

### Le détachement manuel

Pour un travail qui doit survivre à la session (upload, indexation), lancez un processus complètement détaché depuis le hook :

```bash
#!/bin/bash
INPUT=$(cat)
nohup /usr/local/bin/indexer.sh <<<"$INPUT" >/tmp/indexer.log 2>&1 &
exit 0
```

## Les pièges classiques

- **Démarrage de runtime** : lancer Node ou Python a un coût fixe à chaque appel. Pour un hook déclenché sur chaque outil, un script shell court ou un daemon interrogé via socket est souvent plus rapide. Mesurez avant de réécrire.
- **Commande trop large** : `prettier --write "**/*.ts"` reformate tout le projet. Ciblez le fichier : `jq -r '.tool_input.file_path'`.
- **Réseau synchrone** : un `curl` dans un hook bloquant ajoute la latence réseau. Mettez `--max-time`, ou passez en `async`.
- **`SessionStart` lent** : la première réponse de chaque session l'attend.
- **Sorties volumineuses** : au-delà de 10 000 caractères, `additionalContext` et stdout sont déportés dans un fichier. Un contexte injecté trop long coûte aussi des tokens à chaque tour.
- **Croire que les hooks s'enchaînent** : les hooks d'un même événement tournent en parallèle. Le temps ressenti est celui du plus lent, pas la somme. Regrouper n'accélère que si les scripts se disputent les mêmes ressources.

## Profiler un hook isolé

```bash
echo '{"tool_name":"Edit","tool_input":{"file_path":"/home/me/projet/src/big.ts"}}' \
  | time .claude/hooks/format.sh
```

Un `real` très supérieur à `user + sys` signale une attente (disque, réseau, verrou). Un `user` élevé indique un calcul coûteux : changez d'outil ou utilisez son mode daemon (`eslint_d`, serveur Biome).
