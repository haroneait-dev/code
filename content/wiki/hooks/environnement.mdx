Un hook s'exécute dans un contexte précis : un JSON sur stdin, des variables d'environnement, un répertoire courant et un shell. Connaître ces canaux permet d'écrire des hooks portables, qui fonctionnent quel que soit le dossier où Claude travaille, sur macOS, Linux ou Windows.

## Les champs JSON communs

Chaque événement envoie ses champs propres (`tool_input`, `prompt`, `source`…), plus une enveloppe commune :

| Champ | Contenu |
|---|---|
| `session_id` | Identifiant de la session |
| `prompt_id` | UUID du prompt en cours, identique à l'attribut `prompt.id` de la télémétrie (absent avant le premier prompt) |
| `transcript_path` | Chemin du transcript JSONL, écrit de façon asynchrone (peut avoir un temps de retard) |
| `cwd` | Répertoire de travail au moment du hook |
| `scratchpad_dir` | Répertoire de travail temporaire de la session, s'il existe |
| `permission_mode` | `default`, `plan`, `acceptEdits`, `auto`, `dontAsk` ou `bypassPermissions` (pas sur tous les événements) |
| `effort` | Objet `{"level": "..."}` avec le niveau d'effort, sur les événements liés aux outils et à `Stop` |
| `hook_event_name` | Nom de l'événement |
| `agent_id`, `agent_type` | Présents dans un sous-agent, ou avec `claude --agent` |

Le mode **Manual** de l'interface arrive sous la valeur `"default"`.

Pour lire le JSON une seule fois et en extraire plusieurs champs :

```bash
#!/bin/bash
INPUT=$(cat)
EVENT=$(jq -r '.hook_event_name' <<<"$INPUT")
CWD=$(jq -r '.cwd' <<<"$INPUT")
TOOL=$(jq -r '.tool_name // empty' <<<"$INPUT")
```

Le modèle actif n'est **pas** dans l'enveloppe. Seul `SessionStart` peut recevoir un champ `model` (pas toujours), et `PreModelSwitch` / `PostModelSwitch` reçoivent `from_model` et `to_model`. Il n'existe pas de variable `$CLAUDE_MODEL`.

## Les variables d'environnement

Un hook hérite de l'environnement du processus `claude`, auquel Claude Code ajoute :

| Variable | Disponible | Rôle |
|---|---|---|
| `CLAUDE_PROJECT_DIR` | Tous les hooks | Racine du projet où la session a démarré |
| `CLAUDE_PLUGIN_ROOT` | Hooks de plugin | Dossier d'installation du plugin |
| `CLAUDE_PLUGIN_DATA` | Hooks de plugin | Dossier de données persistant du plugin |
| `CLAUDE_PLUGIN_OPTION_<CLÉ>` | Hooks de plugin | Valeur d'une option configurée par l'utilisateur |
| `CLAUDE_ENV_FILE` | `SessionStart`, `Setup`, `CwdChanged`, `FileChanged` | Fichier où écrire des `export` pour les commandes `Bash` suivantes |
| `CLAUDE_EFFORT` | Hooks et outil Bash | Niveau d'effort en vigueur |
| `CLAUDE_CODE_REMOTE` | Sessions web | Vaut `"true"` dans un environnement distant |
| `CLAUDE_CODE_BRIDGE_SESSION_ID` | Remote Control actif | Identifiant de la session Remote Control |

Deux familles de variables sont retirées : les variables d'export `OTEL_*`, que Claude Code supprime de tous ses sous-processus, et celles que filtre `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` si vous l'activez. Tout le reste, secrets compris, est hérité.

Le `PATH` est celui du shell qui a lancé `claude`. Si vous utilisez `nvm`, `pyenv` ou `mise`, un `npx` qui marche dans votre terminal peut échouer dans un hook lancé depuis l'application de bureau ou un IDE. Donnez des chemins absolus en cas de doute.

## `CLAUDE_PROJECT_DIR` contre `cwd`

- `${CLAUDE_PROJECT_DIR}` désigne la racine où la session a démarré. Il **ne bouge pas**, même quand Claude entre dans un worktree ou fait `cd`. C'est le bon point d'ancrage pour trouver vos scripts.
- `cwd` (dans le JSON) suit Claude : il devient la racine du worktree ou le nouveau dossier après un `cd`. Lisez-le quand le hook doit agir là où Claude travaille.

```bash
#!/bin/bash
# Script trouvé via CLAUDE_PROJECT_DIR, action dans le dossier courant de Claude
CWD=$(jq -r '.cwd')
cd "$CWD" || exit 0
git status --porcelain
```

Si le dossier courant a été supprimé entre-temps (worktree effacé), Claude Code lance les hooks `command` depuis le premier dossier encore existant parmi : dossier de départ, racine du projet, dossier personnel, dossier temporaire.

## Shell, forme exec et Windows

- **Forme shell** (pas de `args`) : la chaîne `command` est passée à `sh -c` sur macOS et Linux, à Git Bash sous Windows, ou à PowerShell si Git Bash est absent. Pipes, `&&` et variables fonctionnent.
- **Forme exec** (`args` présent, même vide) : l'exécutable est lancé directement, sans shell. Les placeholders `${CLAUDE_PROJECT_DIR}`, `${CLAUDE_PLUGIN_ROOT}` et `${CLAUDE_PLUGIN_DATA}` sont substitués comme des chaînes simples, sans souci de guillemets.

```json
{
  "type": "command",
  "command": "node",
  "args": ["${CLAUDE_PROJECT_DIR}/.claude/hooks/check.js", "--strict"]
}
```

Sous Windows, `"shell": "powershell"` exécute la commande dans PowerShell (`pwsh.exe` si présent, sinon `powershell.exe`). Écrivez `${CLAUDE_PROJECT_DIR}` ou `$env:CLAUDE_PROJECT_DIR`, jamais `$CLAUDE_PROJECT_DIR` nu, que PowerShell lit comme une variable locale vide. La forme exec exige un vrai exécutable : les raccourcis `.cmd` de `node_modules/.bin` ne se lancent pas sans shell.

## Pas de terminal

Sur macOS et Linux, les hooks tournent sans terminal de contrôle : impossible d'ouvrir `/dev/tty`, d'afficher un menu interactif ou d'écrire des séquences d'échappement directement. Pour parler à l'utilisateur, renvoyez `systemMessage` ; pour une notification ou un titre de fenêtre, renvoyez `terminalSequence`.

## Les canaux de retour

| Canal | Lu par Claude Code comme |
|---|---|
| Code de sortie `0` | Succès ; stdout analysé (JSON si l'objet commence par `{` et finit par `}`) |
| Code de sortie `2` | Blocage sur les événements bloquants ; stderr sert de motif |
| Autre code | Erreur non bloquante, notice `hook error` dans le transcript |
| stdout en texte brut | Ajouté au contexte uniquement pour `SessionStart`, `UserPromptSubmit`, `UserPromptExpansion` et `PostModelSwitch` ; sinon journal de debug |
| stderr avec exit 0 | Journal de debug uniquement, jamais montré à Claude |

Pour un hook `http`, le JSON est envoyé en corps de requête POST et la réponse doit être un 2xx avec un corps JSON pour transmettre une décision.

## Persister des variables : `CLAUDE_ENV_FILE`

```bash
#!/bin/bash
# SessionStart : charger la bonne version de Node pour toute la session
ENV_BEFORE=$(export -p | sort)
source "$HOME/.nvm/nvm.sh" && nvm use 20 >/dev/null
if [ -n "$CLAUDE_ENV_FILE" ]; then
  comm -13 <(echo "$ENV_BEFORE") <(export -p | sort) >> "$CLAUDE_ENV_FILE"
fi
exit 0
```

Avec direnv, un hook `CwdChanged` qui exécute `direnv export bash > "$CLAUDE_ENV_FILE"` recharge l'environnement à chaque changement de dossier. Les variables écrites par `CwdChanged` ou `FileChanged` sont effacées au `CwdChanged` suivant.

## Isoler un sous-processus

Pour appeler un outil tiers sans lui transmettre vos secrets :

```bash
env -i PATH="$PATH" HOME="$HOME" /usr/local/bin/outil-tiers --input "$FILE"
```

## Cartographier votre environnement

```bash
# Hook temporaire : capturer une fois l'environnement et le JSON reçus
{ env | sort; echo '---'; cat; } > /tmp/hook-env.txt
```

Supprimez-le ensuite : le fichier contient vos variables, secrets compris.
