Un hook qui ne fait rien est frustrant : quand il réussit, Claude Code n'affiche rien dans la conversation. La chaîne reste pourtant déterministe. En vérifiant dans l'ordre la configuration, le déclenchement, le code de sortie puis la sortie JSON, on trouve presque toujours la cause en quelques minutes.

## Étape 1 : le hook est-il chargé ?

Tapez `/hooks`. Ce menu en lecture seule liste les hooks configurés avec leur origine (settings utilisateur, projet, local, plugin, session). Sélectionnez-en un pour voir la commande exacte et le fichier qui la définit. `All events`, en bas de liste, affiche aussi les événements sans hook.

Si votre hook n'apparaît pas :

- **JSON invalide** : virgule finale ou commentaire dans `settings.json`. Vérifiez avec `jq . .claude/settings.json`.
- **Mauvais fichier** : `.claude/settings.json` pour le projet, `~/.claude/settings.json` pour tous vos projets, `.claude/settings.local.json` pour vos réglages locaux.
- **Modification non prise en compte** : les éditions sont normalement détectées automatiquement ; sinon, redémarrez la session.
- **Message `Only hooks from managed settings run here`** : votre organisation a activé `allowManagedHooksOnly`. Vos hooks ne tournent pas.
- **Dossier non approuvé** : en session interactive, aucun hook de settings ne tourne avant l'acceptation de la boîte de dialogue de confiance.
- **`disableAllHooks: true`** quelque part dans vos settings.

## Étape 2 : le hook se déclenche-t-il ?

Les causes les plus fréquentes d'un hook présent mais muet :

- **Matcher** : sensible à la casse. `bash` ne correspond pas à `Bash`. `mcp__memory` (sans `.*`) est comparé comme une chaîne exacte et ne correspond à aucun outil : écrivez `mcp__memory__.*`.
- **Mauvais événement** : `PreToolUse` avant l'outil, `PostToolUse` après un succès seulement (un échec déclenche `PostToolUseFailure`), `PermissionRequest` uniquement quand une permission va vous être demandée.
- **`if` sur un événement non-outil** : un hook avec `if` sur `Stop` ou `SessionStart` ne tourne jamais.
- **Matcher sur un événement qui n'en a pas** (`UserPromptSubmit`, `Stop`, `PostToolBatch`…) : il est ignoré silencieusement, le hook tourne à chaque fois.
- **Windows** : un hook qui ne cible que `Bash` ne voit rien quand Claude passe par l'outil `PowerShell`. Utilisez `Bash|PowerShell`.
- **Fichier mentionné avec `@`** : inséré sans appel à `Read`, donc sans `PreToolUse`.
- **Outil d'un MCP de plugin** : son nom réel est `mcp__plugin_<plugin>_<serveur>__<outil>`.

Pour isoler le problème, remplacez temporairement le matcher par `"*"` : si le hook se déclenche, c'est le motif qui est en cause.

## Étape 3 : lire le journal de debug

```bash
claude --debug-file /tmp/claude.log
# dans un autre terminal
tail -f /tmp/claude.log
```

`claude --debug` écrit aussi un journal, dans `~/.claude/debug/<session-id>.txt`, mais **n'affiche rien dans le terminal**. En cours de session, `/debug` active la journalisation et indique le chemin du fichier. Pour voir le détail du matching (nombre de hooks retenus par matcher), ajoutez `CLAUDE_CODE_DEBUG_LOG_LEVEL=verbose`.

Un hook `PostToolUse` sur `Write` qui affiche `hook-ran` produit par exemple :

```text
[DEBUG] Hook output does not start with {, treating as plain text
[DEBUG] "Hook PostToolUse:Write (PostToolUse) success:\nhook-ran"
```

La vue transcript (`Ctrl+O`) complète ce journal :

- **succès** : rien n'apparaît, sauf un `systemMessage` ou un retour de hook `Stop` ;
- **blocage** : le motif (champ `reason` ou stderr) ;
- **erreur non bloquante** : une notice `<événement> hook error` suivie de la première ligne du stderr, préfixée par `Failed with non-blocking status code:`.

## Étape 4 : vérifier le code de sortie

| Code | Effet |
|---|---|
| `0` | Succès. stdout est analysé comme JSON s'il commence par `{` et finit par `}` |
| `2` | Blocage sur les événements qui le permettent ; stderr devient le motif |
| Autre (1, 127…) | Erreur non bloquante : l'action continue |

`exit 1` ne bloque pas, même si c'est le code d'échec habituel sous Unix. Un script introuvable ou non exécutable produit un code 127 et une notice du type `/bin/sh: /chemin/hook.sh: No such file or directory`, mais l'action continue : un hook de sécurité mal configuré est **désactivé sans bruit**. Surveillez cette notice au premier lancement.

Le stderr d'un hook qui sort en `0` va uniquement dans le journal de debug : ni vous ni Claude ne le voyez.

## Étape 5 : tester hors session

Le moyen le plus rapide : envoyer un JSON factice au script.

```bash
echo '{"hook_event_name":"PreToolUse","tool_name":"Bash","tool_input":{"command":"rm -rf /tmp/build"}}' \
  | .claude/hooks/block-rm.sh
echo "code: $?"
```

Pour connaître la structure exacte des données réelles, capturez-les une fois :

```bash
#!/bin/bash
# Hook temporaire : enregistre le JSON reçu
cat >> /tmp/hook-payloads.jsonl
exit 0
```

Transformez ces captures en tests automatisés qui vérifient le code de sortie attendu : un hook devient alors un composant testable comme un autre.

## Quand le JSON n'a aucun effet

Le hook affiche un JSON valide mais la décision est ignorée, sans erreur visible. Deux causes :

1. **Texte parasite avant le JSON.** Un `echo` inconditionnel dans `~/.bashrc` ou `~/.zshrc`, chargé par certains shells non interactifs (Git Bash, `BASH_ENV`), s'imprime avant votre objet. La sortie ne commence plus par `{` et part comme texte brut. Correctif :

```bash
# Dans ~/.zshrc ou ~/.bashrc
if [[ $- == *i* ]]; then
  echo "Shell prêt"
fi
```

2. **Champ au mauvais niveau.** `permissionDecision` et `additionalContext` vont dans `hookSpecificOutput`, avec `hookEventName`. Placés au premier niveau, ils sont ignorés sans erreur. Cherchez `Hook JSON output had unrecognized keys` dans le journal.

Si le transcript affiche un message de validation ou d'analyse JSON, construisez la sortie avec `jq -n --arg` plutôt que par concaténation de chaînes : les guillemets et antislashs seront échappés correctement.

## Autres pièges

- **Commande introuvable** : utilisez des chemins absolus ou `${CLAUDE_PROJECT_DIR}`, et passez en forme exec (`"args": []`) pour éviter les problèmes de guillemets.
- **`jq: command not found`** : installez `jq` ou parsez en Python ou Node.
- **Timeout** : 600 s par défaut pour un hook `command`, mais 30 s sur `UserPromptSubmit` et 1,5 s de budget partagé pour `SessionEnd`. Un hook annulé ne rend aucune décision.
- **Hook `Stop` qui boucle** : testez `stop_hook_active` et sortez en `exit 0` s'il vaut `true`. Après huit relances consécutives, Claude Code force la fin du tour.
- **Deux hooks qui réécrivent la même entrée** : ils tournent en parallèle, le dernier à finir gagne.

## Couper les hooks pour isoler un problème

`"disableAllHooks": true` dans vos settings, ou pour une seule exécution :

```bash
claude --settings '{"disableAllHooks": true}'
```

Cela ne désactive pas les hooks imposés par les settings gérés de votre organisation.
