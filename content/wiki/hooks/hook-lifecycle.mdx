Chaque événement de hook correspond à un moment précis d'une session Claude Code. Connaître l'ordre évite des bugs subtils (un hook qui lit un fichier qu'un autre n'a pas encore écrit) et aide à choisir le bon événement. Cet article donne la carte complète, avec ce qui bloque et ce qui ne bloque pas.

## Trois cadences

La documentation officielle range les événements principaux en trois rythmes :

- **par session** : `SessionStart` et `SessionEnd` ;
- **par tour** : `UserPromptSubmit`, puis `Stop` ou `StopFailure` ;
- **par appel d'outil** dans la boucle agentique : `PreToolUse` et `PostToolUse`.

Autour d'eux gravitent des événements ponctuels (compaction, notifications, fichiers modifiés, changement de modèle…).

## La séquence d'une session

```
Setup                         (uniquement --init-only, ou -p avec --init / --maintenance)
SessionStart                  (startup | resume | clear | compact | fork)
│
├─ Tour 1
│  ├─ UserPromptSubmit
│  ├─ UserPromptExpansion     (si le prompt est une commande /skill)
│  ├─ Boucle agentique
│  │  ├─ PreToolUse           (Read)
│  │  ├─ PostToolUse          (Read)
│  │  ├─ PreToolUse           (Bash)
│  │  ├─ PermissionRequest    (si une permission est nécessaire)
│  │  ├─ PostToolUse ou PostToolUseFailure (Bash)
│  │  └─ PostToolBatch        (une fois par lot d'appels parallèles)
│  └─ Stop                    (ou StopFailure si erreur d'API)
│
├─ Tour 2 …
│
├─ PreCompact → compaction → PostCompact → SessionStart (compact)
│
SessionEnd                    (clear | resume | logout | prompt_input_exit | other)
```

Points à retenir :

- `PermissionRequest` ne se déclenche que si Claude Code s'apprête à vous demander une permission. `PreToolUse`, lui, tourne avant **chaque** appel, avant même le contrôle du mode de permission.
- En mode `auto`, si le classifieur refuse un appel, `PermissionDenied` se déclenche.
- `PostToolBatch` arrive une seule fois, après que tous les appels parallèles d'un lot sont résolus et avant la requête suivante au modèle.
- `Stop` ne se déclenche pas si vous interrompez Claude.

## Les sous-agents

Quand Claude lance un sous-agent avec l'outil `Agent` (anciennement `Task`) :

```
PreToolUse (Agent)
SubagentStart                 (matcher : type d'agent, ex. Explore)
  PreToolUse / PostToolUse    (outils du sous-agent, avec agent_id et agent_type)
SubagentStop
PostToolUse (Agent)
```

Cet ordre vaut pour un sous-agent au premier plan. Or les sous-agents tournent désormais **en arrière-plan par défaut** : l'appel `Agent` rend la main immédiatement (`status: "async_launched"`), donc `PostToolUse (Agent)` peut précéder `SubagentStop`. Ne supposez pas d'ordre strict entre les deux.

Les hooks de vos settings s'appliquent aussi aux outils des sous-agents. Le JSON contient alors `agent_id` et `agent_type`, ce qui permet de distinguer le fil principal.

## Les événements hors de la boucle

| Événement | Moment |
|---|---|
| `Notification` | Permission en attente, inactivité, dialogue MCP, fin de session de fond |
| `InstructionsLoaded` | Chargement d'un `CLAUDE.md` ou d'un fichier `.claude/rules/*.md` |
| `ConfigChange` | Modification d'un fichier de settings ou de skill pendant la session |
| `CwdChanged` | Changement de répertoire (par exemple un `cd` de Claude) |
| `FileChanged` | Modification d'un fichier surveillé sur disque |
| `DirectoryAdded` | Ajout d'un répertoire via `/add-dir` |
| `WorktreeCreate` / `WorktreeRemove` | Création ou suppression d'un worktree isolé |
| `PreModelSwitch` / `PostModelSwitch` | Avant et après un changement de modèle |
| `TaskCreated` / `TaskCompleted` / `TeammateIdle` | Tâches et équipes d'agents |
| `Elicitation` / `ElicitationResult` | Demande de saisie d'un serveur MCP |
| `MessageDisplay` | Pendant l'affichage d'une réponse, pour modifier le rendu |

La documentation décrit `Notification`, `InstructionsLoaded`, `ConfigChange`, `CwdChanged`, `FileChanged`, `DirectoryAdded` et les worktrees comme des événements autonomes, qui ne s'insèrent pas dans le fil du tour. `PreModelSwitch` est séquentiel : il s'exécute avant le changement et peut le bloquer.

## Synchrone ou pas ?

Par défaut, Claude Code attend la fin d'un hook avant de poursuivre l'action qu'il encadre. Il y a des exceptions notables :

- **`SessionStart` au lancement** tourne en arrière-plan : vous pouvez taper, mais la première réponse de Claude attend la fin du hook.
- **`DirectoryAdded`** n'est pas attendu : l'ajout se termine tout de suite.
- **Un hook `command` avec `"async": true`** tourne en arrière-plan ; sa sortie arrive au tour suivant et il ne peut plus rien bloquer. Avec `"asyncRewake": true`, un `exit 2` réveille Claude.

Et dans un même événement, **tous les hooks qui correspondent s'exécutent en parallèle**. Il n'y a pas d'ordre garanti entre eux (voir [Chaînage de hooks](/wiki/hooks/chainage-hooks)).

## Qui peut bloquer ?

| Peut bloquer (exit 2 ou JSON) | Ne peut pas bloquer |
|---|---|
| `PreToolUse`, `UserPromptSubmit`, `UserPromptExpansion` | `SessionStart`, `SessionEnd`, `Setup` |
| `Stop`, `SubagentStop`, `TeammateIdle` | `PostToolUse`, `PostToolUseFailure` (stderr montré à Claude) |
| `TaskCreated`, `TaskCompleted`, `PostToolBatch` | `Notification`, `StopFailure`, `PermissionDenied` |
| `PreCompact`, `ConfigChange`, `PreModelSwitch` | `PostCompact`, `PostModelSwitch`, `InstructionsLoaded` |
| `Elicitation`, `ElicitationResult` | `CwdChanged`, `FileChanged`, `DirectoryAdded`, `MessageDisplay` |
| `WorktreeCreate`, `WorktreeRemove` (tout code non nul) | `SubagentStart` |

`PermissionRequest` est un cas à part : l'exit 2 n'y est pas pris en compte, il faut renvoyer un objet `decision` en JSON.

## Délais par défaut

Le `timeout` s'exprime **en secondes**.

| Cas | Délai par défaut |
|---|---|
| Hooks `command`, `http`, `mcp_tool` | 600 s |
| Les mêmes sur `UserPromptSubmit`, `PreModelSwitch`, `PostModelSwitch` | 30 s |
| Les mêmes sur `MessageDisplay` | 10 s |
| Hooks `prompt` | 30 s |
| Hooks `agent` | 60 s |
| `SessionEnd` | budget partagé de 1,5 s (extensible jusqu'à 60 s) |

## Observer l'ordre réel

Le plus fiable est le journal de debug : lancez `claude --debug-file /tmp/claude.log` puis `tail -f /tmp/claude.log` dans un autre terminal. Chaque exécution y apparaît avec l'événement, le matcher et le résultat. Pour plus de détails sur le matching, ajoutez `CLAUDE_CODE_DEBUG_LOG_LEVEL=verbose`. Côté télémétrie, les événements `claude_code.hook_execution_start` et `claude_code.hook_execution_complete` donnent l'horodatage et la durée de chaque passage.
