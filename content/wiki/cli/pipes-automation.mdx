`claude -p` lit l'entrée standard, écrit sur la sortie standard et renvoie un code de retour. Il se combine donc avec `git`, `jq`, `xargs` ou `gh` comme n'importe quel outil Unix. Cet article rassemble des recettes prêtes à l'emploi et les précautions à prendre. Les bases du mode non interactif sont dans [Mode headless](/wiki/cli/headless-mode).

## Envoyer des données sur stdin

```bash
git log --oneline -20 | claude -p "Transforme ces commits en notes de version en Markdown, en français"

cat build-error.log | claude -p "Explique en trois phrases la cause racine de cette erreur" > diagnostic.txt
```

Envoyer les données par le pipe a un avantage : Claude n'a besoin d'aucune permission pour les lire. L'entrée standard est limitée à 10 Mo ; au-delà, écrivez dans un fichier et donnez son chemin dans le prompt.

## Un « linter » dans package.json

```json
{
  "scripts": {
    "lint:fautes": "git diff main | claude -p \"Tu relis un diff. Pour chaque faute de frappe, donne fichier:ligne puis la correction. N'écris rien d'autre.\""
  }
}
```

`npm run lint:fautes` suffit ensuite. Les guillemets doubles échappés gardent le script compatible avec Windows.

## Extraire des champs avec jq

```bash
# Texte du résultat
claude -p "Liste 5 améliorations pour src/api.ts" --output-format json | jq -r '.result'

# Résultat, coût et identifiant de session
claude -p "Écris un test unitaire pour slugify()" --output-format json \
  | jq '{result, cost: .total_cost_usd, session: .session_id}'
```

Pour des données vraiment structurées, préférez `--json-schema` au parsing de texte : le résultat validé arrive dans `.structured_output`.

```bash
claude -p "Liste les dépendances obsolètes de package.json" \
  --output-format json \
  --json-schema '{"type":"object","properties":{"outdated":{"type":"array","items":{"type":"string"}}},"required":["outdated"]}' \
  | jq -r '.structured_output.outdated[]'
```

## Suivre les outils utilisés en temps réel

Avec `stream-json`, chaque ligne est un événement. Les appels d'outils se trouvent dans le contenu des messages `assistant` :

```bash
claude -p "Refactorise src/utils/date.ts" \
  --output-format stream-json --verbose \
  --permission-mode acceptEdits \
  | jq -c 'select(.type == "assistant") | .message.content[]? | select(.type == "tool_use") | {outil: .name, entree: .input}'
```

## Enchaîner plusieurs étapes

Plutôt que de découper un plan en lignes de texte (fragile), gardez le contexte avec `--resume` :

```bash
sid=$(claude -p "Analyse src/auth et propose un plan en 3 étapes pour passer à PKCE. Ne modifie rien." \
  --permission-mode plan --output-format json | jq -r '.session_id')

claude -p "Applique l'étape 1 du plan" --resume "$sid" --permission-mode acceptEdits
claude -p "Lance les tests et corrige si besoin" --resume "$sid" \
  --permission-mode acceptEdits --allowedTools "Bash(npm test *)"
```

## Traiter des fichiers par lots

```bash
find src -name "*.ts" -not -name "*.test.ts" -print0 \
  | xargs -0 -n 1 -P 2 -I {} \
      claude --bare -p "Ajoute une JSDoc concise aux fonctions exportées de {} sans changer le code" \
        --allowedTools "Read,Edit" --max-turns 5
```

Précautions :

- **Coût et limites** : chaque fichier est une session complète. Testez sur 3 fichiers, mesurez avec `--output-format json` (`total_cost_usd`), puis augmentez le parallélisme (`-P`) progressivement.
- **Reproductibilité** : `--bare` évite que les hooks ou plugins de la machine changent le comportement (nécessite `ANTHROPIC_API_KEY`).
- **Plafonds** : `--max-turns` et `--max-budget-usd` empêchent une exécution qui s'emballe.
- **Relecture** : travaillez sur une branche dédiée et relisez le `git diff` avant de commiter.

Pour des centaines de fichiers, les [workflows dynamiques](/wiki/cli/dynamic-workflows-agents-arriere-plan) orchestrent des sous-agents en parallèle depuis une seule session.

## Un hook git pre-commit

```bash
#!/usr/bin/env bash
# .git/hooks/pre-commit
verdict=$(git diff --cached | claude --bare -p \
  "Ce diff contient-il un secret (clé d'API, mot de passe, jeton) ?" \
  --output-format json \
  --json-schema '{"type":"object","properties":{"secret":{"type":"boolean"},"detail":{"type":"string"}},"required":["secret"]}' \
  | jq -r '.structured_output.secret')

if [ "$verdict" = "true" ]; then
  echo "Commit bloqué : secret probable détecté. Vérifiez le diff."
  exit 1
fi
```

Le schéma évite de dépendre d'une réponse « OUI » ou « NON » formulée librement. Un tel contrôle complète un vrai scanner de secrets (gitleaks, trufflehog), il ne le remplace pas : un modèle peut se tromper.

## Avec la CLI GitHub

```bash
gh pr diff 123 | claude -p \
  --append-system-prompt "Tu es ingénieur sécurité. Signale uniquement les vulnérabilités réelles." \
  --output-format json | jq -r '.result' | gh pr comment 123 --body-file -
```

## Une fonction shell avec des valeurs par défaut sûres

```bash
# ~/.zshrc
cl() {
  claude -p "$*" --output-format json --permission-mode dontAsk --max-turns 10 | jq -r '.result'
}
# cl "Quels fichiers importent lib/supabase.ts ?"
```

`dontAsk` refuse tout ce qui demanderait une confirmation : la fonction peut lire et chercher, mais pas modifier sans règle `allow` explicite.
