`claude --continue` reprend votre dernière conversation, et les checkpoints vous permettent d'annuler ce que Claude a modifié. Ensemble, ils forment un filet de sécurité pour expérimenter sans crainte, à condition d'en connaître les limites.

## --continue : reprendre la dernière session

```bash
claude --continue      # ou claude -c
claude -c "Reprends là où on s'était arrêté et lance les tests"
```

Claude Code rouvre la conversation la plus récente **du dossier courant**, avec son historique complet, son modèle et (depuis le terminal) son mode de permission. Les sessions lancées en `-p` et celles qui commencent par `/loop` sont ignorées.

Points à connaître :

- Rien n'est réexécuté. Si l'environnement a changé (branche git, services arrêtés), Claude travaille sur une image périmée : commencez par lui demander un `git status`.
- Une longue session reprise après une pause d'environ une heure n'est plus en cache. Sur Pro et Max, Claude Code propose de repartir d'un résumé pour limiter le coût.
- Pour choisir une session précise : `claude --resume` (voir [Sessions et reprise](/wiki/cli/sessions-reprise)).

## Comment fonctionnent les checkpoints

Les checkpoints sont automatiques, il n'y a rien à activer :

- **chaque prompt qui démarre un tour crée un checkpoint** ;
- avant de modifier un fichier avec ses outils d'édition, Claude Code en garde une copie ;
- les instantanés des **100 derniers checkpoints** de la session sont conservés ;
- ils sont stockés avec la session (`~/.claude/file-history/`), donc `/rewind` fonctionne aussi après un `--continue` ;
- ils sont supprimés avec la transcription, après 30 jours par défaut (`cleanupPeriodDays`).

Le réglage `fileCheckpointingEnabled` permet de les désactiver.

## Le menu /rewind

Ouvrez-le avec `/rewind` (alias `/checkpoint` et `/undo`) ou en appuyant deux fois sur `Esc` quand la zone de saisie est vide. Il liste vos prompts de la session. Choisissez un point, puis une action :

| Action | Fichiers | Conversation |
|---|---|---|
| Restore code and conversation | Restaurés | Revient à ce point |
| Restore conversation | Inchangés | Revient à ce point |
| Restore code | Restaurés | Conservée |
| Summarize from here | Inchangés | Résume la suite à partir de ce point |
| Summarize up to here | Inchangés | Résume ce qui précède |
| Never mind | Annuler | Annuler |

Après une restauration de conversation, votre prompt d'origine revient dans la zone de saisie : vous pouvez le reformuler et le renvoyer.

Les deux options « Summarize » libèrent du contexte de façon ciblée, comme un `/compact` partiel. Avant de valider, vous pouvez taper une consigne dans le champ « add context (optional) » pour orienter le résumé.

Si vous avez fait `/clear` dans le même processus, le menu affiche en tête une entrée `/resume <id> (previous session)` pour revenir à la conversation précédente.

## Exemple : essayer deux approches

```text
> Refactorise src/auth.ts pour utiliser PKCE
  ... Claude modifie 4 fichiers, les tests cassent ...

/rewind
  -> choisir le prompt « Refactorise src/auth.ts... »
  -> Restore code and conversation

> Refactorise src/auth.ts pour utiliser PKCE, sans changer la signature publique de login()
```

Pour garder les deux pistes plutôt que d'écraser la première, utilisez `/branch` : il copie la conversation dans une nouvelle session et laisse l'originale intacte.

## Ce que les checkpoints ne couvrent pas

- **Les commandes Bash** : `rm`, `mv`, `npm install`, un script de build ou une migration ne sont pas annulables.
- **La plupart des sous-agents** : leurs modifications ne sont pas restaurées (sauf une skill `context: fork` exécutée au premier plan). Utilisez git.
- **Les modifications externes** : vos éditions manuelles ou celles d'une autre session.
- **Les messages envoyés en cours de tour** : un message mis en file qui rejoint le tour en cours n'a pas son propre checkpoint.
- **Les liens symboliques et physiques** : ils sont ignorés à la restauration (fichiers liés par un gestionnaire de dotfiles, `node_modules` de pnpm).
- **Les effets distants** : base de données, API, déploiement.

## Checkpoints et git

Les checkpoints servent à la récupération rapide au sein d'une session. Ils ne remplacent pas git :

- commitez avant chaque étape importante (migration, gros refactoring) ;
- utilisez `/rewind` pour les itérations rapides entre deux commits ;
- pour une opération risquée en Bash, demandez à Claude de travailler dans un worktree (`claude -w`) ou une branche dédiée.
