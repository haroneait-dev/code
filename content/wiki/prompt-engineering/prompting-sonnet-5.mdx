Les modèles Claude actuels (Opus 5.5, Sonnet 5.5, Fable 5.1) comprennent bien des consignes simples et directes. Les prompts écrits pour Sonnet 5 ou Opus 5 fonctionnent en général sans changement, mais plusieurs habitudes héritées des anciens modèles deviennent inutiles ou provoquent des erreurs. Cet article rassemble ce qui change, avec des consignes officielles prêtes à copier.

## Les modèles concernés

| Modèle | Identifiant API | Effort par défaut (API) | Points de prompt propres |
|---|---|---|---|
| Opus 5.5 (22 sept. 2026) | `claude-opus-5-5` | `medium` | Réflexion toujours active, arrêts anticipés en agent autonome |
| Sonnet 5.5 (28 sept. 2026) | `claude-sonnet-5-5` | `high` | Réflexion désactivable avec `between_tools`, ajouts non demandés en code |
| Fable 5.1 et Mythos 5.1 (1er sept. 2026) | `claude-fable-5-1`, `claude-mythos-5-1` | `high` | Peu de messages de progression, prose parfois dense |
| Sonnet 5 et Opus 5 | `claude-sonnet-5`, `claude-opus-5` | `high` | Génération précédente, toujours disponible |

Les modèles 4.x (Opus 4.6 à 4.8, Sonnet 4.6) sont des modèles historiques : si vos prompts ont été écrits pour eux, lisez la section « Nettoyer un ancien prompt » ci-dessous. Pour les caractéristiques et les prix, voir [Opus 5.5 et Sonnet 5.5](/wiki/modeles/opus-sonnet-5-5).

## Les principes qui ne changent pas

La documentation d'Anthropic les applique à tous les modèles actuels :

- **Soyez clair et direct.** Imaginez un collègue brillant mais nouveau, sans contexte : s'il serait perdu avec votre consigne, Claude le sera aussi.
- **Expliquez pourquoi.** Le but et le public de la tâche permettent au modèle de deviner les paramètres que vous n'avez pas précisés.
- **Dites quoi faire, pas quoi éviter.** Plutôt que « N'utilisez pas de Markdown », écrivez « Répondez en paragraphes de prose continue ».
- **Écrivez votre prompt dans le style voulu.** Un prompt sans Markdown réduit le Markdown dans la réponse.
- **Séparez consignes et données** avec des [balises XML](/wiki/prompt-engineering/balises-xml), et donnez des [exemples variés](/wiki/prompt-engineering/few-shot) qui couvrent les cas limites.

## Règle 1 : l'effort est le premier réglage

Le paramètre `effort` (`low`, `medium`, `high`, `xhigh`, `max`) est le levier principal sur la quantité de réflexion, donc sur la qualité, la latence et le coût. Deux points à retenir :

- **Les niveaux ne se transposent pas d'un modèle à l'autre.** Selon Anthropic, Opus 5.5 en `medium` égale ou dépasse Opus 5 en `high` sur le code et le travail documentaire. Refaites un balayage des niveaux sur vos propres tests au lieu de reprendre l'ancien réglage.
- **Baisser l'effort marche mieux que de demander « réfléchissez moins ».** Sur Sonnet 5.5, une consigne de ce type dans le prompt système ne réduit pas la réflexion de façon fiable.

Points de départ recommandés pour Sonnet 5.5 :

| Usage | Effort de départ |
|---|---|
| Code agentique bien spécifié, outils en plusieurs étapes | `medium`, puis `high` pour les tâches longues ou difficiles |
| Chat et usages sensibles à la latence | `medium` ou `low` |
| Le reste | `high` |
| `xhigh` et `max` | Seulement si vos tests montrent un gain |

Prévoyez un `max_tokens` assez large : la réflexion compte dans cette limite, même quand elle n'est pas renvoyée. Pour du code agentique, Anthropic indique 128 000 tokens (le maximum) avec streaming. Enfin, changer l'`effort` de premier niveau entre deux requêtes invalide le cache de prompt ; pour changer un seul tour, utilisez le changement d'effort par message (bêta). Détails dans [Raisonnement adaptatif et paramètre effort](/wiki/modeles/adaptive-thinking-effort).

## Règle 2 : la réflexion n'est plus un interrupteur

- **Opus 5.5** : la réflexion adaptative est toujours active. `thinking: {"type": "disabled"}` et `budget_tokens` renvoient une erreur 400. Pour réduire la latence, commencez en `low`.
- **Sonnet 5.5** : le réglage le plus bas est `thinking: {"type": "between_tools"}` (pas de réflexion initiale, uniquement des notes entre les appels d'outils). Il n'est accepté qu'en effort `high` ou inférieur.
- **Toutes les générations depuis 4.7** : `budget_tokens` renvoie une erreur 400.

Conséquence sur vos prompts : **supprimez les consignes « ne réfléchissez pas »**. Avec `between_tools`, elles rendent plus probable l'apparition de balises XML internes dans la réponse visible.

Et côté code : lisez la réponse **par type de bloc**. Elle peut commencer par un bloc `thinking` vide (affichage `omitted` par défaut). Renvoyez ces blocs inchangés au tour suivant et gardez l'historique en ajout seul : modifier un message antérieur, le prompt système ou la liste d'outils invalide les blocs de réflexion suivants.

## Règle 3 : ne demandez plus le raisonnement dans la réponse

Opus 5.5 et Sonnet 5.5 peuvent refuser une requête qui leur demande de **reproduire leur raisonnement interne** dans le texte de la réponse. Le refus arrive avec `stop_reason: "refusal"` et la catégorie `reasoning_extraction`.

| Avant | Maintenant |
|---|---|
| « Réfléchissez étape par étape dans `<thinking>`, puis répondez dans `<answer>` » | Laissez la réflexion adaptative travailler, et lisez son résumé avec `display: "summarized"` |
| « Écrivez tout votre raisonnement avant la conclusion » | « Expliquez brièvement votre réponse » ou « Résumez les actions effectuées » (autorisé) |

Voir [Faire réfléchir Claude](/wiki/prompt-engineering/chain-of-thought).

## Règle 4 : remplacez prefill et tool_choice forcé

- **Prefill** : terminer `messages` par un début de réponse de l'assistant renvoie une erreur 400 depuis la génération 4.6. Utilisez les sorties structurées (`output_config.format`) ou une consigne de format (voir [Prefilling](/wiki/prompt-engineering/prefilling)).
- **`tool_choice` forcé** : sur Opus 5.5 et Sonnet 5.5, `{"type": "any"}` et `{"type": "tool"}` renvoient une erreur 400. Passez en `auto`, marquez l'outil `strict: true` et dites dans le prompt quand l'utiliser.
- **`temperature`, `top_p`, `top_k`** : une valeur non par défaut est refusée. Guidez le ton et la variété par des consignes.

## Règle 5 : du JSON sur une tâche de raisonnement

Quand vous demandez un JSON pour une tâche qui exige quelques étapes de calcul (additionner des montants, appliquer une règle, classer), Sonnet 5.5 répond souvent sans réfléchir, surtout en `low` et `medium`. Avec les sorties structurées, ajoutez à la fin du prompt système :

```text
Think the problem through before you answer.
```

En `high`, cette ligne rapproche la précision de celle obtenue en `xhigh`. Traitez toute réponse arrêtée sur `stop_reason: "max_tokens"` comme un échec, même si le JSON semble valide. Sans sorties structurées, analysez la **dernière** valeur JSON de la réponse, pas tout ce qui va du premier `{` au dernier `}` : le modèle écrit parfois un brouillon avant le JSON final. Voir [Formater la sortie](/wiki/prompt-engineering/output-format).

## Règle 6 : réglez l'initiative avec des consignes précises

Les modèles 5.5 répondent bien aux consignes qui **nomment le comportement** à obtenir ou à éviter. Les formules alarmistes (« CRITIQUE : vous DEVEZ… ») et « en cas de doute, utilisez l'outil » provoquent au contraire un sur-déclenchement. Les consignes ci-dessous viennent de la documentation officielle, en anglais : vous pouvez les traduire, puis vérifiez l'effet sur vos tests.

**Sonnet 5.5 s'arrête pour demander avant d'avoir fini (en `low` et `medium`)** :

```text
Keep working until everything the user asked for is done, and only stop to ask when you can't go on without the user or before a risky step.
```

**Sonnet 5.5 ajoute tests, docs ou fichiers non demandés** :

```text
When the work the user asked for is done and checked, stop and report. Don't add features, tests, files, docs or refactors that weren't asked for. If you think one would help, mention it at the end instead of doing it.
```

**En `xhigh` ou `max`, le modèle lance ses propres tours de relecture** (dans les tests d'Anthropic, cette consigne a réduit le coût d'environ un tiers sans perte de qualité) :

```text
When the work the user asked for is done and its checks pass, stop and report. Don't start extra rounds of review or hardening on your own, and don't launch reviewer sub-agents unless the user asked for a review. If you think a deeper review is worth doing, say so at the end.
```

**Une demande ouverte part en production alors que vous vouliez des idées** :

```text
When the user asks for ideas, options or a plan, give them that and stop. Don't start building or changing anything until they say to go ahead.
```

**Le code est déclaré terminé sans test** : demandez de lancer une vraie vérification (tests, vérificateur de types, build) avant de conclure, et de dire laquelle n'a pas pu tourner et pourquoi. La documentation de Sonnet 5.5 fournit un paragraphe complet pour cela.

**Opus 5.5 en agent sans surveillance s'arrête après un rapport d'étape** : côté harnais, traitez une fin de tour sans appel d'outil comme un rapport, pas comme la fin de la tâche. Gardez une liste de tâches, relancez avec les points encore ouverts, et arrêtez-vous après deux ou trois relances automatiques. La documentation d'Opus 5.5 propose aussi un paragraphe de prompt système dédié, à réserver aux agents vraiment autonomes.

## Règle 7 : recherche et outils dans le chat

Sonnet 5.5 répond parfois de mémoire alors qu'une recherche trouverait une information plus récente (tarifs, règles, obligations). Retirez d'abord les consignes du type « n'utilisez les outils qu'en cas de stricte nécessité ». Puis, si votre produit fournit un outil de recherche :

```text
Use the search tool to check specifics that may have changed since your training, such as what is allowed, required or charged, even when you feel confident. For researched work such as a report or a comparison, gather current sources rather than writing from your training knowledge.
```

Fable 5.1 cherche moins souvent en effort `low` : testez ce niveau si votre usage dépend de la recherche.

## Règle 8 : messages de progression et texte collé

**Progression.** Entre deux appels d'outils, Opus 5.5 et Sonnet 5.5 écrivent des notes pour l'utilisateur. Les notes de plus d'une ou deux phrases arrivent dans des blocs `thinking` de progression, **vides** avec l'affichage par défaut. Une interface qui n'affiche que les blocs `text` paraît donc muette. Activez `display: "updates"` (bêta). Si vous voulez des points d'étape réguliers (une ligne avant le premier outil, un récapitulatif à la fin), demandez-le dans le prompt système. À l'inverse, Fable 5.1 écrit peu pendant les longues tâches : demandez-lui explicitement ces messages.

**Texte collé.** Opus 5.5 résiste mieux à l'injection de prompt quand il sait quel texte vient de l'utilisateur et quel texte a été collé (un e-mail, une page web). Entourez chaque bloc collé d'une balise portant un identifiant aléatoire, et expliquez la convention dans le prompt système :

```text
Résumez les réclamations principales de ce fil.

<pasted_content id="ab12">
...texte collé par l'utilisateur...
</pasted_content id="ab12">
```

Cette balise n'est qu'un garde-fou parmi d'autres : elle peut être imitée. Voir [Prompt injection](/wiki/workflows/prompt-injection).

## Nettoyer un ancien prompt : la liste de contrôle

| À retirer ou changer | Pourquoi |
|---|---|
| Prefill du message assistant | Erreur 400 |
| `budget_tokens`, `thinking: disabled` (Opus 5.5) | Erreur 400 ; utilisez `effort` |
| `tool_choice` de type `any` ou `tool` (5.5) | Erreur 400 ; `auto` + `strict: true` |
| `temperature` et consorts | Erreur 400 si valeur non par défaut |
| « Écrivez votre raisonnement dans la réponse » | Refus `reasoning_extraction` possible |
| « CRITIQUE : vous DEVEZ… », « en cas de doute, utilisez l'outil » | Sur-déclenchement des outils |
| « N'utilisez les outils qu'en cas de stricte nécessité » | Réponses de mémoire, parfois obsolètes |
| « Réfléchissez soigneusement avant de répondre » dans un chat | Sur Opus 5.5, ralentit la première réponse sans gain net |
| Règles anti-formatage héritées (Fable 5.1) | Fable 5.1 formate déjà peu ; préférez une règle qui dit quand formater |
| Niveau d'effort recopié de l'ancien modèle | Les niveaux sont recalibrés |

Dans Claude Code, la commande `/claude-api prompt-audit` fait ce tri dans votre projet et propose les corrections sous forme de diff (voir [Meta-prompting](/wiki/prompt-engineering/meta-prompting)).
