Le *prompt caching* permet à l'API de réutiliser le début d'un prompt déjà traité au lieu de le relire à chaque requête. Résultat : des requêtes plus rapides et des tokens d'entrée facturés une fraction de leur prix. Il ne marche que si le début du prompt est **strictement identique** d'une requête à l'autre : tout l'enjeu est d'organiser vos prompts pour cela.

## Le principe

Le cache fonctionne par **préfixe**. L'API vérifie si le prompt, jusqu'à un point de cache, a déjà été traité récemment :

- si oui (*cache hit*), elle relit la version en cache ;
- sinon, elle traite le prompt complet et met le préfixe en cache dès que la réponse commence.

L'ordre de lecture est toujours le même : **`tools`, puis `system`, puis `messages`**. Une modification à un niveau invalide ce niveau et tous les suivants.

## Deux façons de l'activer

| Mode | Comment | Pour quoi |
|---|---|---|
| **Automatique** | Un champ `cache_control` au niveau racine de la requête | Conversations multi-tours : le point de cache avance seul à mesure que la conversation grandit. Point de départ recommandé |
| **Points de cache explicites** | `cache_control` sur des blocs précis, **4 maximum** par requête | Contrôle fin, quand des parties changent à des rythmes différents |

Le cache automatique utilise l'un des quatre emplacements disponibles. L'implémentation détaillée est dans [Implémenter le prompt caching](/wiki/api/prompt-caching-implementation).

## Durée et tarifs

Le cache dure **5 minutes** par défaut, renouvelées à chaque lecture. Une durée d'**1 heure** est disponible avec `"ttl": "1h"`.

| Opération | Prix par rapport au tarif d'entrée normal |
|---|---|
| Écriture, cache de 5 minutes | 1,25 fois |
| Écriture, cache d'1 heure | 2 fois |
| Lecture (hit) | 0,1 fois (0,05 fois sur Opus 5.5, 0,025 fois sur Fable 5.1 et Mythos 5.1) |

Exemples par million de tokens :

| Modèle | Entrée normale | Écriture 5 min | Lecture en cache |
|---|---|---|---|
| Opus 5.5 | 4 $ | 5 $ | 0,20 $ |
| Sonnet 5.5 | 2 $ | 2,50 $ | 0,20 $ |
| Haiku 4.5 | 1 $ | 1,25 $ | 0,10 $ |

Le cache de 5 minutes est rentable dès la première relecture, celui d'1 heure dès la deuxième. Ces réductions se cumulent avec celle de l'API Batch.

## Taille minimale

En dessous d'une certaine taille, le préfixe n'est **pas** mis en cache, sans message d'erreur :

| Minimum | Modèles |
|---|---|
| 512 tokens | Fable 5.1, Mythos 5.1, Opus 5.5, Opus 5, Sonnet 5.5, Fable 5, Mythos 5 |
| 1 024 tokens | Sonnet 5, Opus 4.8, Sonnet 4.6, Sonnet 4.5 |
| 4 096 tokens | Haiku 4.5, Opus 4.6, Opus 4.5 |

Vérifiez dans la réponse : si `cache_creation_input_tokens` et `cache_read_input_tokens` valent tous deux 0, rien n'a été mis en cache.

## La règle d'or : le stable d'abord, le variable à la fin

Rangez votre requête du plus stable au plus changeant :

1. **Outils** (définitions, schémas) ;
2. **Prompt système** (rôle, règles) ;
3. **Documents de référence et exemples** ;
4. **Historique de conversation** ;
5. **Message du moment**.

Placez le point de cache **à la fin de la partie identique** d'une requête à l'autre, pas sur le bloc qui change.

## Ce qui casse le cache sans prévenir

| Changement | Effet |
|---|---|
| Définitions d'outils modifiées ou réordonnées | Tout le cache est invalidé |
| Activation ou désactivation de la recherche web ou des citations | Invalide `system` et `messages` |
| Changement de `tool_choice`, ajout ou retrait d'images | Invalide `messages` |
| Changement de l'effort ou des paramètres de réflexion | Invalide au moins `messages` |
| Blocs de réflexion retirés de l'historique (Fable 5.1, Opus 5.5, Sonnet 5.5) | Invalide `messages` |

Et les pièges classiques côté code :

- une **date ou une heure** en tête du prompt système ;
- un **identifiant** d'utilisateur ou de session dans le `system` ;
- des outils générés depuis un objet dont **l'ordre des clés** varie ;
- un historique **réécrit** entre deux requêtes (résumé en place, rappel inséré puis supprimé).

Pour changer l'effort d'un seul tour sans perdre le cache, la documentation recommande le **changement d'effort par message** (bêta) plutôt que la modification du paramètre global. Et pour les rappels ponctuels, ajoutez-les à la suite de l'historique au lieu de les insérer puis de les retirer.

## Mesurer le taux de cache

Chaque réponse détaille l'usage :

```json
"usage": {
  "cache_read_input_tokens": 100000,
  "cache_creation_input_tokens": 0,
  "input_tokens": 50,
  "output_tokens": 503
}
```

Attention : `input_tokens` ne compte que les tokens **après** le dernier point de cache. Le total d'entrée est la somme des trois premiers champs. Un indicateur simple :

```text
taux de cache = cache_read / (cache_read + cache_creation + input_tokens)
```

S'il reste bas sur des requêtes qui devraient se ressembler, cherchez un élément variable au début du prompt.

## À savoir

- Les tokens en cache **comptent toujours** dans la fenêtre de contexte : le cache change le prix, pas la place occupée.
- Les blocs de réflexion ne peuvent pas être marqués avec `cache_control`, mais ils sont mis en cache avec le reste de l'historique.
- Dans **claude.ai**, pas de réglage à faire : le contenu d'un projet est mis en cache, ce qui permet de l'interroger plusieurs fois en consommant moins de vos limites d'usage (voir [Bien nourrir un projet](/wiki/claude-ai/projects-knowledge-base)).
