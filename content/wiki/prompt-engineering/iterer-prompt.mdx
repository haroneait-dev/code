Un prompt n'est jamais fini : il évolue avec vos cas d'usage, vos utilisateurs et les modèles. Mais une formulation qui semble meilleure sur trois exemples peut dégrader cent autres cas. Cet article décrit une méthode simple pour itérer sans tourner en rond, aussi bien dans claude.ai que dans une application.

## Avant de toucher au prompt

La documentation d'Anthropic pose trois prérequis avant tout travail de prompt :

1. des **critères de réussite** clairs ;
2. un moyen de les **tester** ;
3. un **premier jet** de prompt à améliorer.

Elle rappelle aussi que tous les problèmes ne se règlent pas par le prompt. Un souci de latence ou de coût se résout souvent mieux en changeant de modèle ou de niveau d'effort.

## Définir ce qu'est une bonne réponse

Un critère utile est précis et mesurable. « Des réponses de qualité » ne l'est pas. Ceci l'est :

| Critère | Exemple mesurable |
|---|---|
| Exactitude | 95 % des tickets classés dans la bonne catégorie |
| Format | 100 % des réponses passent la validation JSON |
| Ton | Note moyenne d'au moins 4 sur 5 pour « ton professionnel », jugée par un autre modèle |
| Longueur | Moins de 150 mots dans 90 % des cas |
| Coût, latence | Moins de 3 secondes avant le premier token |

La plupart des applications ont besoin de plusieurs critères à la fois.

## Le cycle d'itération

1. **Observer** un échec : retour utilisateur, log, cas raté.
2. **L'ajouter au jeu de tests**, pour ne plus jamais le perdre de vue.
3. **Formuler une hypothèse** : « Claude invente des chiffres parce que le prompt ne l'autorise pas à dire qu'il ne sait pas. »
4. **Changer une seule chose** dans le prompt.
5. **Mesurer sur tout le jeu de tests**, pas seulement sur le cas qui a déclenché le changement.
6. **Décider** : garder, annuler ou affiner.

Le piège classique : modifier trois éléments d'un coup. Si le score bouge, vous ne savez pas lequel a compté.

## Les modifications qui paient le plus souvent

Dans l'ordre où les essayer :

- **Ajouter du contexte** : pourquoi la tâche existe, pour qui, avec quel enjeu. Claude généralise à partir de l'explication.
- **Préciser le résultat attendu** plutôt que d'ajouter des interdits.
- **Ajouter ou diversifier des exemples** (voir [Few-shot prompting](/wiki/prompt-engineering/few-shot)).
- **Séparer consignes et données** avec des [balises XML](/wiki/prompt-engineering/balises-xml).
- **Ajuster l'effort** avant d'ajouter « réfléchissez bien » : sur les modèles récents, l'effort contrôle la réflexion plus sûrement que le prompt.
- **Découper en plusieurs appels** quand vous devez inspecter une étape intermédiaire : brouillon, relecture selon des critères, version finale.

## Itérer dans claude.ai

Pas besoin d'outillage pour progresser sur un prompt personnel :

1. **Gardez un jeu de test minimal** : trois à cinq demandes types, dont une difficile, dans un document à part.
2. **Modifiez votre message** plutôt que d'empiler les corrections dans la conversation : la nouvelle version part d'un contexte propre.
3. **Demandez à Claude ce qui manquait** :

```text
Votre réponse ne correspond pas à ce que je voulais : j'attendais un
tableau comparatif court, vous avez écrit une dissertation. Quelles
informations auraient dû figurer dans ma demande pour que vous
produisiez directement le bon format ? Réécrivez ma demande initiale
en les intégrant.
```

4. **Stabilisez la bonne version** dans les instructions d'un projet (voir [Créer un projet](/wiki/claude-ai/projects-creation)), puis rejouez votre jeu de test dans une nouvelle conversation du projet.

## Itérer sur un prompt d'application

### Traiter le prompt comme du code

- Un **fichier dédié** versionné dans Git (`prompts/support-v3.md`), pas une chaîne cachée dans le code.
- Un **message de commit** qui dit ce qui a changé et l'effet mesuré.
- La **version du prompt** envoyée dans vos logs ou métadonnées, pour relier un comportement à une version.
- Le **jeu de tests à côté du prompt**, pour pouvoir tout rejouer en une commande.

### Tester en conditions réelles

Pour un changement à fort impact, complétez les tests hors ligne par un essai sur une petite part du trafic (par exemple 10 %), avec des indicateurs produit : taux de réussite de la tâche, relances, retours négatifs. Attendez un volume suffisant avant de conclure.

### Les outils

- Le **playground de la Console Claude** permet d'essayer un prompt, de changer de modèle et de paramètres, et d'exporter le code. Il a remplacé le Workbench, retiré en 2026, et ne conserve pas votre travail sur les serveurs d'Anthropic : gardez vos prompts dans votre dépôt.
- Le **notebook « metaprompt »** du Claude Cookbook génère un premier jet quand vous partez de zéro (voir [Meta-prompting](/wiki/prompt-engineering/meta-prompting)).
- Les **évaluations automatisées** notent chaque version (voir [Tester un prompt](/wiki/prompt-engineering/tester-prompt)).

## À chaque nouveau modèle, revérifiez

Un prompt réglé pour un modèle n'est pas forcément optimal pour le suivant. Points relevés par Anthropic sur les modèles récents :

- **Refaites un balayage d'effort.** Les niveaux ne correspondent pas à la même quantité de réflexion d'un modèle à l'autre : Opus 5.5 est à `medium` par défaut et égale ou dépasse Opus 5 en `high` dans les tests d'Anthropic.
- **Retirez les consignes « anti-paresse »** du type « en cas de doute, utilisez l'outil » : les modèles récents risquent de sur-réagir.
- **Retirez les demandes de raisonnement écrit dans la réponse** : elles peuvent déclencher un refus `reasoning_extraction` (voir [Faire réfléchir Claude](/wiki/prompt-engineering/chain-of-thought)).
- **Retirez le prefill** : il renvoie une erreur 400 depuis la génération 4.6 (voir [Prefilling](/wiki/prompt-engineering/prefilling)).
- **Revoyez les consignes de vérification** : Opus 5 vérifie déjà son travail, et les instructions héritées le poussent à sur-vérifier.
