Le **time-to-first-token** (TTFT) est le délai entre l'envoi d'une requête et l'arrivée du premier token de la réponse. Dans une interface conversationnelle, c'est ce que l'utilisateur perçoit comme la « vitesse » de votre assistant. Voici comment le mesurer, puis les leviers qui le réduisent vraiment.

## Ce qui compose l'attente

Avant de voir le premier mot de la réponse, trois phases s'enchaînent :

1. **Réseau et file d'attente** : aller-retour HTTP, mise en file côté API.
2. **Lecture du prompt** (prefill) : le modèle traite tout le contexte. Ce temps grandit avec la taille du prompt non caché.
3. **Réflexion** : sur Opus 5.5, la réflexion est **toujours active**. Le texte visible n'arrive qu'après elle. C'est souvent la plus grosse part de l'attente.

Distinguez donc deux mesures : le premier événement du flux (TTFT technique) et le **premier token de texte** (ce que voit l'utilisateur).

## 1. Mesurer d'abord

```ts
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

const t0 = performance.now();
let premierEvenement: number | null = null;
let premierTexte: number | null = null;

const stream = client.messages.stream({
  model: "claude-opus-5-5",
  max_tokens: 4096,
  messages: [{ role: "user", content: "Explique le pattern repository en 5 lignes." }],
});

for await (const event of stream) {
  premierEvenement ??= performance.now() - t0;
  if (event.type === "content_block_delta" && event.delta.type === "text_delta") {
    premierTexte ??= performance.now() - t0;
    process.stdout.write(event.delta.text);
  }
}

const final = await stream.finalMessage();
console.log({
  premierEvenement,
  premierTexte,
  cacheLu: final.usage.cache_read_input_tokens,
  sortie: final.usage.output_tokens,
});
```

Enregistrez ces deux durées avec le modèle, l'effort, la taille du prompt et le taux de cache. Regardez le p50 **et** le p95 : ce sont les requêtes lentes qui font fuir les utilisateurs.

## 2. Streamer systématiquement

Sans streaming, l'utilisateur attend la réponse entière. Avec le streaming, le texte s'affiche au fur et à mesure : c'est le gain perçu le plus important et le plus simple à obtenir. Côté Next.js ou tout autre front, relayez le flux SSE jusqu'au navigateur (voir [Streaming](/wiki/api/streaming)).

## 3. Régler l'effort selon la route

La réflexion se pilote avec `output_config.effort` (`low`, `medium`, `high`, `xhigh`, `max`). Sur Opus 5.5, la valeur par défaut est `medium` et la réflexion ne peut pas être désactivée : l'effort est **le** réglage de latence.

```python
response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=2048,
    output_config={"effort": "low"},  # chat, reformulation, classification
    messages=[{"role": "user", "content": question}],
)
```

Règle pratique : `low` pour le chat simple, la classification, les réponses courtes ; `medium` ou `high` pour le code et les tâches à plusieurs étapes. Mesurez la qualité sur un échantillon avant de baisser l'effort d'une route (voir [Évals automatisées](/wiki/api/evals-automatisees)).

### Montrer que le modèle réfléchit

Par défaut, les blocs de réflexion arrivent **vides** (`display: "omitted"`). Le flux démarre, mais rien ne s'affiche pendant la réflexion. Pour montrer un résumé de la réflexion pendant l'attente :

```python
thinking={"type": "adaptive", "display": "summarized"}
```

Cela ne réduit pas la latence, mais l'attente est mieux perçue. Un simple indicateur « Claude réfléchit… » affiché dès le premier événement fonctionne aussi.

## 4. Mettre en cache le début du prompt

Le prompt caching évite de retraiter un long préfixe stable (prompt système, documents, outils). Sur un hit, la lecture du prompt est bien plus rapide, et moins chère.

```ts
await client.messages.create({
  model: "claude-opus-5-5",
  max_tokens: 2048,
  cache_control: { type: "ephemeral" }, // cache automatique
  system: PROMPT_SYSTEME_LONG,
  messages,
});
```

Deux compléments utiles :

- **Préchauffage** : au démarrage de votre service, envoyez une requête avec `max_tokens: 0` pour écrire le cache. Le premier vrai utilisateur ne paie pas la latence d'écriture.
- **Durée 1 heure** (`"ttl": "1h"`) si votre trafic a des creux de plus de 5 minutes.

Détails et pièges dans [Implémenter le prompt caching](/wiki/api/prompt-caching-implementation).

## 5. Alléger le prompt non caché

Tout ce qui n'est pas en cache est relu à chaque requête. Supprimez les exemples redondants, les consignes répétées et les documents inutiles pour la question posée. En RAG, envoyez les passages pertinents plutôt que des documents entiers. Un prompt plus court est aussi plus rapide à traiter et moins cher.

## 6. Choisir le bon modèle

| Modèle | Quand le préférer pour la latence |
|---|---|
| Haiku 4.5 (`claude-haiku-4-5-20251001`) | Le plus rapide : classification, extraction, autocomplétion, réponses courtes |
| Sonnet 5.5 (`claude-sonnet-5-5`) | Bon compromis vitesse / qualité pour le chat et les agents du quotidien |
| Opus 5.5 (`claude-opus-5-5`) | Qualité maximale ; latence maîtrisée avec un effort `low` ou `medium` |

Avant de router vers un modèle plus petit, testez d'abord le modèle principal avec un effort plus bas : la qualité tient souvent mieux, et vous gardez un seul cache.

Sur Sonnet 5.5, `thinking: {"type": "between_tools"}` supprime la réflexion initiale (accepté uniquement jusqu'à l'effort `high`) : utile pour une route de chat où chaque milliseconde compte.

## 7. Fast mode : un gain sur le débit, pas sur le TTFT

Le **fast mode** (aperçu de recherche, sur demande d'accès) augmente jusqu'à 2,5 fois le nombre de tokens de sortie par seconde d'Opus 5.5, pour 8 $ / 40 $ par million de tokens. La documentation précise que le gain porte sur le **débit de sortie**, pas sur le TTFT. Il raccourcit donc le temps total des longues réponses, pas l'attente du premier mot. Il n'est disponible que sur l'API Claude, et changer de vitesse invalide le cache.

## 8. Côté infrastructure

- Réutilisez le même client SDK (connexions HTTP gardées ouvertes) au lieu d'en créer un par requête.
- Évitez les proxys qui mettent les réponses en tampon : ils annulent le streaming (désactivez le buffering sur nginx, utilisez une route en streaming sur votre plateforme).
- Pour les agents qui appellent des outils, chaque aller-retour d'outil s'ajoute à l'attente : parallélisez les appels d'outils indépendants.
