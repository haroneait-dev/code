Le **prompt caching** permet à l'API de réutiliser le début d'un prompt déjà traité (long prompt système, documents, définitions d'outils). Les requêtes suivantes qui partagent ce début sont plus rapides et beaucoup moins chères. C'est en général la première optimisation de coût à mettre en place.

## Le principe : un préfixe identique à l'octet près

Le cache fonctionne par **correspondance de préfixe**. L'API rend la requête dans l'ordre **`tools` → `system` → `messages`**, puis cherche une entrée de cache identique jusqu'au bloc marqué `cache_control` (le « breakpoint »). Un seul octet différent dans ce préfixe, et tout ce qui suit est recalculé.

Conséquence pratique :

- placez le **contenu stable en premier** (prompt système figé, liste d'outils fixe, documents de référence) ;
- placez le **contenu variable après** le dernier breakpoint (question de l'utilisateur, date, identifiants de requête).

## Cache automatique ou explicite

**Automatique (le plus simple).** Ajoutez `cache_control` au niveau de la requête. L'API pose le breakpoint sur le dernier bloc cacheable et le fait avancer à mesure que la conversation grandit. C'est le bon choix pour un chat multi-tours.

```python
import anthropic

client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=2048,
    cache_control={"type": "ephemeral"},
    system="Vous êtes l'assistant support de la société X. " + GUIDE_INTERNE,
    messages=[{"role": "user", "content": "Comment réinitialiser mon mot de passe ?"}],
)
```

**Explicite.** Vous posez `cache_control` sur des blocs précis, jusqu'à **4 breakpoints** par requête. Utile quand plusieurs parties changent à des rythmes différents (outils rarement, documents chaque jour, conversation à chaque tour).

```ts
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

const response = await client.messages.create({
  model: "claude-opus-5-5",
  max_tokens: 2048,
  system: [
    { type: "text", text: "Vous analysez des contrats pour un cabinet d'avocats." },
    {
      type: "text",
      text: contratComplet, // gros document stable
      cache_control: { type: "ephemeral" },
    },
  ],
  messages: [{ role: "user", content: "Liste les clauses de résiliation." }],
});
```

Chaque breakpoint regarde au plus **20 blocs** en arrière pour retrouver une entrée existante. Dans une très longue conversation, ajoutez un second breakpoint ou utilisez le mode automatique.

## Combien ça coûte

Le cache a trois tarifs, exprimés par rapport au prix d'entrée normal :

| Opération | Multiplicateur |
|---|---|
| Écriture, durée 5 minutes (par défaut) | 1,25× |
| Écriture, durée 1 heure (`"ttl": "1h"`) | 2× |
| Lecture | 0,1× sur la plupart des modèles, **0,05× sur Opus 5.5** |

Ce qui donne, par million de tokens :

| Modèle | Entrée normale | Écriture 5 min | Écriture 1 h | Lecture |
|---|---|---|---|---|
| Opus 5.5 (`claude-opus-5-5`) | 4 $ | 5 $ | 8 $ | 0,20 $ |
| Sonnet 5.5 (`claude-sonnet-5-5`) | 2 $ | 2,50 $ | 4 $ | 0,20 $ |
| Haiku 4.5 (`claude-haiku-4-5-20251001`) | 1 $ | 1,25 $ | 2 $ | 0,10 $ |

**Rentabilité.** Avec la durée de 5 minutes, le cache est rentable dès la deuxième requête (1,25 + 0,1 contre 2 fois le prix plein). Avec 1 heure, il faut environ trois requêtes. Chaque lecture remet le compteur de durée à zéro : un cache utilisé régulièrement reste chaud. Ces multiplicateurs se cumulent avec la remise de l'[API Batch](/wiki/api/batch-api).

Choisissez 1 heure quand les requêtes sont espacées de plus de 5 minutes (traitements par lots, agents qui réfléchissent longtemps, utilisateurs qui reviennent après une pause).

## La taille minimale : le piège silencieux

Sous un certain nombre de tokens, le préfixe n'est **pas mis en cache, sans aucune erreur**. Le seuil dépend du modèle :

| Modèle | Préfixe minimal |
|---|---:|
| Opus 5.5, Sonnet 5.5, Fable 5.1 | 512 tokens |
| Opus 5, Sonnet 5, Opus 4.8 | 1 024 tokens |
| Opus 4.7 | 2 048 tokens |
| Haiku 4.5, Opus 4.6 | 4 096 tokens |

Exemple : un prompt système de 2 000 tokens se cache sur Opus 5.5, mais pas sur Haiku 4.5. Si vous changez de modèle, revérifiez vos hits.

## Vérifier que le cache fonctionne

Le champ `usage` de chaque réponse détaille l'activité du cache :

| Champ | Contenu |
|---|---|
| `cache_creation_input_tokens` | Tokens écrits dans le cache à cette requête |
| `cache_read_input_tokens` | Tokens relus depuis le cache |
| `input_tokens` | Tokens **après** le dernier breakpoint, payés plein tarif |
| `cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens` | Répartition des écritures par durée |

La taille totale du prompt est la **somme** des trois premiers champs. Un `input_tokens` de 50 sur un agent qui relit 100 000 tokens est normal : le reste vient du cache.

```python
u = response.usage
total = u.input_tokens + u.cache_creation_input_tokens + u.cache_read_input_tokens
print(f"Prompt : {total} tokens, dont {u.cache_read_input_tokens} relus depuis le cache")
```

Si `cache_read_input_tokens` reste à zéro sur des requêtes répétées, cherchez un invalidateur. L'outil bêta de **cache diagnostics** compare deux requêtes successives et indique où le préfixe a divergé.

## Les invalidateurs silencieux

À traquer dans tout ce qui construit le début du prompt :

- une date ou une heure (`datetime.now()`, `Date.now()`) dans le prompt système ;
- un identifiant de requête ou de session (`uuid4()`) placé avant le breakpoint ;
- un JSON sérialisé sans ordre stable (`json.dumps` sans `sort_keys=True`, itération d'un `set`) ;
- une liste d'outils construite dans un ordre variable, ou modifiée en cours de conversation ;
- un changement de `model` : chaque modèle a son propre cache.

Certains paramètres invalident aussi une partie du cache quand ils changent :

| Changement | Effet |
|---|---|
| Définitions d'outils | Tout le cache (outils, système, messages) |
| Activation de web search ou des citations, `speed` | Système et messages |
| `tool_choice`, ajout ou retrait d'images | Messages |
| Configuration de la réflexion, niveau d'effort | Messages (selon le modèle) |

Pour ajouter une consigne en cours de conversation sans casser le cache, Opus 5.5 et Sonnet 5.5 acceptent un message `{"role": "system", ...}` **dans** `messages`, plutôt qu'une modification du champ `system` principal.

## Préchauffer le cache

Pour que le premier utilisateur ne paie pas la latence d'écriture, envoyez au démarrage une requête avec `max_tokens: 0` : l'API écrit le cache sans rien générer.

```python
SYSTEME = [{
    "type": "text",
    "text": GUIDE_INTERNE,
    "cache_control": {"type": "ephemeral", "ttl": "1h"},
}]

client.messages.create(
    model="claude-opus-5-5",
    max_tokens=0,
    system=SYSTEME,
    messages=[{"role": "user", "content": "préchauffage"}],
)
```

`max_tokens: 0` est refusé en streaming, avec les sorties structurées, avec un `tool_choice` forcé et dans l'API Batch.

## Réflexion, batch et isolation

- **Blocs de réflexion** : on ne peut pas y poser `cache_control`, mais ils sont mis en cache avec le reste quand vous les renvoyez dans l'historique. Relus depuis le cache, ils comptent comme des tokens d'entrée.
- **Batch** : les hits sont « best effort », car les requêtes tournent en parallèle. Préférez la durée 1 heure et des blocs `cache_control` identiques partout.
- **Isolation** : le cache est propre à chaque workspace sur l'API Claude (à chaque organisation sur Bedrock et Google Cloud). Deux organisations ne partagent jamais de cache.
- **Limites de débit** : les tokens relus depuis le cache ne comptent pas dans la limite de tokens d'entrée par minute sur les modèles récents, ce qui augmente votre débit utile (voir [les en-têtes de rate limit](/wiki/api/rate-limit-headers)).

## Check-list

1. Prompt système figé, sans date ni identifiant.
2. Outils triés et identiques d'une requête à l'autre.
3. Préfixe au-dessus du seuil minimal du modèle.
4. Breakpoint sur le dernier bloc **stable**, pas sur la question.
5. Suivi de `cache_read_input_tokens` dans vos logs.
