Un agent qui enchaîne les appels d'outils finit par remplir sa fenêtre de contexte, même avec 1M de tokens. Le **token budgeting** consiste à mesurer cette croissance et à la contrôler avant qu'elle ne provoque une erreur, une facture élevée ou une baisse de qualité. Cet article présente les outils officiels de l'API (comptage, compaction, context editing) et les stratégies côté client.

## D'où vient la croissance du contexte

Chaque tour d'un agent ajoute à l'historique :

- le message utilisateur ou le résultat d'outil précédent ;
- les blocs `thinking` du modèle (selon le modèle, ceux des tours précédents comptent ou sont retirés par l'API) ;
- le texte de réponse et les appels d'outils ;
- les résultats d'outils, souvent les plus lourds (fichiers, pages web, sorties de commandes).

Cinquante appels d'outils renvoyant chacun 5 000 tokens représentent déjà 250 000 tokens. Et l'historique est renvoyé à chaque requête : vous payez ces tokens en entrée à chaque tour (le prompt caching réduit fortement ce coût, voir plus bas).

Point important : depuis Claude Opus 4.7, les modèles récents (dont Fable 5.1 et Mythos 5.1) utilisent un tokenizer qui produit environ 30 % de tokens en plus pour le même texte. Ne réutilisez pas des comptes mesurés sur un ancien modèle.

## Compter avant d'envoyer

L'endpoint `POST /v1/messages/count_tokens` accepte la même structure qu'une requête Messages (system, tools, images, PDF en base64, thinking) et renvoie `input_tokens`. Il est **gratuit**, avec une limite de requêtes par minute indépendante de celle des messages.

```ts
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

const { input_tokens } = await client.messages.countTokens({
  model: "claude-sonnet-5-5",
  system: systemPrompt,
  tools,
  messages,
});

if (input_tokens > BUDGET) {
  messages = await compacter(messages);
}
```

Limites à connaître :

- le résultat est une **estimation** (un léger écart avec la facturation réelle est possible) ;
- les server tools (web search, web fetch, code execution…), le connecteur MCP et les images ou documents en source `url` ou `file` renvoient une erreur : envoyez les fichiers en base64, ou lisez simplement `usage` dans la réponse.

## Mesurer après chaque appel

Chaque réponse renvoie un objet `usage` (`input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`). Journalisez la trajectoire par tour :

```ts
const total =
  res.usage.input_tokens +
  (res.usage.cache_read_input_tokens ?? 0) +
  (res.usage.cache_creation_input_tokens ?? 0);

metrics.gauge("agent_context_tokens", total, { agentId, turn });
```

Attention : `input_tokens` seul n'inclut pas les tokens lus ou écrits en cache. Additionnez les trois champs pour connaître la taille réelle du contexte.

Une règle simple : alerte à 80 % de la fenêtre, compaction à 60-70 %. Mieux vaut compacter tôt : la qualité des réponses baisse quand le contexte s'allonge, bien avant la limite.

## Stratégie 1 : borner les résultats d'outils

C'est le levier le plus rentable. Tronquez à la source :

```ts
function borner(resultat: string, maxChars = 8_000): string {
  if (resultat.length <= maxChars) return resultat;
  const omis = resultat.length - maxChars;
  return `${resultat.slice(0, maxChars)}\n\n[tronqué : ${omis} caractères omis]`;
}
```

Le ratio caractères/tokens varie selon la langue et le contenu (le code et le français ne se comptent pas comme l'anglais) : utilisez `count_tokens` pour calibrer votre seuil plutôt qu'une règle fixe. Autres réflexes :

- pour un gros fichier, renvoyez un extrait ciblé (lignes pertinentes, `grep`) plutôt que le fichier entier ;
- pour une page web, extrayez le contenu principal plutôt que le HTML brut ;
- donnez aux outils des paramètres `limit` / `offset` pour que Claude pagine lui-même.

## Stratégie 2 : context editing

Le **context editing** de l'API efface automatiquement, selon des règles, les anciens résultats d'outils ou les anciens blocs de thinking, sans les résumer. C'est adapté aux agents dont les vieux résultats d'outils ne servent plus (lectures de fichiers déjà traitées, recherches terminées). Les paramètres exacts sont décrits dans la page « Context editing » de la documentation.

## Stratégie 3 : compaction côté serveur

La **compaction** remplace les anciens tours par un résumé écrit par Claude côté serveur. Deux modes existent, tous deux en bêta :

| Mode | Qui déclenche | Ce que vous écrivez |
|---|---|---|
| Compaction à la demande | Vous, par une requête dédiée | Une boucle qui demande le résumé et le remplace dans `messages` |
| Compaction à un seuil | L'API, quand l'entrée atteint le seuil fixé | Un paramètre sur vos requêtes habituelles |

La compaction à la demande (en-tête bêta `compact-2026-09-04`, paramètre de premier niveau `compaction`) est le choix recommandé par Anthropic : elle peut conserver les derniers tours mot pour mot et tourner en arrière-plan. Consultez la page « Compaction » pour la syntaxe exacte et la compatibilité par plateforme, car ces API bêta évoluent vite.

## Stratégie 4 : résumé côté client

Si vous ne pouvez pas utiliser les fonctions bêta, résumez vous-même. Gardez le premier message (la consigne initiale) et les derniers tours intacts, et résumez le milieu avec un petit modèle :

```ts
async function compacter(messages: Anthropic.MessageParam[], garder = 10) {
  if (messages.length <= garder + 1) return messages;

  const anciens = messages.slice(1, -garder);
  const resume = await client.messages.create({
    model: "claude-haiku-4-5-20251001",
    max_tokens: 2000,
    messages: [{
      role: "user",
      content:
        "Résume ces échanges en conservant les faits, décisions, chemins de fichiers et données chiffrées :\n\n" +
        JSON.stringify(anciens),
    }],
  });

  const texte = resume.content.find((b) => b.type === "text")?.text ?? "";

  return [
    messages[0],
    { role: "assistant", content: `[Résumé des échanges précédents]\n${texte}` },
    { role: "user", content: "Continuez à partir de ce résumé." },
    ...messages.slice(-garder),
  ] as Anthropic.MessageParam[];
}
```

Pièges fréquents :

- **ne coupez jamais entre un `tool_use` et son `tool_result`** : l'API rejette un `tool_result` dont l'appel a disparu. Choisissez le point de coupe sur un message utilisateur texte ;
- respectez l'alternance des rôles `user` / `assistant` ;
- si vous renvoyez des blocs `thinking` sur un modèle à thinking préservé, un résumé client peut invalider leur signature : retirez-les des tours conservés.

Une simple fenêtre glissante (ne garder que les N derniers tours) reste possible, mais l'agent perd alors tout ce qui précède. Préférez le résumé dès qu'une décision ancienne peut compter.

## Stratégie 5 : mémoire externe

Pour un agent qui travaille sur plusieurs jours, sortez l'état du contexte : fichier de notes, base clé-valeur ou base vectorielle. L'agent écrit ses décisions et son avancement, puis relit uniquement ce qui est utile. L'outil mémoire de l'API (memory tool) fournit ce schéma clé en main. C'est aussi le principe de `CLAUDE.md` et de la mémoire automatique dans Claude Code.

## Combiner avec le prompt caching

Le cache réduit le coût de l'historique renvoyé à chaque tour, mais il ne réduit pas sa taille. Placez les éléments stables (system prompt, définitions d'outils, résumé compacté) en tête pour qu'ils restent cachables. Sur Sonnet 5.5, une lecture en cache coûte 0,20 $ par million de tokens contre 2 $ en entrée normale.

## Récapitulatif

| Problème | Outil |
|---|---|
| Savoir si une requête tient | `count_tokens` (gratuit) |
| Suivre la croissance | `usage` dans chaque réponse |
| Résultats d'outils trop gros | Troncature à la source, pagination |
| Vieux résultats d'outils inutiles | Context editing |
| Historique trop long | Compaction serveur ou résumé client |
| Agent sur plusieurs jours | Mémoire externe, memory tool |
| Coût de l'historique | Prompt caching |
