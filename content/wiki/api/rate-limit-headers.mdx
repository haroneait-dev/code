L'API Claude limite le nombre de requêtes et de tokens que votre organisation peut consommer par minute. Plutôt que de découvrir ces limites par des erreurs 429 en production, lisez les en-têtes `anthropic-ratelimit-*` renvoyés avec chaque réponse et adaptez votre débit avant d'atteindre le plafond.

## Les trois limites par modèle

Pour l'API Messages, chaque **modèle** a trois limites, mesurées par minute au niveau de l'organisation :

- **RPM** : requêtes par minute ;
- **ITPM** : tokens d'entrée par minute ;
- **OTPM** : tokens de sortie par minute.

L'API utilise un **seau à jetons** (token bucket) : votre capacité se reconstitue en continu, elle n'est pas remise à zéro chaque minute. En contrepartie, une limite de 60 RPM peut être appliquée comme 1 requête par seconde : une rafale courte peut déclencher un 429 même si la moyenne sur la minute est correcte.

Deux bonnes nouvelles :

- **Les tokens lus depuis le cache ne comptent pas dans l'ITPM** (sur tous les modèles actuels). Seuls `input_tokens` et `cache_creation_input_tokens` comptent. Avec 80 % de hits de cache, une limite de 2 millions d'ITPM permet de traiter environ 10 millions de tokens d'entrée par minute.
- **`max_tokens` n'entre pas dans le calcul de l'OTPM** : seuls les tokens réellement générés comptent. Un `max_tokens` généreux ne vous pénalise pas.

Les limites sont **séparées par modèle** : Opus 5.5 et Sonnet 5.5 ont chacun leur propre seau.

## Les niveaux d'usage (tiers)

Votre organisation est placée automatiquement dans un niveau selon son historique. Les nouvelles organisations peuvent démarrer dans un niveau d'évaluation plus bas. Limites standard au 3 octobre 2026 :

| Niveau | Plafond de dépense mensuel | Opus 5.5 / Sonnet 5.5 / Haiku 4.5 (RPM, ITPM, OTPM) |
|---|---|---|
| Start | 500 $ | 1 000 / 2 000 000 / 400 000 |
| Build | 1 000 $ | 5 000 / 5 000 000 / 1 000 000 |
| Scale | 200 000 $ | 10 000 / 10 000 000 / 2 000 000 |
| Custom | sur contrat | sur contrat |

Vos valeurs exactes sont visibles dans la Console, page **Settings > Limits**, où vous pouvez aussi demander une augmentation. L'API Batch a ses propres limites, partagées entre modèles (par exemple 200 000 requêtes en file d'attente au niveau Start).

## Les en-têtes renvoyés

| En-tête | Contenu |
|---|---|
| `retry-after` | Secondes à attendre avant de réessayer (sur un 429) |
| `anthropic-ratelimit-requests-limit` / `-remaining` / `-reset` | Limite de requêtes, solde restant, date de recharge complète |
| `anthropic-ratelimit-tokens-limit` / `-remaining` / `-reset` | La limite de tokens **la plus contraignante** en vigueur |
| `anthropic-ratelimit-input-tokens-limit` / `-remaining` / `-reset` | Idem pour les tokens d'entrée |
| `anthropic-ratelimit-output-tokens-limit` / `-remaining` / `-reset` | Idem pour les tokens de sortie |
| `anthropic-workspace-id` | Le workspace auquel la requête a été imputée |

Les dates `-reset` sont au format **RFC 3339** et indiquent quand le seau sera **entièrement** rechargé. Les soldes de tokens sont arrondis au millier.

## Lire les en-têtes avec les SDK

En Python, `with_raw_response` donne accès aux en-têtes ; `parse()` renvoie le `Message` habituel :

```python
import anthropic

client = anthropic.Anthropic()

raw = client.messages.with_raw_response.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    messages=[{"role": "user", "content": "Bonjour"}],
)
print(raw.headers.get("anthropic-ratelimit-input-tokens-remaining"))
print(raw.headers.get("anthropic-ratelimit-output-tokens-reset"))

message = raw.parse()
```

En TypeScript, avec `.withResponse()` :

```ts
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

const { data: message, response } = await client.messages
  .create({
    model: "claude-opus-5-5",
    max_tokens: 1024,
    messages: [{ role: "user", content: "Bonjour" }],
  })
  .withResponse();

const restant = Number(response.headers.get("anthropic-ratelimit-input-tokens-remaining"));
```

## Un limiteur côté client

L'idée : garder en mémoire le dernier solde connu, estimer le coût de la prochaine requête et attendre si le solde est insuffisant. Pour estimer les tokens d'entrée, utilisez l'endpoint de comptage (voir [Budgéter ses tokens](/wiki/api/token-budgeting)) ou une estimation prudente.

```python
import time
from datetime import datetime, timezone

class LimiteurEntree:
    def __init__(self):
        self.restant = None
        self.recharge = None

    def mettre_a_jour(self, headers):
        valeur = headers.get("anthropic-ratelimit-input-tokens-remaining")
        reset = headers.get("anthropic-ratelimit-input-tokens-reset")
        if valeur is not None:
            self.restant = int(valeur)
        if reset:
            self.recharge = datetime.fromisoformat(reset.replace("Z", "+00:00"))

    def attendre_si_besoin(self, tokens_estimes):
        if self.restant is None or tokens_estimes <= self.restant:
            return
        attente = (self.recharge - datetime.now(timezone.utc)).total_seconds()
        time.sleep(max(0.5, min(attente, 60)))
```

Limites de cette approche : avec plusieurs workers, chacun ne voit que ses propres réponses. Au-delà d'un processus, centralisez le solde (Redis, par exemple) ou passez par une file d'attente unique.

## Gérer le 429 qui reste

Même avec un limiteur, des 429 arriveront (rafales, plusieurs instances). Les SDK relancent déjà automatiquement les 429 en respectant `retry-after` (2 tentatives par défaut, réglables avec `max_retries`). Si vous gérez la relance vous-même, respectez toujours `retry-after` et ajoutez un peu d'aléa :

```ts
async function appelerAvecRelance(payload: Anthropic.MessageCreateParamsNonStreaming) {
  for (let tentative = 0; tentative < 5; tentative++) {
    try {
      return await client.messages.create(payload, { maxRetries: 0 });
    } catch (e) {
      if (e instanceof Anthropic.RateLimitError) {
        const retryAfter = e.headers?.get("retry-after");
        if (!retryAfter) throw e; // plafond de dépense : inutile d'insister
        const attente = Number(retryAfter) * 1000 + Math.random() * 500;
        await new Promise((r) => setTimeout(r, attente));
        continue;
      }
      throw e;
    }
  }
  throw new Error("Limite de débit : relances épuisées");
}
```

Un 429 **sans** `retry-after` signale le plus souvent le plafond de dépense mensuel du niveau (code `enforced_spend_limit_reached` dans `error.details.error_code`). L'accès reprend le 1er du mois suivant à 00:00 UTC ou après passage à un niveau supérieur : relancer ne sert à rien.

Une montée en charge très brutale peut aussi provoquer des 429 dus aux **limites d'accélération** : augmentez le trafic progressivement.

## Organiser le trafic

- **Séparez les priorités** : une file pour les requêtes interactives, une autre pour les tâches de fond, avec un débit réservé aux premières.
- **Limitez par workspace** : dans la Console, vous pouvez fixer des limites de débit et de dépense plus basses par workspace (pas sur le workspace par défaut). Un job d'analyse ne peut alors plus épuiser le quota de votre application.
- **Passez les gros volumes en [batch](/wiki/api/batch-api)** : file et limites séparées, moitié prix.
- **Activez le [prompt caching](/wiki/api/prompt-caching-implementation)** : c'est le levier le plus efficace pour gagner du débit d'entrée.
- **Surveillez** la page Usage de la Console, qui affiche votre pic d'ITPM non caché par heure, votre limite et votre taux de cache.
