Chaque requête à l'API Messages accepte un champ `metadata` dont le seul sous-champ est `user_id` : un identifiant opaque de l'utilisateur final de votre application. Anthropic peut s'en servir pour détecter les abus. Côté application, ce même identifiant structure vos logs, vos quotas par utilisateur et vos analyses de coût.

## Ce que dit la documentation

D'après la référence de l'API, `metadata.user_id` est :

- **optionnel** (chaîne ou `null`) ;
- limité à **512 caractères** ;
- censé être « un UUID, une valeur hachée ou un autre identifiant opaque » ;
- utilisable par Anthropic « pour aider à détecter les abus ».

La documentation demande explicitement de **ne mettre aucune information identifiante** : ni nom, ni adresse e-mail, ni numéro de téléphone.

Elle ne décrit pas plus précisément comment l'identifiant est exploité. Retenez simplement qu'il permet de distinguer vos utilisateurs entre eux, au lieu que tout votre trafic apparaisse comme venant d'une seule source : votre clé API.

## Exemple

```python
import anthropic

client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=2048,
    metadata={"user_id": "usr_7f3a9c21e4b84d0f"},
    messages=[{"role": "user", "content": "Explique-moi les closures en JavaScript."}],
)
```

```ts
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

const response = await client.messages.create({
  model: "claude-opus-5-5",
  max_tokens: 2048,
  metadata: { user_id: "usr_7f3a9c21e4b84d0f" },
  messages: [{ role: "user", content: "Explique-moi les closures en JavaScript." }],
});
```

Le champ fonctionne aussi dans les requêtes d'un [batch](/wiki/api/batch-api), puisque chaque `params` reprend le corps d'une requête Messages.

## Choisir un bon identifiant

| Critère | Bon exemple | À éviter |
|---|---|---|
| Opaque | UUID interne, hash | e-mail, nom, adresse IP |
| Stable | même valeur à chaque session | identifiant de session ou de requête |
| Un par personne | un compte = un identifiant | un identifiant partagé par toute une équipe |

Si votre identifiant interne est lui-même sensible (numéro client lisible, par exemple), hachez-le avec un secret côté serveur :

```python
import hashlib
import hmac
import os

SECRET = os.environ["USER_ID_HASH_SECRET"].encode()

def user_id_opaque(id_interne: str) -> str:
    return hmac.new(SECRET, id_interne.encode(), hashlib.sha256).hexdigest()[:32]
```

Le HMAC (plutôt qu'un simple SHA-256) empêche de retrouver l'identifiant d'origine en testant toutes les valeurs possibles.

Pour une application multi-tenant, un préfixe de tenant reste opaque et facilite vos analyses : `t_8c1f_u_7f3a9c21`.

## Réutiliser l'identifiant chez vous

### Des logs exploitables

Enregistrez l'identifiant avec le `request_id` de la réponse et la consommation de tokens :

```ts
logger.info({
  user_id: userIdOpaque,
  request_id: response._request_id,
  model: response.model,
  input_tokens: response.usage.input_tokens,
  output_tokens: response.usage.output_tokens,
  stop_reason: response.stop_reason,
});
```

Vous saurez ainsi quel utilisateur consomme le plus, lequel déclenche des refus (`stop_reason: "refusal"`), et quelle requête transmettre au support Anthropic en cas de problème.

### Un quota par utilisateur

Les limites de débit de l'API s'appliquent à toute votre organisation. Un seul utilisateur trop actif peut donc consommer la capacité de tous les autres. Limitez-le avant l'appel :

```ts
const cle = `quota:claude:${userIdOpaque}`;
const appels = await redis.incr(cle);
if (appels === 1) await redis.expire(cle, 60);
if (appels > 20) {
  throw new Error("Trop de requêtes, réessayez dans une minute.");
}
```

Un quota en tokens par jour (en additionnant `usage.input_tokens` et `usage.output_tokens`) est encore plus juste qu'un quota en nombre de requêtes. Voir [Budgéter ses tokens](/wiki/api/token-budgeting).

## RGPD

Même pseudonymisé, cet identifiant reste une donnée personnelle au sens du RGPD tant que vous pouvez le relier à une personne. Mentionnez dans votre politique de confidentialité qu'un identifiant pseudonyme est transmis à Anthropic en tant que sous-traitant, et ne le réutilisez pas pour d'autres finalités sans base légale.

## À ne pas confondre

- **`anthropic-workspace-id`** : en-tête qui choisit le workspace de la requête, utile seulement pour des identifiants valables sur plusieurs workspaces.
- **`anthropic-user-profile-id`** : en-tête bêta (fonction « user profiles ») pour attribuer une requête à un profil quand vous agissez pour le compte d'un tiers. C'est un mécanisme distinct de `metadata.user_id`.
