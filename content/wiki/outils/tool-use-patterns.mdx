L'efficacité de Claude Code tient moins à chaque outil qu'à la façon de les enchaîner. Trois schémas reviennent sans cesse : **paralléliser** les appels indépendants, **chaîner** ceux qui dépendent l'un de l'autre, et **brancher** selon un résultat. Comprendre ces schémas vous aide à formuler des demandes qui vont vite et coûtent moins.

## Pattern 1 : la parallélisation

Claude peut émettre plusieurs appels d'outils dans un même tour quand ils sont indépendants. Les résultats reviennent ensemble, ce qui économise des allers-retours.

**Bons candidats :**

- plusieurs `Read` sur des fichiers différents ;
- plusieurs recherches (`grep`, `rg`, Glob, Grep) sur des sujets distincts ;
- des commandes Git en lecture (`git status`, `git diff`, `git log --oneline -10`) ;
- plusieurs `WebFetch` ou `WebSearch` sans lien entre eux ;
- plusieurs sous-agents (`Agent`) sur des périmètres séparés.

Exemple d'un premier tour d'exploration :

```text
Tour 1, en parallèle :
- Read README.md
- Read package.json
- Bash : git log --oneline -10
- Bash : find app -name "page.tsx" -not -path "*/node_modules/*"
```

**À ne pas paralléliser :**

- un appel qui dépend du résultat d'un autre (lire un fichier trouvé par une recherche) ;
- deux modifications du même fichier ;
- deux commandes qui écrivent dans la même ressource (même base de test, même port).

## Pattern 2 : le chaînage

Chaque étape utilise le résultat de la précédente. Le chaînage typique : **trouver, lire, modifier, vérifier**.

```text
1. rg -l "oldFunctionName" src          → liste de fichiers
2. Read de chaque fichier (en parallèle)
3. Edit de chaque fichier (en parallèle si fichiers distincts)
4. npm run build && npm test            → vérification
```

Les étapes sont séquentielles, mais les appels **à l'intérieur** d'une étape peuvent être parallèles.

Le dernier maillon, la vérification, est celui qui compte le plus. Une modification sans build ni test n'est pas terminée.

## Pattern 3 : le branchement

Claude décide de la suite selon un résultat.

```text
npm test
├─ tout passe                → récapitulatif, proposition de commit
├─ échec dans un module      → lire le test et le code, corriger, relancer
└─ échecs dans 8 modules     → sous-agents par module, ou enquête sur une cause commune
```

Autre exemple, l'exploration adaptative :

```text
find . -path "*auth*" -name "*.ts"
├─ 0 résultat   → élargir (middleware, proxy.ts, lib/session)
├─ 5 résultats  → tout lire en parallèle
└─ 60 résultats → déléguer à un sous-agent Explore qui résume
```

## Combiner les trois

Un refactoring d'API réel ressemble à ceci :

```text
1. Parallèle : README, package.json, recherche des appels à l'ancienne API
2. Branchement : 4 fichiers → édition directe ; 40 fichiers → plan validé en mode plan,
   puis sous-agents en worktree par zone
3. Parallèle : éditions indépendantes
4. Chaînage : build → tests → git diff relu → commit si vous le demandez
```

## Outils qui changent la donne en 2026

| Outil | Pattern facilité |
|-------|------------------|
| `Agent` avec `isolation: worktree` | Paralléliser des modifications sans collision |
| `Monitor` | Réagir à un événement (log, CI) sans boucle d'attente |
| `LSP` (avec un plugin d'intelligence de code) | Chaîner « définition, références, correction » de façon précise |
| `Workflow` (dynamic workflows) | Orchestrer de nombreux sous-agents et récupérer un résultat consolidé |

## Comment formuler vos demandes

- **Donnez les tâches indépendantes ensemble** : « Vérifie le build, les tests et le lint » permet à Claude de lancer les trois.
- **Dites ce qui dépend de quoi** : « Trouve d'abord où X est défini, puis propose une modification ».
- **Fixez le critère de fin** : « Termine quand `npm test` passe ».
- **Demandez un plan** pour les branchements coûteux (beaucoup de fichiers, opérations risquées).

## Anti-patterns

| Symptôme | Problème | Remède |
|----------|----------|--------|
| Dix tours « lire le fichier X » | Pas de parallélisation | Demander une lecture groupée |
| Modification sans lecture ni vérification | Risque d'erreur silencieuse | Chaîner jusqu'au test |
| `sleep` en boucle pour attendre | Gaspillage | `run_in_background` ou `Monitor` |
| Sous-agent pour lire un fichier | Surcoût | Lecture directe |
| Trente appels parallèles | Sorties illisibles, contexte saturé | Regrouper par sous-agents |
