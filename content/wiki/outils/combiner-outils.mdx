Les outils de Claude Code prennent leur valeur quand ils s'enchaînent : chercher puis lire, lire puis modifier, modifier puis vérifier. Cet article rassemble les combinaisons qui reviennent le plus, avec le prompt à donner et l'enchaînement d'outils que Claude déroule. Vous n'appelez pas les outils vous-même : vous décrivez l'objectif et le critère de réussite.

## Le principe commun

Chaque combo suit la même boucle, recommandée par Anthropic : **explorer, planifier, coder, vérifier**. La vérification (tests, build, lint, capture d'écran) est ce qui permet à Claude de corriger seul ses erreurs au lieu de vous attendre.

## Combo 1 : découvrir un dépôt inconnu

**Prompt :** « Explique-moi l'architecture de ce projet : stack, points d'entrée, routes, conventions. Ne modifie rien. »

**Enchaînement :**

1. En parallèle : `Read` du `README.md` et du manifeste (`package.json`, `pyproject.toml`), `git log --oneline -10`, recherche des points d'entrée (`find app -name "page.tsx"`).
2. Lecture des fichiers d'entrée et des utilitaires partagés.
3. Pour un gros monorepo : un sous-agent `Explore` par zone, qui renvoie chacun un résumé.

Le `CLAUDE.md` est déjà chargé au démarrage : inutile de le relire.

## Combo 2 : renommer ou changer une signature partout

**Prompt :** « Renomme `getUserData` en `fetchUserProfile` dans tout le projet, puis lance `npm run build` et `npm test`. »

**Enchaînement :**

1. `rg -n "\bgetUserData\b"` pour cartographier les usages.
2. `Read` des fichiers concernés, puis `Edit` sur chacun (en parallèle si les fichiers sont distincts).
3. `npm run build` puis `npm test` ; en cas d'échec, lecture de l'erreur et correction.

Avec un plugin d'intelligence de code, l'outil `LSP` trouve les références exactes d'un symbole, plus fiable qu'une recherche textuelle sur un nom courant.

## Combo 3 : diagnostiquer une erreur de production

**Prompt :** « Voici l'erreur : [coller la stack trace]. Trouve la cause racine, écris un test qui la reproduit, corrige, et vérifie que le test passe. Ne masque pas l'erreur. »

**Enchaînement :**

1. Recherche du message et des fichiers de la stack trace.
2. `Read` de la zone fautive et de ses appelants.
3. `git log -p` sur le fichier pour voir le changement récent suspect.
4. `Write` d'un test qui échoue, `Edit` du correctif, relance du test ciblé.

## Combo 4 : intégrer une API externe

**Prompt :** « Ajoute une route `app/api/xyz/route.ts` qui appelle l'API XYZ. Suis le modèle de `app/api/wiki/route.ts`. Lis la doc officielle d'abord. »

**Enchaînement :**

1. `WebSearch` limité au domaine officiel, puis `WebFetch` de la page de référence avec un prompt précis (« endpoint, en-têtes, format de réponse, erreurs »).
2. `Read` de la route existante citée comme modèle.
3. `Write` de la nouvelle route, `Edit` de `.env.example` pour la nouvelle variable.
4. Test avec `curl` sur le serveur de dev lancé en arrière-plan.

## Combo 5 : auditer un diff avant fusion

**Prompt :** « Lance `/code-review` sur la branche, puis `/security-review`. »

Les commandes intégrées font le travail dans un contexte neuf : `/code-review` cherche les bugs du diff (avec `--max-findings` pour régler le nombre de constats), `/security-review` les risques de sécurité. Pour un contrôle à la main :

1. `git diff main...HEAD --stat`, puis le diff des fichiers sensibles (auth, base de données, variables d'environnement).
2. Recherche de secrets en dur : `rg -n -i "(api[_-]?key|secret|token)\s*[:=]"`.
3. Un sous-agent de revue qui ne voit que le diff et vos critères.

## Combo 6 : monter une dépendance majeure

**Prompt :** « Passe Next.js en version 16. Commence en mode plan : lis les notes de version et liste les changements qui nous concernent. »

**Enchaînement :**

1. Mode plan : `WebFetch` du guide de migration, `Read` du `package.json` et des fichiers impactés.
2. Approbation du plan via `ExitPlanMode`.
3. `npm install next@16`, codemod officiel si disponible.
4. Boucle build, lecture des erreurs, `Edit`, rebuild jusqu'au vert.

## Combo 7 : générer des tests pour un module

**Prompt :** « Écris les tests de `lib/format.ts` en suivant le style de `lib/parse.test.ts`. Couvre les cas limites. Lance-les. »

**Enchaînement :** `Read` du module et du test modèle, `Write` du fichier de test, exécution ciblée (`npm test -- format`), corrections jusqu'au vert.

## Combo 8 : migration massive en parallèle

**Prompt :** « `/batch` migre tous les composants de `components/` vers la nouvelle API de thème. »

`/batch` répartit le changement entre plusieurs sous-agents, chacun dans son propre worktree. Pour piloter vous-même la répartition depuis un script :

```bash
for file in $(cat fichiers.txt); do
  claude -p "Migre $file vers la nouvelle API de thème. Réponds OK ou FAIL." \
    --allowedTools "Read,Edit,Bash(npm test *)"
done
```

Testez d'abord sur deux ou trois fichiers, ajustez le prompt, puis lancez sur tout le lot.

## Principes transversaux

- **Lire avant de modifier**, même quand le modèle n'y est plus strictement obligé.
- **Paralléliser les lectures indépendantes**, séquencer ce qui dépend d'un résultat.
- **Fermer la boucle** par une vérification exécutable, et demander à Claude de montrer la preuve (sortie de test, commande lancée).
- **Déléguer les explorations larges** à des sous-agents pour garder le contexte principal propre.
- **Encoder vos combos récurrents en skills** (`.claude/skills/<nom>/SKILL.md`) : vous les lancez ensuite avec `/<nom>`.
