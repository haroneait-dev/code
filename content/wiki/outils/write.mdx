`Write` crée un nouveau fichier ou remplace intégralement un fichier existant par le contenu fourni. Il n'ajoute rien à la fin et ne fusionne pas : ce qui était là disparaît. C'est l'outil idéal pour créer un fichier, et le mauvais choix pour changer trois lignes.

## Quand Claude utilise Write

- **Créer** un fichier qui n'existe pas : composant, script, test, migration ;
- **Réécrire entièrement** un petit fichier dont presque tout change (fichier de configuration, fixture régénérée) ;
- **Produire un fichier généré** : rapport, données de test, export.

Pour une modification partielle d'un fichier existant, Claude utilise `Edit`. C'est plus sûr (seul le passage visé change) et le diff reste lisible.

## Paramètres

| Paramètre | Obligatoire | Rôle |
|-----------|-------------|------|
| `file_path` | oui | Chemin absolu du fichier |
| `content` | oui | Contenu complet du fichier |

Exemple d'appel tel que Claude l'envoie :

```json
{
  "file_path": "/home/vous/projet/components/Button.tsx",
  "content": "export function Button({ children }: { children: React.ReactNode }) {\n  return <button type=\"button\">{children}</button>;\n}\n"
}
```

## Faut-il lire le fichier avant de l'écraser ?

La règle dépend du modèle et du fichier :

| Situation | Lecture préalable exigée ? |
|-----------|----------------------------|
| Nouveau fichier | Non |
| Fichier existant, Claude Opus 4.6, Haiku 4.5 ou modèle plus ancien | Oui, sinon erreur |
| Fichier existant, modèle plus récent (Opus 5.5, Sonnet 5.5…) | Non, si la lecture ne demanderait pas d'autorisation et que l'outil Read est disponible |
| Notebook Jupyter | Oui, sur tous les modèles |
| Fichier lu seulement en partie (`PARTIAL view`) | Oui, sur tous les modèles |

Une lecture via Bash compte aussi si la commande est simple (`cat`, `head`, `tail`, `sed -n 'X,Yp'`, `grep`, `rg`… sur un seul fichier, sans pipe ni redirection). Avant la version 2.1.228, tous les modèles devaient lire le fichier avant de l'écraser.

## Permissions

En mode Manuel (`default`), Write demande votre accord. En mode `acceptEdits` ou `auto`, les écritures dans le répertoire de travail passent sans question (hors chemins protégés comme `.git`).

Pour encadrer les écritures, utilisez des règles **`Edit(...)`** : elles s'appliquent à tous les outils qui modifient des fichiers, Write compris.

```json
{
  "permissions": {
    "ask": ["Edit(/prisma/schema.prisma)"],
    "deny": ["Edit(/.env*)", "Read(/secrets/**)"]
  }
}
```

À savoir :

- une règle de chemin écrite pour `Write`, comme `Write(docs/**)`, est acceptée mais **jamais consultée**. Claude Code affiche un avertissement au démarrage. Écrivez `Edit(docs/**)` ;
- une règle `Read(...)` en `deny` bloque aussi Write sur ce chemin, création comprise ;
- dans `.claude/settings.json`, un chemin commençant par `/` est relatif au projet. Pour un chemin absolu, utilisez `//`.

## Revenir en arrière

Chaque prompt que vous envoyez crée un checkpoint. Les fichiers créés ou écrasés par Write peuvent être restaurés avec `/rewind` (ou `Échap` deux fois sur une saisie vide), option « Restore code ». Les checkpoints ne remplacent pas Git : commitez avant les réécritures importantes.

## Pièges fréquents

**Réécrire un gros fichier pour quelques lignes.** Claude doit renvoyer tout le contenu : c'est long, coûteux en tokens de sortie, et un oubli efface du code. Demandez explicitement `Edit` pour les retouches.

**Écraser des changements faits entre-temps.** Si vous modifiez le fichier dans votre éditeur pendant que Claude travaille, un Write efface vos changements. L'article sur les conflits d'édition détaille les parades.

**Générer d'énormes fichiers de données.** Pour un jeu de données volumineux, demandez plutôt un script qui produit le fichier : Claude écrit vingt lignes au lieu de vingt mille.

**Créer des fichiers non demandés.** Si Claude a tendance à ajouter des `README.md` ou des fichiers de notes, précisez-le dans votre `CLAUDE.md` (« ne crée pas de documentation sans demande explicite »).

## Bonne pratique

Après un Write sur un fichier de configuration, faites valider le résultat par l'outil concerné : `npx tsc --noEmit`, `npm run lint`, `python -m json.tool fichier.json`. Un hook `PostToolUse` sur `Edit|Write` peut automatiser le formatage ou le lint après chaque écriture.
