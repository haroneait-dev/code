L'outil `Agent` lance un **sous-agent** : une instance de Claude avec sa propre fenêtre de contexte, qui travaille en autonomie puis renvoie un seul résultat final. Il s'appelait `Task` jusqu'à la version 2.1.63 ; les anciennes références `Task(...)` dans vos settings et définitions d'agents fonctionnent toujours comme alias.

## Pourquoi déléguer

- **Préserver le contexte principal** : le sous-agent peut lire cinquante fichiers, seul son résumé revient dans la conversation ;
- **Paralléliser** des investigations indépendantes ;
- **Spécialiser** : un agent de revue avec ses propres instructions, outils et modèle ;
- **Isoler** des modifications dans un worktree Git.

Le parent ne voit ni les appels d'outils intermédiaires ni leurs sorties : uniquement le rapport final.

## Paramètres

| Paramètre | Rôle |
|-----------|------|
| `subagent_type` | Type d'agent : intégré ou personnalisé (obligatoire) |
| `description` | Courte description de la tâche |
| `prompt` | Instructions complètes pour le sous-agent |
| `model` | Modèle pour cet appel (`haiku`, `sonnet`, `opus` ou identifiant complet) |
| `run_in_background` | Exécution en arrière-plan |
| `name` | Nom de l'instance, utile pour la reprendre ensuite |
| `isolation` | `worktree` pour travailler dans un worktree Git temporaire |

Exemple d'appel :

```json
{
  "subagent_type": "Explore",
  "description": "Cartographier l'authentification",
  "prompt": "Dans /home/vous/projet, trouve où sont gérées la connexion, la session et la déconnexion. Rends une liste de fichiers avec une phrase par fichier et les points d'entrée principaux."
}
```

Le `prompt` doit être autonome : un sous-agent classique ne voit pas votre conversation.

## Les agents intégrés

| Agent | Outils | Usage |
|-------|--------|-------|
| `Explore` | Lecture seule (Write et Edit refusés) | Recherche rapide dans le code |
| `Plan` | Lecture seule | Collecte de contexte pendant le mode plan |
| `general-purpose` | Tous les outils disponibles aux sous-agents | Tâches à plusieurs étapes qui explorent et agissent |
| `claude` | Tous les outils disponibles aux sous-agents | Agent fourre-tout, utilisé par défaut pour les sessions en arrière-plan |

S'y ajoutent des assistants internes comme `statusline-setup` et `claude-code-guide`. Vos agents personnalisés vivent dans `.claude/agents/` (projet) ou `~/.claude/agents/` (personnel), et les plugins peuvent en fournir.

## Premier plan ou arrière-plan

En session interactive, les sous-agents tournent **en arrière-plan par défaut** : vous continuez à travailler pendant qu'ils avancent. Leurs demandes d'autorisation remontent dans votre session principale avec le nom de l'agent ; `Échap` refuse cet appel sans arrêter l'agent.

- `/tasks` liste les sous-agents et commandes en cours.
- `Ctrl+X Ctrl+K` (deux fois en trois secondes) arrête tous les sous-agents d'arrière-plan.
- Un agent défini avec `background: true` reste en arrière-plan même si Claude demande le premier plan.

## Imbrication et limites

| Réglage | Défaut | Variable |
|---------|--------|----------|
| Profondeur de sous-agents sous la conversation | 3 niveaux | `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` (`1` désactive l'imbrication) |
| Sous-agents simultanés | 20 | `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` |
| Tours maximum d'un agent | aucun | champ `maxTurns` de la définition |

À la profondeur maximale, l'outil Agent est retiré : l'agent fait le travail lui-même. Quand `maxTurns` est atteint, le résultat est marqué partiel et Claude peut reprendre l'agent.

## Forks et reprise

- Un **fork** hérite de toute la conversation au lieu de partir de zéro, et réutilise le cache de prompt du parent. Lancez-en un avec `/subtask <consigne>`.
- Un sous-agent terminé peut être **repris** : Claude lui envoie un message avec l'outil `SendMessage`, et l'agent retrouve tout son historique. Les agents intégrés `Explore` et `Plan` ne se reprennent pas.

## Isoler les modifications dans un worktree

Avec `isolation: worktree` (paramètre d'appel ou champ de la définition), le sous-agent travaille dans un worktree Git temporaire. Si l'agent ne change rien, le worktree est supprimé automatiquement. C'est la bonne réponse au risque de deux agents qui éditent les mêmes fichiers en parallèle.

```markdown
---
name: refactorer
description: Applique un refactoring mécanique sur de nombreux fichiers
tools: Read, Edit, Bash
isolation: worktree
---

Applique le refactoring demandé à tous les fichiers concernés, lance les tests et rends un rapport.
```

## Contrôler les sous-agents

Les règles de permission utilisent `Agent(NomDuType)` :

```json
{
  "permissions": {
    "deny": ["Agent(general-purpose)"]
  }
}
```

Lancer un sous-agent ne demande pas d'autorisation : ce sont **ses** appels d'outils qui sont vérifiés. Pour limiter ce qu'il peut faire, restreignez son champ `tools` (ou `disallowedTools`) dans sa définition.

## Pièges fréquents

**Prompt incomplet.** « Continue ce qu'on a commencé » ne veut rien dire pour un agent neuf. Donnez chemins, objectif et format de rendu attendu.

**Déléguer une micro-tâche.** Lancer un agent pour lire deux fichiers coûte plus de tokens et de temps que de les lire directement.

**Croire à `/rewind`.** Les modifications faites par un sous-agent (hors skill forké au premier plan) ne sont pas restaurées par `/rewind`. Utilisez Git ou l'isolation en worktree.

**Faire confiance aveuglément au rapport.** Un rapport peut être incomplet. Pour un changement important, demandez au parent de vérifier le diff.
