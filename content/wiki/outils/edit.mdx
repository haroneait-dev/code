`Edit` modifie un fichier existant par **remplacement exact de texte** : il cherche `old_string` et le remplace par `new_string`. Pas d'expression régulière, pas de correspondance approximative. Si le texte n'est pas trouvé tel quel, rien ne change : c'est cette rigueur qui rend l'outil fiable.

## Quand Claude utilise Edit

C'est l'outil par défaut pour toute modification ciblée :

- corriger une ligne, ajouter un import ou une prop ;
- renommer une variable dans un fichier (avec `replace_all`) ;
- changer une valeur de configuration ;
- réécrire une fonction sans toucher au reste.

Pour créer un fichier ou tout réécrire, Claude utilise `Write`. Pour un notebook Jupyter, `NotebookEdit`.

## Paramètres

| Paramètre | Obligatoire | Rôle |
|-----------|-------------|------|
| `file_path` | oui | Chemin absolu du fichier |
| `old_string` | oui | Texte à remplacer, à l'identique |
| `new_string` | oui | Texte de remplacement, différent de `old_string` |
| `replace_all` | non | `true` pour remplacer toutes les occurrences (défaut `false`) |

Exemple d'appel tel que Claude l'envoie :

```json
{
  "file_path": "/home/vous/projet/lib/format.ts",
  "old_string": "export function formatDte(d: Date) {",
  "new_string": "export function formatDate(d: Date) {"
}
```

## Les trois vérifications

Avant tout, un chemin couvert par une règle `Read(...)` en `deny` est refusé. Ensuite, trois conditions doivent être réunies :

1. **Lecture préalable.** Claude doit avoir lu le fichier dans la conversation, et une lecture tronquée (`PARTIAL view`) ne compte pas. Claude Opus 4.6, Haiku 4.5 et les modèles plus anciens exigent toujours cette lecture. Les modèles plus récents peuvent éditer un fichier non lu si sa lecture ne demanderait pas d'autorisation.
2. **Correspondance.** `old_string` doit apparaître exactement : une espace ou une tabulation de différence suffit à rater.
3. **Unicité.** `old_string` doit apparaître une seule fois. Sinon, Claude ajoute du contexte autour ou passe `replace_all: true`.

Une lecture par Bash compte aussi (`cat`, `nl`, `bat`, `head`, `tail`, `sed -n 'X,Yp'`, `grep`, `rg` sur un seul fichier, sans pipe ni redirection).

## Fichier modifié sur disque depuis la lecture

Depuis la version 2.1.208, un fichier qui a changé après la lecture de Claude peut quand même être édité si `old_string` correspond exactement et sans ambiguïté au contenu **actuel**. Le résultat signale alors que le fichier contient d'autres changements, pour que Claude le relise avant une modification qui dépend du contexte. Dans les autres cas (texte périmé, plusieurs correspondances), Claude relit le fichier avant de réessayer.

## Exemples

### Lever une ambiguïté avec du contexte

Si `return null;` apparaît dans cinq fonctions, Claude inclut la signature englobante :

```json
{
  "file_path": "/home/vous/projet/app/page.tsx",
  "old_string": "function LoadingState() {\n  return null;\n}",
  "new_string": "function LoadingState() {\n  return <p>Chargement…</p>;\n}"
}
```

### Renommer dans un fichier

```json
{
  "file_path": "/home/vous/projet/components/Hero.tsx",
  "old_string": "userName",
  "new_string": "displayName",
  "replace_all": true
}
```

Attention : `replace_all` ne connaît pas le contexte. Il renomme aussi `userNameLabel` ou une chaîne de texte qui contient `userName`. Pour un renommage de symbole sûr à l'échelle du projet, l'outil `LSP` (avec un plugin d'intelligence de code) ou l'outil de refactoring de votre IDE sont plus précis.

## Erreurs courantes

| Message ou symptôme | Cause | Solution |
|---------------------|-------|----------|
| Texte introuvable | Indentation, espaces de fin, CRLF/LF, fichier changé | Relire le fichier, copier le passage exact |
| Plusieurs occurrences | `old_string` trop court | Ajouter les lignes voisines ou `replace_all` |
| Fichier non lu | Modèle ancien ou lecture partielle | Lire le fichier (en entier ou la zone concernée) |
| Refus par règle | `Read(...)` en `deny` sur ce chemin | Vérifier `/permissions` |

Rappel : les numéros de ligne affichés par Read ne font pas partie du fichier. Ils ne doivent jamais se retrouver dans `old_string`.

## Permissions

En mode Manuel, chaque Edit demande votre accord ; « oui, ne plus demander » vaut jusqu'à la fin de la session. En `acceptEdits` ou `auto`, les éditions dans le répertoire de travail passent sans question. Les règles de chemin s'écrivent avec `Edit(...)` et couvrent aussi Write et NotebookEdit :

```json
{
  "permissions": {
    "allow": ["Edit(/src/**)"],
    "deny": ["Edit(/.github/workflows/**)"]
  }
}
```

Une règle `Edit(...)` en `allow` accorde aussi la lecture du même chemin.

## Automatiser après chaque édition

Un hook `PostToolUse` avec le matcher `Edit|Write` peut lancer votre formateur après chaque modification :

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/format.sh" }
        ]
      }
    ]
  }
}
```

Le formateur modifie alors le fichier juste après Claude : c'est attendu, et la règle « fichier modifié sur disque » ci-dessus gère ce cas.
