Pendant une session, un même fichier peut être modifié par plusieurs acteurs : Claude, vous dans votre éditeur, un formateur automatique, un sous-agent, une autre session ou un `git pull`. Claude Code a des garde-fous pour ne pas écraser ce qu'il n'a pas vu, mais certains cas restent à votre charge. Cet article couvre les deux familles de conflits : les **modifications concurrentes** en cours de session et les **conflits de merge Git**.

## Ce que Claude Code fait pour vous protéger

### Le remplacement exact d'Edit

`Edit` ne modifie un fichier que si `old_string` correspond **exactement** et **une seule fois** au contenu. Si vous avez changé ce passage entre-temps, l'édition échoue au lieu d'écraser votre travail.

### Le fichier modifié sur disque

Depuis la version 2.1.208, si le fichier a changé depuis la dernière lecture de Claude, l'édition passe quand même lorsque `old_string` correspond exactement au contenu **actuel**. Le résultat signale à Claude que le fichier contient d'autres changements, pour qu'il le relise avant toute modification qui dépend du contexte. Dans tous les autres cas, Claude relit le fichier avant de réessayer.

### La lecture préalable

Selon le modèle, Claude doit avoir lu un fichier avant de l'éditer ou de l'écraser. Les modèles récents peuvent s'en dispenser quand la lecture ne demanderait pas d'autorisation, mais une lecture partielle (`PARTIAL view`) ne compte jamais, et un notebook doit toujours être lu avant un `Write`.

## Les situations à risque

| Situation | Risque | Parade |
|-----------|--------|--------|
| Vous éditez le fichier dans votre IDE pendant que Claude travaille | Un `Write` efface vos changements | Laissez Claude finir son tour, ou demandez des `Edit` ciblés |
| Formatage automatique (format-on-save, hook) | Les `Edit` suivants ne correspondent plus | Relecture automatique ; formater via un hook `PostToolUse` plutôt que dans l'IDE |
| Deux sous-agents sur les mêmes fichiers | Le dernier écrit gagne | Périmètres disjoints ou `isolation: worktree` |
| Deux sessions Claude sur le même dépôt | Modifications croisées | Une session par worktree (`claude --worktree`) |
| `git pull` ou changement de branche en cours de session | Claude travaille sur une version périmée | Lui dire de relire les fichiers concernés |

## Isoler le travail parallèle avec les worktrees

La meilleure prévention est de ne jamais faire travailler deux agents dans le même dossier.

```bash
# Terminal 1
claude --worktree feature-auth
# Terminal 2
claude --worktree fix-paiement
```

Chaque session travaille dans `.claude/worktrees/<nom>/` sur sa propre branche (`worktree-<nom>`). Ajoutez `.claude/worktrees/` à votre `.gitignore`, et un fichier `.worktreeinclude` pour copier les fichiers ignorés utiles (`.env`, `.env.local`) dans chaque nouveau worktree.

Pour les sous-agents, ajoutez `isolation: worktree` à leur définition : chacun reçoit un worktree temporaire, supprimé automatiquement s'il n'a rien modifié.

## Revenir en arrière : checkpoints et limites

`/rewind` (ou `Échap` deux fois sur une saisie vide) restaure le code et/ou la conversation à un prompt précédent. Mais il ne restaure pas tout :

- les fichiers modifiés par des commandes **Bash** (`rm`, `mv`, `sed -i`, scripts) ;
- les modifications **externes** (vous, une autre session), sauf si elles touchent les mêmes fichiers ;
- les modifications des **sous-agents** (hors skill forké au premier plan) ;
- les fichiers liés par lien symbolique ou lien physique.

Pour tout cela, Git reste le filet de sécurité : commitez avant les opérations risquées.

## Résoudre un conflit de merge Git avec Claude

Claude gère bien les conflits Git, à condition de travailler en non interactif (`git rebase -i` ou un éditeur qui attend une saisie bloquent la commande).

**Prompt type :** « Fusionne `main` dans ma branche. S'il y a des conflits, résous-les en gardant notre logique métier et les correctifs de `main`, explique chaque choix, puis lance les tests. Ne commite pas sans mon accord. »

Enchaînement typique :

```bash
git fetch origin
git merge origin/main            # ou : git rebase origin/main
git status                       # liste des fichiers en conflit
git diff --name-only --diff-filter=U
```

Pour chaque fichier en conflit, Claude lit les blocs `<<<<<<<`, `=======`, `>>>>>>>`, comprend l'intention des deux côtés (au besoin avec `git log -p` sur les commits concernés), remplace le bloc par la version fusionnée avec `Edit`, puis :

```bash
rg -n "^(<<<<<<<|=======|>>>>>>>)" .   # vérifier qu'aucun marqueur ne reste
npm run build && npm test
git add <fichiers résolus>
GIT_EDITOR=true git merge --continue   # ou : GIT_EDITOR=true git rebase --continue
```

`GIT_EDITOR=true` évite l'ouverture d'un éditeur interactif pour le message de commit.

Bonnes pratiques :

- **Exigez une explication par conflit** : vous validez des choix, pas seulement un résultat qui compile.
- **Méfiez-vous des fichiers générés** (lockfiles, migrations, snapshots) : régénérez-les (`npm install`, outil de migration) plutôt que de fusionner le texte.
- **Pour un rebase long**, demandez un arrêt après chaque commit en conflit pour vérifier.

## Commandes Git destructives

Ne laissez jamais Claude lancer sans votre accord explicite `git reset --hard`, `git checkout .`, `git clean -fd` ou `git push --force`. Deux règles de permission suffisent à imposer une confirmation, même en mode `auto` :

```json
{
  "permissions": {
    "ask": ["Bash(git push --force *)", "Bash(git reset --hard *)", "Bash(git clean *)"]
  }
}
```

## Récupérer après un écrasement

```bash
git diff -- chemin/fichier.ts                       # ce qui a changé depuis le dernier commit
git log -p -5 -- chemin/fichier.ts                  # historique récent du fichier
git restore --source=HEAD~1 -- chemin/fichier.ts    # restaurer une version précédente
git reflog                                          # retrouver un état perdu après reset ou rebase
```

Si rien n'était commité : essayez d'abord `/rewind` (pour les modifications faites par les outils d'édition de Claude), puis l'historique local de votre IDE.
