MCP suit une architecture client/serveur inspirée du Language Server Protocol (LSP), qui standardise déjà le dialogue entre éditeurs et langages. Comprendre qui fait quoi vous aide à configurer vos serveurs, à lire les erreurs de `/mcp` et à écrire votre propre serveur.

## Trois participants

| Participant | Rôle | Exemple |
|---|---|---|
| **Host** | L'application d'IA qui coordonne tout | Claude Code, Claude Desktop, VS Code |
| **Client** | Composant du host qui gère **une** connexion avec **un** serveur | créé automatiquement par Claude Code |
| **Serveur** | Programme qui fournit tools, resources et prompts | Filesystem, GitHub, Sentry |

Le host crée **un client par serveur**. Si vous avez configuré cinq serveurs, Claude Code maintient cinq clients, chacun avec sa connexion dédiée.

Un serveur local (stdio) sert en général un seul client. Un serveur distant (Streamable HTTP) en sert beaucoup.

Point important pour la sécurité : chaque serveur tourne dans son propre processus ou sur sa propre machine, mais **c'est le host qui voit tout**. Les résultats de tous les serveurs arrivent dans le même contexte du modèle. Un serveur malveillant ne lit pas directement les données d'un autre serveur, mais il peut tenter une injection de prompt pour que le modèle le fasse. Voir [Sécurité des serveurs MCP](/wiki/mcp/securite-mcp).

## Deux couches

**La couche données** définit les messages, en JSON-RPC 2.0 :

- la découverte (version du protocole, capacités, identité) ;
- les primitives serveur : tools, resources, prompts ;
- les primitives client : élicitation (sampling est déprécié depuis la révision 2026-07-28) ;
- les utilitaires : progression, annulation, notifications de changement.

**La couche transport** achemine ces messages :

- **stdio** : le client lance le serveur comme sous-processus. Un message JSON par ligne sur stdin et stdout. Le serveur ne doit rien écrire d'autre sur stdout ; ses logs vont sur stderr ;
- **Streamable HTTP** : chaque message est un POST vers une URL unique ; la réponse arrive en JSON ou en flux SSE propre à la requête. L'authentification passe par OAuth, un jeton Bearer ou des en-têtes.

L'ancien transport HTTP+SSE (2024) est déprécié. Le détail est dans [Transports MCP](/wiki/mcp/transports-stdio-sse).

## Le dialogue, version 2026-07-28

La révision courante de la spécification rend le protocole **sans état** :

1. **Pas de poignée de main.** Chaque requête porte dans son champ `_meta` la version du protocole et les capacités du client.
2. **Découverte facultative.** Le client peut appeler `server/discover`, que tout serveur doit implémenter, pour connaître les versions supportées, les capacités et l'identité du serveur.
3. **Liste puis appel.** Le client appelle `tools/list` (et `resources/list`, `prompts/list`), puis `tools/call` quand le modèle choisit un outil.
4. **Notifications sur abonnement.** Pour être prévenu d'un changement de liste d'outils, le client ouvre un flux `subscriptions/listen`.

Exemple d'appel d'outil :

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "weather_current",
    "arguments": { "location": "Paris", "units": "metric" },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": { "name": "example-client", "version": "1.0.0" },
      "io.modelcontextprotocol/clientCapabilities": { "elicitation": {} }
    }
  }
}
```

Réponse, avec le même `id` :

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "result": {
    "resultType": "complete",
    "content": [{ "type": "text", "text": "Paris : 18 °C, nuageux" }]
  }
}
```

Quand le serveur a besoin d'une information de l'utilisateur, il ne lui envoie plus de requête : il répond avec `"resultType": "input_required"`, et le client renvoie la requête d'origine complétée. C'est le motif « Multi Round-Trip Requests ».

**Révisions antérieures (2025-11-25 et avant).** La connexion commençait par `initialize` puis `notifications/initialized`, avec une session portée par l'en-tête `Mcp-Session-Id` en HTTP. Beaucoup de serveurs fonctionnent encore ainsi. Les clients et serveurs récents savent détecter l'ancienne génération et s'y adapter.

## Côté Claude Code

- Claude Code utilise le SDK TypeScript MCP. Son runtime « v2 » (SDK 2.0) négocie la révision 2026-07-28 avec les serveurs HTTP qui la supportent, et l'ancienne poignée de main avec les autres. La variable `MCP_SDK_GENERATION` (`v1` ou `v2`) force un runtime.
- Chaque outil apparaît sous le nom `mcp__<serveur>__<outil>`, par exemple `mcp__github__create_issue`. C'est ce nom que vous utilisez dans les règles de permission et les matchers de hooks.
- Par défaut, la **recherche d'outils** (tool search) ne charge que les noms des outils au démarrage et récupère les définitions à la demande. Ajouter des serveurs coûte donc peu de contexte.
- Un serveur distant qui tombe est reconnecté automatiquement (jusqu'à cinq tentatives). Un serveur stdio ne l'est pas : relancez-le depuis `/mcp`.

## Un serveur minimal en TypeScript

Avec le SDK v2 (`npm install @modelcontextprotocol/server zod`) :

```ts
import { McpServer } from "@modelcontextprotocol/server";
import { StdioServerTransport } from "@modelcontextprotocol/server/stdio";
import * as z from "zod/v4";

const server = new McpServer({ name: "ping-server", version: "1.0.0" });

server.registerTool(
  "ping",
  {
    description: "Renvoie pong suivi du message reçu",
    inputSchema: z.object({ message: z.string() }),
  },
  async ({ message }) => ({
    content: [{ type: "text", text: `pong : ${message}` }],
  })
);

await server.connect(new StdioServerTransport());
```

Le SDK gère la découverte, la version du protocole et le format JSON-RPC. Pour le tutoriel complet, voir [Créer un serveur MCP en TypeScript](/wiki/mcp/creer-serveur-ts-setup) ou [en Python](/wiki/mcp/creer-serveur-py-setup).

## Pourquoi ce découpage

- **Isolation** : un serveur qui plante ne fait pas tomber le host.
- **Indépendance du langage** : SDK officiels en TypeScript, Python, Go, Rust, Java, Kotlin, C#, Swift, Ruby et PHP.
- **Évolution séparée** : chaque serveur se met à jour à son rythme, et la négociation de version gère la compatibilité.
