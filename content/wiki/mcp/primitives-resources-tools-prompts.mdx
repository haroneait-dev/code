Un serveur MCP expose trois types de briques : **tools**, **resources** et **prompts**. Elles se distinguent surtout par **qui décide de les utiliser** : le modèle, l'application ou l'utilisateur. Choisir la bonne primitive rend votre serveur plus simple à utiliser et moins coûteux en contexte.

## Vue d'ensemble

| Primitive | Contrôlée par | Rôle | Dans Claude Code |
|---|---|---|---|
| **Tool** | le modèle | une action ou un calcul que Claude décide d'appeler | outil `mcp__serveur__outil`, soumis aux permissions |
| **Resource** | l'application (souvent sur demande de l'utilisateur) | une donnée identifiée par une URI, à lire et joindre au contexte | mention `@serveur:uri` dans le prompt |
| **Prompt** | l'utilisateur | un modèle de messages paramétré | commande `/serveur:prompt` |

Ces trois primitives sont toutes facultatives : beaucoup de serveurs n'exposent que des tools.

## Tools : ce que le modèle peut faire

Un tool est une fonction avec un nom, une description et un schéma d'entrée (JSON Schema). Le modèle lit la liste, choisit un outil et fournit les arguments. Un tool peut lire (rechercher des tickets) ou agir (créer une issue, déployer).

Définition telle que le client la reçoit dans `tools/list` :

```json
{
  "name": "create_issue",
  "title": "Créer une issue",
  "description": "Crée une issue dans le dépôt indiqué. À utiliser quand l'utilisateur demande de signaler un bug ou une tâche.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "repo": { "type": "string", "description": "Dépôt au format owner/nom" },
      "title": { "type": "string" },
      "body": { "type": "string" }
    },
    "required": ["repo", "title"]
  },
  "annotations": { "readOnlyHint": false, "destructiveHint": false, "idempotentHint": false }
}
```

Points clés :

- **Résultat** : un tableau `content` (blocs `text`, `image`, `audio`, `resource_link`, ressource intégrée) et, si l'outil déclare un `outputSchema`, un `structuredContent` JSON. Dans ce cas, renvoyez aussi la version texte dans `content` pour les clients qui ne lisent que ce champ.
- **Erreurs** : un échec métier (fichier absent, API indisponible) se renvoie comme résultat avec `isError: true`. Le modèle le lit et peut corriger son appel. Une erreur de protocole JSON-RPC, elle, ne lui parvient pas.
- **Annotations** (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`) : des indications pour le client. Elles ne sont fiables que si le serveur l'est.
- **Nommage** : 1 à 128 caractères, lettres ASCII, chiffres, `_`, `-` et `.`. Préférez un verbe explicite (`create_issue`, pas `issue`).

## Resources : les données à lire

Une resource est un contenu identifié par une URI : `file:///projet/README.md`, `postgres://schema/users`, `github://issue/42`. Le serveur la décrit dans `resources/list` et la renvoie avec `resources/read`, en texte ou en binaire (base64).

- **Templates** : pour une famille de resources, le serveur publie un modèle d'URI (RFC 6570) via `resources/templates/list`, par exemple `github://issue/{numero}`.
- **Annotations** : `audience` (`user`, `assistant`), `priority` (0 à 1) et `lastModified` aident le client à trier.
- **Changements** : un client peut s'abonner aux mises à jour d'une resource. Depuis la révision 2026-07-28, cela passe par `subscriptions/listen` (et non plus `resources/subscribe`).
- **Cache** : les réponses portent `ttlMs` et `cacheScope`, qui disent au client combien de temps les garder.

Dans Claude Code, tapez `@` : les resources des serveurs connectés apparaissent dans l'autocomplétion, à côté des fichiers. Une resource mentionnée est lue et jointe à votre message :

```text
Compare @postgres:schema://users avec @docs:file://database/user-model
```

Claude Code fournit aussi au modèle des outils pour lister et lire les resources lui-même. Les ressources d'interface MCP Apps (`ui://`) n'apparaissent pas dans ces listes : elles sont faites pour être affichées par un hôte graphique, pas lues par Claude.

## Prompts : les commandes de l'utilisateur

Un prompt est un modèle de conversation que l'utilisateur déclenche explicitement. Le serveur déclare ses arguments ; `prompts/get` renvoie une liste de messages prêts à injecter.

Dans Claude Code, chaque prompt devient une commande. Les arguments se passent séparés par des espaces :

```text
/github:pr_review 456
/mcp__jira__create_issue login-bug high
```

Cas d'usage : une revue de PR qui embarque les règles de l'équipe, un résumé d'incident, un gabarit de rapport. Les prompts restent la primitive la moins prise en charge par les clients : ne mettez pas dedans une fonction indispensable.

## Un serveur qui expose les trois

Avec le SDK Python officiel v2 (`MCPServer`, ex-FastMCP) :

```python
from mcp.server import MCPServer

mcp = MCPServer("tickets")

TICKETS = {"42": "Le formulaire de connexion plante sur Safari."}


@mcp.tool()
def search_tickets(query: str) -> str:
    """Cherche des tickets dont le texte contient la requête."""
    hits = [f"#{k} {v}" for k, v in TICKETS.items() if query.lower() in v.lower()]
    return "\n".join(hits) or "Aucun ticket trouvé."


@mcp.resource("tickets://{ticket_id}")
def get_ticket(ticket_id: str) -> str:
    """Texte complet d'un ticket."""
    return TICKETS.get(ticket_id, "Ticket inconnu.")


@mcp.prompt()
def triage(ticket_id: str) -> str:
    """Prépare le tri d'un ticket."""
    return f"Lis le ticket {ticket_id}, estime sa gravité (1 à 4) et propose une équipe."


if __name__ == "__main__":
    mcp.run()
```

Branchement dans Claude Code :

```bash
claude mcp add tickets -- uv run --directory /chemin/absolu/projet server.py
```

Vous obtenez l'outil `mcp__tickets__search_tickets`, la mention `@tickets:tickets://42` et la commande `/tickets:triage 42`.

## Comment choisir

| Besoin | Primitive |
|---|---|
| Claude doit agir ou chercher de lui-même | Tool |
| Donnée stable que l'utilisateur veut joindre au contexte | Resource |
| Procédure répétée que l'utilisateur lance à la demande | Prompt |
| Donnée que Claude doit trouver seul au fil de la tâche | Tool de recherche ou de lecture (éventuellement en plus d'une resource) |

Deux erreurs fréquentes :

- **Tout mettre en resources** : dans la plupart des clients, le modèle n'explore pas les resources aussi naturellement qu'il appelle un outil. Si Claude doit découvrir l'information seul, exposez aussi un tool (`search_…`, `get_…`), quitte à renvoyer un `resource_link`.
- **Transformer un prompt en tool** : si c'est l'utilisateur qui doit décider de lancer la procédure, c'est un prompt. Si c'est le modèle, c'est un tool.

## Et côté client ?

La spécification définit aussi des fonctions côté client, que le serveur peut solliciter :

- **Élicitation** : le serveur demande une information à l'utilisateur (formulaire ou page web). C'est la fonction client recommandée en 2026.
- **Sampling** (demander une complétion au modèle) et **Roots** (connaître les dossiers de travail) sont **dépréciés** depuis la révision 2026-07-28.

Voir [MCP en 2026](/wiki/mcp/evolution-2026-apps-elicitation).
