Le serveur **Memory** est un serveur MCP de référence, maintenu dans le dépôt officiel `modelcontextprotocol/servers`. Il donne à Claude une mémoire persistante sous forme de **graphe de connaissances** : Claude peut y écrire des faits et les relire dans une session suivante.

## Le modèle de données

- **Entité** : un nœud nommé avec un type (`person`, `project`, `concept`...).
- **Relation** : un lien orienté entre deux entités, formulé à la voix active (`works_on`, `depends_on`).
- **Observation** : un fait textuel attaché à une entité.

```text
Entité : Alice (person)
  Observations :
    - "Préfère TypeScript"
    - "Lead du projet Pegasus"
Entité : Pegasus (project)
  Observations :
    - "Migration vers Next.js 16 prévue"
Relation : Alice --works_on--> Pegasus
```

## Installation

### Dans Claude Code

```bash
claude mcp add memory -e MEMORY_FILE_PATH=/home/vous/.claude/memory.jsonl -- npx -y @modelcontextprotocol/server-memory
```

Ajoutez `--scope user` pour l'avoir dans tous vos projets. Vérifiez ensuite avec `/mcp`.

### Dans Claude Desktop (ou un fichier `.mcp.json`)

```json
{
  "mcpServers": {
    "memory": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-memory"],
      "env": {
        "MEMORY_FILE_PATH": "/home/vous/.claude/memory.jsonl"
      }
    }
  }
}
```

Sous Windows, encadrez la commande avec `cmd /c`. Une image Docker `mcp/memory` existe aussi.

Le graphe est stocké au format **JSONL** (une ligne JSON par élément). Sans `MEMORY_FILE_PATH`, le fichier `memory.jsonl` est créé dans le dossier du serveur, qu'un cache `npx` peut effacer : définissez toujours un chemin explicite.

## Les outils exposés

| Outil | Rôle |
|---|---|
| `create_entities` | Créer des entités |
| `create_relations` | Créer des relations |
| `add_observations` | Ajouter des faits à une entité |
| `delete_entities`, `delete_relations`, `delete_observations` | Supprimer |
| `read_graph` | Lire tout le graphe |
| `search_nodes` | Chercher par texte (noms, types, observations) |
| `open_nodes` | Lire des entités précises |

Claude les appelle quand vous lui demandez de « retenir » quelque chose ou de « retrouver ce qu'on a dit sur X ».

## Bien l'utiliser

Sans discipline, le graphe devient vite un fouillis. Quelques règles :

1. **Fixez une liste de types d'entités** dans vos instructions (`person`, `project`, `decision`, `bug`).
2. **Demandez une recherche avant création** (`search_nodes`) pour éviter les doublons.
3. **Préférez des observations courtes et atomiques** à des paragraphes.
4. **Nettoyez régulièrement** : `read_graph`, puis suppression de ce qui est périmé.

Exemple d'instruction à placer dans votre `CLAUDE.md` ou votre system prompt :

```text
Au début de chaque tâche, cherchez dans la mémoire (search_nodes) les entités liées au projet.
Quand une décision technique est prise, enregistrez-la comme observation de l'entité du projet.
```

## Memory ou mémoire intégrée ?

Claude Code dispose déjà de `CLAUDE.md` et d'une mémoire automatique (`/memory`), et l'assistant claude.ai a sa propre mémoire. Le serveur Memory reste utile si vous voulez une mémoire **structurée**, **portable** entre clients MCP et inspectable dans un fichier.

## Limites

- Pas de recherche sémantique : `search_nodes` fait une correspondance textuelle.
- Pas d'historique ni de versionnage (sauf si vous versionnez le fichier vous-même).
- Fichier local unique : évitez plusieurs clients qui écrivent en même temps.
- Pas d'oubli automatique : le nettoyage est à votre charge.
