Quand une équipe utilise dix serveurs MCP, chaque poste finit avec sa propre configuration, ses propres jetons et ses propres pannes. Une **passerelle MCP** (gateway) regroupe ces serveurs derrière une seule URL et centralise authentification, filtrage et journalisation. Avant d'en installer une, vérifiez que Claude Code ne règle pas déjà votre problème : c'est souvent le cas.

## Le problème à résoudre

Trois symptômes distincts, qui n'appellent pas la même réponse :

| Symptôme | Réponse la plus simple |
|---|---|
| Chaque développeur reconfigure les mêmes serveurs | `.mcp.json` commité, plugin, ou serveurs fournis par l'organisation |
| Trop d'outils, le contexte sature | tool search de Claude Code (activé par défaut) |
| Jetons d'API partagés sur tous les postes, pas d'audit | passerelle MCP avec authentification centralisée |

## Ce que Claude Code fait déjà

**Espaces de noms.** Chaque outil est préfixé par le nom de son serveur : `mcp__github__create_issue`, `mcp__linear__create_issue`. Deux serveurs peuvent exposer le même nom d'outil sans collision, et vos règles de permission ciblent un serveur précis.

**Coût en contexte.** Avec le tool search, seuls les noms des outils sont chargés au démarrage ; les définitions arrivent à la demande. Ajouter des serveurs coûte peu. Agréger pour « économiser du contexte » n'est donc plus un bon argument.

**Partage dans un projet.** Un `.mcp.json` à la racine du dépôt, avec des `${VAR}` à la place des secrets, donne à toute l'équipe les mêmes serveurs :

```json
{
  "mcpServers": {
    "sentry": { "type": "http", "url": "https://mcp.sentry.dev/mcp" },
    "outils-internes": {
      "type": "http",
      "url": "https://mcp.interne.exemple.com/mcp",
      "headers": { "Authorization": "Bearer ${INTERNAL_MCP_TOKEN}" }
    }
  }
}
```

**Distribution par l'organisation.** Les administrateurs disposent de trois leviers dans les paramètres gérés :

| Mécanisme | Effet |
|---|---|
| `managedMcpServers` (v2.1.259+) | fournit des serveurs distants à chaque utilisateur, en plus des siens. HTTPS obligatoire, aucune commande locale |
| `managed-mcp.json` | contrôle exclusif : seuls les serveurs de ce fichier se chargent |
| `allowedMcpServers` / `deniedMcpServers` | listes d'autorisation et d'interdiction par URL, commande ou nom |

Exemple de liste d'autorisation :

```json
{
  "allowedMcpServers": [
    { "serverUrl": "https://mcp.sentry.dev/*" },
    { "serverUrl": "https://*.interne.exemple.com/*" }
  ],
  "deniedMcpServers": [
    { "serverName": "serveur-non-approuve" }
  ]
}
```

Vous pouvez aussi empaqueter des serveurs dans un **plugin** diffusé par une marketplace interne, ou passer par les **connecteurs** gérés depuis la console d'administration claude.ai, qui apparaissent automatiquement dans Claude Code.

## Quand une passerelle se justifie

Une passerelle apporte une vraie valeur quand vous avez besoin de :

- **ne jamais distribuer** les identifiants des API en aval (le jeton GitHub de l'équipe reste sur la passerelle) ;
- **filtrer les outils par rôle** : un stagiaire ne voit pas `delete_database` ;
- **journaliser** chaque appel pour l'audit et la conformité ;
- **limiter le débit** et protéger des services fragiles ;
- **exposer des serveurs stdio** (qui ne servent qu'un client) à plusieurs personnes, en les faisant tourner dans des conteneurs.

Architecture type :

```text
Postes Claude Code / Claude Desktop
        │  Streamable HTTP + OAuth (SSO de l'entreprise)
        ▼
   Passerelle MCP  ── journal d'audit, filtrage par rôle
        │
   ┌────┼──────────┬──────────────┐
   ▼    ▼          ▼              ▼
GitHub  Linear   Postgres   Outils internes
(jeton propre à la passerelle pour chaque service)
```

## Ce que la révision 2026-07-28 change pour le routage

La révision courante a été pensée en partie pour les passerelles :

- **Sans état** : plus de `Mcp-Session-Id`, donc plus de sessions collantes. N'importe quelle instance de la passerelle peut traiter n'importe quelle requête.
- **En-têtes de routage** : chaque POST porte `Mcp-Method` (par exemple `tools/call`) et `Mcp-Name` (le nom de l'outil, du prompt ou l'URI de la resource). Un répartiteur de charge ou un pare-feu applicatif peut router ou bloquer **sans lire le corps JSON**.
- **Paramètres en en-tête** : un outil peut marquer un paramètre avec `x-mcp-header` dans son schéma (par exemple la région). Le client le recopie dans un en-tête `Mcp-Param-Region`, utilisable pour router vers le bon centre de données.
- **Cohérence vérifiée** : un serveur qui lit le corps doit rejeter une requête dont les en-têtes ne correspondent pas au corps (`400`, erreur `-32020`). Cela empêche de tromper un intermédiaire avec un en-tête falsifié.
- **Cache** : les listes portent `ttlMs` et `cacheScope` (`public` ou `private`). Un intermédiaire ne doit mettre en cache que les réponses `public`.

Pendant la transition, beaucoup de serveurs en amont restent sur une révision 2025, avec session. Une passerelle doit gérer les deux générations, ou n'agréger que des serveurs à jour.

## Règles d'authentification à respecter

C'est là que la plupart des passerelles maison se trompent :

1. **Pas de relais de jeton.** La spécification interdit à un serveur MCP d'accepter ou de transmettre un jeton qui n'a pas été émis pour lui. La passerelle valide le jeton de l'utilisateur, puis utilise **ses propres** identifiants (ou un échange de jetons) pour chaque service en aval.
2. **Audience vérifiée.** Le jeton présenté à la passerelle doit avoir été émis pour l'URL de la passerelle (paramètre `resource` d'OAuth, RFC 8707).
3. **Métadonnées publiées.** La passerelle, comme tout serveur MCP protégé, publie ses métadonnées de ressource protégée (RFC 9728) pour que les clients trouvent le serveur d'autorisation.
4. **SSO d'entreprise.** L'extension officielle Enterprise-Managed Authorization permet de piloter l'accès depuis le fournisseur d'identité de l'entreprise ; l'extension OAuth Client Credentials couvre les accès machine à machine.

## Espaces de noms dans la passerelle

Si la passerelle expose tous les outils sous un seul serveur, les collisions reviennent. Deux solutions :

- **préfixer** : `github_create_issue`, `linear_create_issue` (restez dans les caractères autorisés : lettres, chiffres, `_`, `-`, `.`) ;
- **exposer plusieurs URL** : `https://passerelle/github/mcp`, `https://passerelle/linear/mcp`. Chaque service reste un serveur distinct dans Claude Code, avec son propre préfixe `mcp__…`, et vos règles de permission restent lisibles.

La seconde option est souvent la meilleure avec Claude Code.

## Outils existants

L'écosystème évolue vite ; évaluez par vous-même avant d'adopter. Parmi les projets open source connus :

- **Docker MCP Gateway** : lance chaque serveur dans un conteneur isolé, derrière un point d'entrée unique ;
- **ToolHive** (Stacklok) : exécution et gestion de serveurs MCP en conteneurs pour une équipe ;
- **agentgateway** : proxy pour agents qui fédère plusieurs serveurs MCP avec espaces de noms ;
- **mcp-proxy** : pont entre stdio et HTTP, pour exposer un serveur local sur le réseau.

Les grands clouds et plusieurs éditeurs de sécurité proposent aussi des passerelles gérées. Vérifiez leur prise en charge de la révision 2026-07-28 et d'OAuth avant de choisir.

## Les inconvénients

- **Un point de défaillance unique** s'il n'est pas redondé.
- **Une cible de choix** : la passerelle détient les identifiants de tous les services. Durcissez-la comme un coffre à secrets.
- **Débogage plus difficile** : une erreur peut venir du client, de la passerelle ou du serveur en amont. Journalisez les en-têtes `Mcp-Method` et `Mcp-Name` à chaque étape.
- **Latence** : un saut réseau de plus.

Pour une personne seule ou une petite équipe, `.mcp.json` et les serveurs officiels distants suffisent largement. Une approche mixte fonctionne bien : les serveurs qui ont besoin de votre machine (fichiers, Git, navigateur) restent en stdio local, les services partagés passent par la passerelle.
