Déléguer n'est pas gratuit : un subagent repart de zéro, consomme ses propres tokens et ne vous montre que son résumé. La bonne question n'est donc pas « puis-je déléguer ? » mais « qu'est-ce que la délégation me fait gagner ? ». Voici les critères issus de la documentation officielle et de la pratique.

## Les signaux qui justifient un subagent

### 1. La tâche produit beaucoup de sortie inutile ensuite

C'est le cas d'usage principal : lancer une suite de tests, lire des logs, parcourir de la documentation, chercher dans 40 fichiers. La sortie volumineuse reste dans le contexte du subagent ; seule la synthèse revient.

```text
Utilisez un subagent pour lancer la suite de tests et ne me rapporter
que les tests en échec avec leur message d'erreur.
```

### 2. La tâche est autonome et se résume

Vous pouvez la décrire en deux ou trois phrases et dire à quoi ressemble le résultat. « Listez les routes API sans vérification de jeton, avec fichier et ligne » est délégable. « Améliorez le code » ne l'est pas.

### 3. Vous voulez imposer des restrictions

Un agent en lecture seule, sans `Bash`, ou limité à un serveur MCP, garantit qu'une analyse ne modifiera rien.

### 4. Plusieurs recherches sont indépendantes

Trois zones du code à étudier sans lien entre elles : trois subagents en parallèle. Le temps total devient celui du plus lent.

### 5. Un modèle moins cher suffit

Une recherche simple peut tourner sur `haiku` pendant que votre session reste sur Opus 5.5.

## Les signaux qui disent « restez dans la conversation »

- Vous allez itérer avec Claude, corriger, préciser.
- Les étapes partagent beaucoup de contexte (plan, implémentation, tests du même changement).
- La modification est petite et ciblée.
- Vous allez éditer les fichiers juste après les avoir lus : les relire dans la conversation principale évite de payer la lecture deux fois.
- Un `grep` ou un `ls` donne la réponse en une commande.

## Choisir le bon outil

| Situation | Outil |
| --- | --- |
| Question sur ce qui est déjà dans la conversation | `/btw` (voit tout, sans outils, hors historique) |
| Tâche annexe qui a besoin de tout le contexte actuel | Fork : `/subtask <tâche>` |
| Tâche annexe autonome, sortie volumineuse | Subagent |
| Consignes réutilisables exécutées dans la conversation | [Skill](/wiki/skills/skill-vs-agent-vs-mcp) |
| Dizaines ou centaines d'agents, résultats recoupés | [Dynamic workflow](/wiki/cli/dynamic-workflows-agents-arriere-plan) |
| Tâches indépendantes que vous voulez suivre vous-même | [Agent view](/wiki/cli/agent-view-sessions) (`claude agents`) |
| Travailleurs qui doivent se parler et se répartir le travail | Équipe d'agents (expérimental, désactivé par défaut) |

## Un test rapide avant de déléguer

Posez-vous trois questions :

1. Puis-je écrire le brief du subagent en une seule fois, sans « vous savez, le fichier de tout à l'heure » ?
2. Le résultat attendu tient-il en quelques dizaines de lignes ?
3. Ai-je besoin de voir le raisonnement intermédiaire ?

Oui, oui, non : déléguez. Sinon, clarifiez d'abord dans la conversation principale.

## Et si Claude délègue trop ou pas assez ?

- Trop : refusez des types précis avec `"deny": ["Agent(Explore)"]` dans `permissions`, ou demandez-le simplement (« faites-le directement, sans subagent »).
- Pas assez : nommez l'agent dans votre demande, ou utilisez une @-mention (`@agent-<nom>`) qui garantit son lancement. Une description d'agent contenant « use proactively » encourage aussi la délégation automatique.
