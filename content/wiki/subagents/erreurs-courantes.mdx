Un subagent échoue rarement de façon spectaculaire : il renvoie quelque chose, mais ce quelque chose est inexploitable, ou bien votre agent personnalisé n'est jamais utilisé. Voici les erreurs les plus fréquentes, regroupées en erreurs de brief et erreurs de configuration.

## Erreurs de brief

### 1. Un brief trop vague

« Regardez le code et dites-moi ce que vous en pensez » produit une analyse générique. Un bon brief contient :

- le **périmètre** exact (« uniquement `app/api/wiki/` ») ;
- l'**objectif** (« vérifier que chaque route contrôle le jeton ») ;
- le **format de sortie** (« tableau Fichier | Ligne | OK/KO ») ;
- le **cas vide** (« répondez RAS si tout est correct »).

### 2. Croire que le subagent connaît la conversation

Un subagent classique ne voit ni votre historique, ni les fichiers déjà lus, ni les skills déjà invoquées. Il reçoit le message de délégation, son prompt système, vos CLAUDE.md et un `git status` (Explore et Plan sautent même ces deux derniers). Si vous avez décidé que la table s'appelle `wiki_tips`, répétez-le dans votre demande. Si le contexte à transmettre est énorme, utilisez un fork : `/subtask <tâche>`.

### 3. Un rapport sans preuves

« J'ai regardé, ça semble correct » ne permet pas d'agir. Exigez le chemin, le numéro de ligne et l'extrait fautif pour chaque problème.

### 4. Déléguer un simple look-up

Un subagent pour un `grep` ou pour lire un fichier que vous connaissez coûte un contexte complet et du temps. Gardez les subagents pour les lectures massives ou les sorties volumineuses.

### 5. Un agent qui modifie alors que vous vouliez une analyse

Les agents general-purpose et ceux sans champ `tools` peuvent écrire. Pour une analyse, utilisez un agent en lecture seule (`tools: Read, Grep, Glob`) ou `disallowedTools: Write, Edit`, plutôt qu'une simple consigne dans le prompt.

### 6. Relancer trois fois en raffinant

Si le brief doit être corrigé plusieurs fois, la tâche n'était pas mûre. Clarifiez dans la conversation principale, puis déléguez une fois. Pour poursuivre un travail, demandez à Claude de **reprendre** le subagent (il garde tout son historique) plutôt que d'en lancer un nouveau.

## Erreurs de configuration

### 7. Un champ mal orthographié

Les champs sont en camelCase : `disallowedTools`, `permissionMode`, `maxTurns`. `disallowed_tools` ou `permission_mode` sont ignorés **sans message d'erreur**.

### 8. Un agent qui n'apparaît jamais

Claude Code ignore le fichier sans le signaler dans la session si :

- il n'a pas de `name` ;
- le `---` d'ouverture n'est pas sur la première ligne ;
- le `name` contient `:` ou commence par `-` ;
- il a un `name` mais pas de `description` ;
- le YAML ne se parse pas.

Lancez `claude --debug` pour voir la raison, ou `claude plugin validate .claude/agents` pour détecter le YAML invalide. Si vous venez de créer le tout premier fichier d'un dossier `agents` qui n'existait pas, redémarrez la session.

### 9. Une description trop floue

Claude délègue sur la base de la `description`. « Aide sur le code » ne sera jamais choisi. Dites quand l'utiliser (« après toute modification dans `app/api/` ») et ajoutez « use proactively » si vous voulez une délégation spontanée. Pour garantir l'appel, utilisez une @-mention : `@agent-<nom>`.

### 10. Une liste `tools` qui ne résout rien

Si toutes les entrées de `tools` sont fausses ou indisponibles pour un subagent, il refuse de démarrer avec une erreur du type `Agent 'code-reviewer' would be spawned with zero tools — refusing`, suivie des entrées non reconnues. Attention aussi : un subagent en arrière-plan (cas par défaut) ne garde qu'une liste réduite d'outils intégrés.

### 11. Croire que `disallowedTools: Bash(git push *)` bloque une seule commande

Cette entrée retire **tout** l'outil `Bash`. Pour bloquer seulement `git push`, ajoutez la règle à `permissions.deny` dans vos réglages.

### 12. Un `permissionMode` qui semble ignoré

Si votre session est en mode `auto`, `acceptEdits` ou `bypassPermissions`, le subagent suit ce mode et ignore son propre `permissionMode`. Un agent ne peut pas s'accorder `bypassPermissions`.

### 13. Un agent de plugin sans ses hooks

Les agents fournis par un plugin ignorent `hooks`, `mcpServers` et `permissionMode`. Copiez le fichier dans `.claude/agents/` si vous en avez besoin.

### 14. `Concurrent subagent limit reached`

Vingt subagents tournent déjà dans la session. Attendez qu'un emplacement se libère, découpez en vagues, ou augmentez `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`.

### 15. Un worktree qui ne contient pas vos derniers changements

Avec `isolation: worktree`, le worktree part par défaut de votre branche par défaut, pas du `HEAD` de la session. Un agent lancé sur une branche de fonctionnalité non fusionnée ne verra pas vos commits. Committez et indiquez la base, ou travaillez sans isolation.

### 16. Accorder une permission « pour la session » à un subagent

Les demandes de permission d'un subagent en arrière-plan remontent dans votre session principale. Une autorisation durable que vous accordez à cette occasion s'applique à toute la session, conversation principale comprise.

### 17. Vouloir reprendre Explore ou Plan

Ces deux agents intégrés sont « one-shot » et ne renvoient pas d'identifiant. Pour un travail à poursuivre, utilisez general-purpose ou un agent personnalisé.

### 18. Des coéquipiers au lieu de subagents

Si les équipes d'agents sont activées (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`), un subagent que Claude nomme se lance comme coéquipier. Désactivez les équipes si vous voulez des subagents classiques.
