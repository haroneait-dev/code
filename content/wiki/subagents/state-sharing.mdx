Chaque subagent travaille dans sa propre fenêtre de contexte : c'est ce qui protège la conversation principale, mais cela pose une question dès que vous enchaînez plusieurs agents. Comment le résultat de A parvient-il à B ? Claude Code offre plusieurs mécanismes, du plus simple au plus outillé.

## 1. Le rapport final

C'est le mécanisme par défaut : le subagent termine par un message que Claude reçoit comme résultat de l'outil `Agent` (ou, pour un subagent en arrière-plan, dans une notification de fin). Claude peut ensuite en transmettre l'essentiel au subagent suivant :

```text
Utilisez l'agent code-reviewer pour trouver les problèmes de performance,
puis l'agent optimizer pour les corriger.
```

À savoir :

- Le rapport entre dans la conversation principale et y reste : gardez-le court (quelques centaines de tokens).
- Claude Code analyse chaque rapport avant que Claude le lise. Les textes qui imitent des balises système sont neutralisés, et le rapport arrive sous un en-tête qui précise que les instructions qu'il contient n'ont aucune autorité de votre part.
- Si le subagent s'arrête à sa limite `maxTurns`, la sortie revient marquée comme partielle.

## 2. La sortie structurée

Imposez un format strict dans le prompt de l'agent pour que le parent puisse l'exploiter sans ambiguïté :

```json
{
  "verdict": "approve | request_changes | block",
  "findings": [
    { "file": "app/api/wiki/route.ts", "line": 42, "severity": "major", "message": "..." }
  ],
  "summary": "..."
}
```

Précisez « répondez uniquement avec ce JSON, sans bloc Markdown » et donnez un exemple. Si le résultat alimente un script (CI, mode `-p`), validez-le côté script et relancez en cas d'échec.

## 3. Les fichiers

Pour un volume important (logs, code généré, liste de 300 fichiers), le subagent écrit sur disque et ne renvoie que le chemin et un résumé :

```text
parent  → explorer : « écrivez l'inventaire dans .claude/scratch/inventaire.json »
explorer → parent  : { "path": ".claude/scratch/inventaire.json", "summary": "312 fichiers, 14 sans test" }
parent  → planner  : « lisez .claude/scratch/inventaire.json et proposez un plan »
```

Précautions :

- Utilisez un dossier de travail ignoré par Git (par exemple `.claude/scratch/` ajouté à `.gitignore`) et des noms uniques si plusieurs agents écrivent en parallèle.
- Un agent avec `isolation: worktree` écrit dans **son** worktree, pas dans votre copie : indiquez un chemin absolu hors du dépôt si le parent doit relire le fichier, ou faites committer le résultat.
- N'écrivez jamais de secrets dans ces fichiers.

## 4. SendMessage et la reprise d'un subagent

Un subagent terminé peut être **repris** : il garde tout son historique (appels d'outils, résultats, raisonnement). Claude utilise l'outil `SendMessage` avec l'identifiant ou le nom de l'agent :

```text
Continuez cette revue et analysez maintenant la logique d'autorisation.
```

- Claude peut nommer un subagent à son lancement ; ce nom permet de le recontacter.
- Un subagent qui possède `SendMessage` reçoit au démarrage la liste des autres agents nommés de la session (`main` compris) et peut leur écrire. La communication directe entre agents existe donc, mais reste à réserver aux cas précis.
- Explore et Plan ne peuvent pas être repris : ils ne renvoient pas d'identifiant.
- Un message d'un autre agent n'est jamais une approbation de votre part : il ne peut ni valider une demande de permission ni modifier la configuration d'un agent.

## 5. Les hooks

| Hook | Ce qu'il reçoit ou permet |
| --- | --- |
| `SubagentStart` | `agent_id`, `agent_type` ; peut injecter du contexte dans le subagent via `additionalContext` |
| `SubagentStop` | `agent_id`, `agent_type`, `agent_transcript_path`, `last_assistant_message` ; `decision: "block"` relance le subagent avec une consigne |
| `PostToolUse` sur `Agent` | Ajoute du contexte à la session parente après le retour d'un subagent |

Exemple : injecter les conventions d'API dans chaque agent `api-developer` au démarrage, ou archiver chaque rapport final dans un fichier de suivi depuis `SubagentStop`.

## 6. La mémoire persistante

Le champ `memory` donne à un agent un dossier qui survit d'une session à l'autre (`project` : `.claude/agent-memory/<nom>/`). C'est l'outil adapté pour un savoir qui s'accumule (motifs de bugs, décisions d'architecture), pas pour passer un résultat ponctuel entre deux agents.

## 7. Au-delà des subagents

- **Équipes d'agents** (expérimental, `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`) : liste de tâches partagée et boîtes aux lettres entre coéquipiers.
- **Dynamic workflows** : les résultats intermédiaires restent dans les variables du script ; la conversation ne reçoit que la réponse finale.
- **Messagerie entre sessions** : pour faire circuler des résultats entre des sessions Claude Code que vous lancez vous-même.

## Quel mécanisme choisir

| Besoin | Mécanisme |
| --- | --- |
| Verdict ou résumé court | Rapport final |
| Résultat à exploiter par un script | Sortie structurée (JSON) |
| Gros volume | Fichier + chemin dans le rapport |
| Poursuivre le travail d'un agent | Reprise via `SendMessage` |
| Contexte commun à injecter ou rapports à archiver | Hooks `SubagentStart` / `SubagentStop` |
| Savoir qui s'accumule dans le temps | `memory` |
| Pipeline de dizaines d'agents | Dynamic workflow |

## Anti-patterns

- **Committer un fichier pour qu'un autre agent le lise** : lent, pollue l'historique et casse en parallèle.
- **Des rapports de 5 000 tokens** : ils restent dans la conversation principale et sont relus à chaque tour.
- **Supposer qu'un subagent connaît le résultat d'un frère** : sans transmission explicite (brief, fichier ou message), il ne le connaît pas.
