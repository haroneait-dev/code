Un agent qui vient d'écrire du code connaît ses raccourcis et les justifie. Un subagent de revue, lui, repart de zéro : il ne voit pas la conversation qui a produit le code, seulement le diff et le brief. Cette isolation en fait un relecteur plus critique. Claude Code ne fournit pas d'agent `code-reviewer` intégré : vous le créez en un fichier.

## Ce que le relecteur voit (et ne voit pas)

| Reçu par le subagent | Pas reçu |
| --- | --- |
| Son prompt système (le corps du fichier) | L'historique de votre conversation |
| Le message de délégation rédigé par Claude | Les fichiers déjà lus par la session |
| Vos CLAUDE.md, sauf avec `omitClaudeMd: true` | Les explications et compromis de l'implémentation |
| Un instantané `git status` | Votre style de sortie et la mémoire automatique de la session |

Garder CLAUDE.md est en général souhaitable : le relecteur connaît ainsi vos conventions. Mettez `omitClaudeMd: true` seulement si vous voulez un regard totalement extérieur.

## Le fichier de l'agent

`.claude/agents/code-reviewer.md` :

```markdown
---
name: code-reviewer
description: Relit les changements récents (qualité, sécurité, tests). À utiliser de façon proactive après une modification de code et avant une PR.
tools: Read, Grep, Glob, Bash
model: inherit
memory: project
color: purple
---

Vous êtes un relecteur senior. Vous critiquez, vous ne corrigez pas.

Quand vous êtes invoqué :
1. Lancez `git diff main...HEAD` et `git diff` pour voir les changements.
2. Ne commentez que les fichiers modifiés ; lisez le reste du dépôt seulement si nécessaire.
3. Consultez votre mémoire pour les problèmes récurrents déjà vus.

Vérifiez :
- sécurité : secrets en clair, entrées non validées, contrôle d'accès manquant ;
- exactitude : cas limites, erreurs non gérées ;
- lisibilité : noms, complexité, duplication ;
- tests : le nouveau code est-il couvert ?

Format de sortie :
| Gravité (critique, majeur, mineur) | Fichier:ligne | Problème | Correction suggérée |
Répondez « RAS » si vous ne trouvez rien.

N'éditez aucun fichier, ne committez rien, ne poussez rien.
À la fin, enregistrez dans votre mémoire les motifs récurrents rencontrés.
```

Le champ `memory: project` crée `.claude/agent-memory/code-reviewer/`, versionnable : le relecteur accumule les problèmes typiques de votre projet d'une revue à l'autre.

## Verrouiller les outils

Sans `Edit` ni `Write`, le relecteur ne peut pas « corriger gentiment » un bug qu'il devrait signaler. Il garde `Bash` pour `git diff` et `git log`. Pour lui interdire des commandes précises, n'utilisez pas `disallowedTools: Bash(git push *)`, qui retirerait tout `Bash`. Ajoutez plutôt des règles de refus dans `.claude/settings.json` (elles s'appliquent aussi à la session principale) :

```json
{
  "permissions": {
    "deny": ["Bash(git push *)", "Bash(git commit *)", "Bash(rm *)"]
  }
}
```

Pour un contrôle plus fin, ajoutez dans le frontmatter un hook `PreToolUse` sur `Bash` qui n'autorise que les commandes `git diff`, `git log` et `git show` (sortie en code 2 pour bloquer).

Évitez `isolation: worktree` pour ce relecteur : le worktree part de votre branche par défaut et ne contiendrait pas vos changements non fusionnés.

## L'invoquer

```text
@agent-code-reviewer relisez les changements de la branche courante
```

La @-mention garantit que c'est bien cet agent qui tourne. Vous pouvez aussi ouvrir une session dédiée avec `claude --agent code-reviewer`, ou l'utiliser en CI en mode non interactif :

```bash
claude -p --agent code-reviewer "Relisez le diff de cette branche par rapport à main"
```

## Le flux recommandé

1. Claude termine l'implémentation.
2. Le subagent `code-reviewer` relit le diff et renvoie son tableau.
3. Claude vous présente les observations.
4. **Vous tranchez** : corriger maintenant, ignorer, ouvrir un ticket.
5. Les corrections sont faites par la session principale, puis une nouvelle revue confirme.

Ne laissez pas le relecteur appliquer lui-même ses corrections : vous recréeriez le biais que l'isolation devait éviter.

## Les faux positifs sont normaux

Le relecteur ne sait pas que `legacyParse` est conservé volontairement ou que la refonte est reportée. Triez rapidement ses remarques plutôt que de surcharger son prompt d'exceptions. Pour les exceptions durables, une ligne dans CLAUDE.md ou dans sa mémoire suffit.

## Alternatives intégrées

- `/code-review` : skill intégrée qui relit le diff courant, une PR, une branche ou un chemin. Options utiles : `--max-findings` pour limiter le nombre de remarques, `--fix` pour appliquer les corrections, `--comment` pour commenter la PR.
- `/security-review` : analyse de sécurité du diff entre votre branche et la branche par défaut d'`origin`.
- `/code-review ultra` (alias `/ultrareview`) : revue multi-agents approfondie dans un bac à sable cloud.

Votre agent personnalisé reste utile quand vous voulez imposer vos critères, votre format et une mémoire propre au projet.
