Un subagent est un assistant spécialisé que Claude lance pour une tâche annexe. Il travaille dans sa propre fenêtre de contexte, avec son propre prompt système et ses propres outils, puis ne renvoie qu'un résumé. Vous gardez ainsi une conversation principale courte et lisible, même sur un gros projet.

## Le problème que résout un subagent

Chaque fichier lu, chaque sortie de commande et chaque résultat de recherche reste dans la conversation principale jusqu'au prochain `/clear` ou `/compact`. Si vous demandez « trouvez où sont gérées les routes API dans `app/` », Claude peut lire des dizaines de fichiers dont vous ne voulez que la conclusion.

Avec un subagent, cette lecture se fait ailleurs. La documentation officielle le résume ainsi : utilisez-en un quand une tâche annexe inonderait la conversation de résultats de recherche, de logs ou de contenus de fichiers que vous ne relirez pas.

## Ce que vous gagnez

| Avantage | Concrètement |
| --- | --- |
| Contexte préservé | L'exploration reste dans la fenêtre du subagent ; seul son rapport revient |
| Contraintes | Le champ `tools` limite ce que le subagent peut faire (lecture seule, pas de `Bash`, etc.) |
| Réutilisation | Un fichier dans `~/.claude/agents/` sert dans tous vos projets |
| Spécialisation | Un prompt système dédié à un domaine (revue, tests, SQL) |
| Coût | Vous pouvez router une tâche simple vers `haiku` avec `model: haiku` |

## Ce qui a changé en 2026

Plusieurs comportements récents modifient la façon de travailler :

- **Arrière-plan par défaut** : en session interactive, le « fork mode » est actif et Claude Code lance les subagents en arrière-plan. Vous continuez à écrire pendant qu'ils travaillent ; leurs demandes de permission remontent dans votre session principale.
- **Forks** : `/subtask <tâche>` lance un subagent qui hérite de toute la conversation, utile quand un subagent classique demanderait trop d'explications.
- **Imbrication** : un subagent peut lancer ses propres subagents, jusqu'à trois niveaux sous la conversation principale par défaut.
- **Concurrence** : 20 subagents au maximum en même temps par défaut.
- **Isolation Git** : `isolation: worktree` donne au subagent une copie isolée du dépôt.

## Cas d'usage typiques

- **Découvrir un dépôt inconnu** : Claude délègue la cartographie à l'agent intégré Explore.
- **Lancer la suite de tests** : « Utilisez un subagent pour lancer les tests et ne me rapporter que les échecs avec leur message d'erreur ».
- **Recherches parallèles** : authentification, base de données et API étudiées par trois subagents distincts.
- **Revue de code** : un `code-reviewer` en lecture seule relit le diff sans connaître vos compromis.
- **Enchaînement** : un subagent trouve les problèmes de performance, un second les corrige.

```text
Utilisez des subagents séparés pour étudier en parallèle
les modules d'authentification, de base de données et d'API.
```

## Quand rester dans la conversation principale

La documentation recommande la conversation principale quand :

- la tâche demande des allers-retours fréquents avec vous ;
- plusieurs phases partagent beaucoup de contexte (plan, implémentation, tests) ;
- il s'agit d'une petite modification ciblée ;
- la latence compte : un subagent (hors fork) repart de zéro et doit d'abord rassembler son contexte.

Pour une simple question sur ce qui est déjà dans la conversation, `/btw` est plus adapté : il voit tout votre contexte, sans outils, et sa réponse n'entre pas dans l'historique.

## Limites à connaître

- Un subagent classique ne voit pas votre conversation. Il reçoit le message de délégation que Claude rédige, son prompt système, vos fichiers CLAUDE.md (sauf Explore et Plan) et un instantané `git status`.
- Il consomme ses propres tokens, décomptés sur les mêmes limites d'usage que votre session.
- Les rapports de nombreux subagents finissent tous dans la conversation principale : dix rapports détaillés pèsent lourd.
- Pour des dizaines ou centaines d'agents, préférez les [dynamic workflows](/wiki/cli/dynamic-workflows-agents-arriere-plan).
