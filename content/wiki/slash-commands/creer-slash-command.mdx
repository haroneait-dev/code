Une commande personnalisée est un simple fichier Markdown : pas de SDK, pas de build. Depuis 2026, les commandes personnalisées ont été fusionnées dans les skills. Un fichier `.claude/commands/deploy.md` et un skill `.claude/skills/deploy/SKILL.md` créent tous les deux `/deploy` et se comportent de la même façon. Vos anciens fichiers continuent de fonctionner, mais le format skill est recommandé pour tout nouveau travail.

## Deux formats, un même résultat

| | `.claude/commands/` (ancien) | `.claude/skills/` (recommandé) |
| --- | --- | --- |
| Fichier | `deploy.md` | `deploy/SKILL.md` |
| Fichiers annexes (scripts, exemples) | Non | Oui, dans le dossier |
| Champ `name`, champ `paths` | Non | Oui |
| Prise en compte des modifications en cours de session | Non | Oui |
| Exécution dans un sous-agent (`context: fork`) | Non | Oui |

Le format skill ajoute surtout la possibilité que Claude charge la commande de lui-même quand elle est pertinente. Si vous voulez qu'elle ne parte que sur votre demande, ajoutez `disable-model-invocation: true`.

## Où placer le fichier

| Emplacement | Chemin | Portée |
| --- | --- | --- |
| Personnel | `~/.claude/skills/<nom>/SKILL.md` | Tous vos projets sur cette machine |
| Projet | `.claude/skills/<nom>/SKILL.md` | Ce dépôt, partagé via git |
| Sous-dossier | `<sous-dossier>/.claude/skills/<nom>/SKILL.md` | Sessions dans ce sous-dossier (monorepo) |
| Plugin | `<plugin>/skills/<nom>/SKILL.md` | Partout où le plugin est activé, sous `/plugin:nom` |
| Entreprise | Dossier des réglages gérés | Tous les postes de l'organisation |

En cas de conflit de nom, l'ordre de priorité est : entreprise, puis personnel, puis projet. Attention, c'est l'inverse de l'intuition : un skill personnel `deploy` masque le `deploy` du projet. Les skills de plugin ne créent pas de conflit, ils sont toujours préfixés.

L'ancien format suit la même logique : `.claude/commands/` pour le projet, `~/.claude/commands/` pour vous.

## Le minimum

`.claude/skills/tests/SKILL.md` :

```md
---
description: Lance les tests unitaires et résume les résultats
disable-model-invocation: true
---

Exécutez `npm test` puis résumez :
- le nombre de tests réussis et échoués ;
- la durée totale ;
- les fichiers en échec, avec la première erreur de chacun.
```

Tapez `/tests` : le contenu du fichier devient le prompt envoyé à Claude. Le nom vient du dossier (`tests`), ou du champ `name` s'il est présent. Sans `description`, Claude Code prend la première ligne non vide du contenu.

## Un exemple complet : préparer une release

`.claude/skills/release/SKILL.md` :

```md
---
description: Prépare une release (changelog, version), sans pousser
argument-hint: <patch|minor|major>
disable-model-invocation: true
allowed-tools: Read Edit Bash(git describe *) Bash(git log *) Bash(npm version *)
---

Préparez une release de type `$ARGUMENTS`.

Dernier tag : !`git describe --tags --abbrev=0`

1. Listez les commits depuis ce tag avec `git log <tag>..HEAD --oneline`.
2. Ajoutez en tête de CHANGELOG.md une section classée en feat, fix et chore.
3. Lancez `npm version $ARGUMENTS --no-git-tag-version`.
4. Affichez un résumé. Ne créez pas de tag et ne poussez rien : je le ferai moi-même.
```

Ce que fait chaque ligne :

- `argument-hint` s'affiche dans l'autocomplétion ;
- `disable-model-invocation: true` garantit que Claude ne lancera pas une release de lui-même ;
- `allowed-tools` pré-autorise ces outils pendant le tour où la commande est invoquée, pour éviter les demandes de confirmation. Il ne bloque pas les autres outils : vos règles de permission habituelles s'appliquent ;
- `` !`git describe …` `` exécute la commande avant l'envoi à Claude et insère sa sortie dans le prompt (voir [Bash injection](/wiki/slash-commands/bash-injection-securisee)). Si le dépôt n'a encore aucun tag, la commande échoue et toute l'invocation est annulée : pensez-y sur un projet neuf.

Usage :

```text
> /release minor
```

## Tester et dépanner

Après avoir créé le fichier, tapez `/` et cherchez votre commande. Si elle n'apparaît pas :

1. **Vérifiez le chemin** : un skill doit être dans son propre dossier (`skills/release/SKILL.md`), pas directement dans `skills/`.
2. **Nouveau dossier racine** : si `.claude/skills/` n'existait pas au démarrage de la session, lancez `/reload-skills` pour qu'il soit surveillé.
3. **Ancien format** : les fichiers de `.claude/commands/` ne sont pas surveillés ; lancez `/reload-skills` après une modification.
4. **Frontmatter** : les noms de champs sont sensibles à la casse (`disable-model-invocation`, pas `disableModelInvocation`) et un champ inconnu est ignoré sans erreur.
5. **Nom réservé** : `anthropic-skills` et un dossier nommé `synced` sont réservés.
6. **Conflit** : un skill personnel du même nom prend le pas sur celui du projet.

`/skills` liste tous les skills chargés et leur coût en tokens (touche `t` pour trier). `/skill-doctor` montre ceux qui coûtent du contexte sans servir.

## Partager avec l'équipe

Commitez le dossier `.claude/skills/` : vos collègues récupèrent les commandes au prochain `git pull`. Documentez-les en une ligne chacune dans votre `CLAUDE.md` ou dans un README. Pour partager entre plusieurs dépôts, passez par un plugin : voir [Partager les commandes en équipe](/wiki/slash-commands/partage-equipe).
