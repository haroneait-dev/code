Un hook ne peut pas « taper » une commande `/nom` dans votre session à votre place. En revanche, hooks et commandes personnalisées (skills) se combinent de quatre façons utiles : intercepter une commande au moment où vous la tapez, embarquer des hooks dans un skill, demander à Claude de lancer un skill, ou exécuter un skill dans une session séparée avec `claude -p`. Cet article présente chaque approche et ses pièges.

## Rappel : le format d'un hook

Les hooks se déclarent dans `settings.json` (`~/.claude/settings.json`, `.claude/settings.json` ou `.claude/settings.local.json`). Le format a trois niveaux : l'événement, un groupe avec un `matcher` facultatif, puis une liste de handlers qui ont chacun un `type`.

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/format.sh" }
        ]
      }
    ]
  }
}
```

Une erreur fréquente dans les anciens tutoriels : mettre `"command"` directement sous l'événement, sans le tableau `hooks` ni le champ `type`. Ce format n'est pas reconnu.

Autre confusion courante : `Stop` se déclenche à la fin de **chaque réponse** de Claude, pas à la fermeture de la session. Pour la fin de session, l'événement est `SessionEnd`.

| Événement | Quand | Utile ici pour |
| --- | --- | --- |
| `UserPromptExpansion` | Quand une commande `/nom` tapée se transforme en prompt | Bloquer ou enrichir une commande précise |
| `UserPromptSubmit` | À chaque prompt envoyé | Ajouter du contexte à tous les prompts |
| `PostToolUse` | Après un appel d'outil réussi | Réagir à un `git commit` |
| `Stop` | Quand Claude a fini de répondre | Demander à Claude de continuer |
| `SessionStart` / `SessionEnd` | Début / fin de session | Contexte initial, nettoyage |

La liste complète des événements est dans [Le cycle de vie des hooks](/wiki/hooks/hook-lifecycle).

## 1. Intercepter une commande avec `UserPromptExpansion`

`UserPromptExpansion` se déclenche quand une commande que vous tapez (skill, commande de `.claude/commands/` ou prompt MCP) est développée en prompt, avant d'arriver à Claude. Le `matcher` porte sur le nom de la commande. C'est le seul moyen de filtrer un `/nom` tapé directement : un hook `PreToolUse` sur l'outil `Skill` ne voit que les invocations faites par Claude.

Exemple : bloquer `/deploy` tant qu'un fichier d'approbation n'existe pas.

```json
{
  "hooks": {
    "UserPromptExpansion": [
      {
        "matcher": "deploy",
        "hooks": [
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/check-deploy.sh" }
        ]
      }
    ]
  }
}
```

`.claude/hooks/check-deploy.sh` :

```bash
#!/bin/bash
if [ ! -f "$CLAUDE_PROJECT_DIR/.deploy-approved" ]; then
  echo "Déploiement non approuvé : créez .deploy-approved d'abord." >&2
  exit 2
fi
exit 0
```

Le code de sortie 2 bloque l'expansion et affiche le message d'erreur. Le hook reçoit aussi sur stdin un JSON avec `command_name`, `command_args` et `command_source`, que vous pouvez lire avec `jq`.

Pour enrichir au lieu de bloquer, renvoyez du contexte supplémentaire, par exemple la checklist de revue de l'équipe :

```bash
#!/bin/bash
jq -n --rawfile checklist "$CLAUDE_PROJECT_DIR/docs/checklist-revue.md" '{
  hookSpecificOutput: {
    hookEventName: "UserPromptExpansion",
    additionalContext: $checklist
  }
}'
```

## 2. Embarquer des hooks dans un skill

Un skill peut déclarer ses propres hooks dans son frontmatter. Ils s'activent quand le skill est invoqué et restent actifs jusqu'à la fin de la session. Avec `once: true`, un hook est retiré après sa première exécution réussie.

`.claude/skills/migration-db/SKILL.md` :

```md
---
description: Écrit une migration Supabase et vérifie le SQL avant chaque commande
disable-model-invocation: true
hooks:
  PreToolUse:
    - matcher: "Bash"
      hooks:
        - type: command
          command: "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/refuser-drop.sh"
---

Créez une migration pour : $ARGUMENTS
Activez RLS sur toute nouvelle table.
```

C'est la bonne approche quand une règle doit être appliquée à chaque fois pendant le travail du skill, et pas seulement « suggérée » dans le texte. Voir [Le frontmatter en détail](/wiki/slash-commands/markdown-frontmatter).

## 3. Demander à Claude de lancer un skill

Un hook `Stop` peut empêcher Claude de s'arrêter et lui donner une consigne. Si le skill est invocable par Claude (pas de `disable-model-invocation: true`), Claude peut alors l'appeler lui-même.

```bash
#!/bin/bash
# .claude/hooks/rappel-changelog.sh, branché sur Stop
input=$(cat)
# Évite de relancer Claude en boucle
if [ "$(echo "$input" | jq -r '.stop_hook_active')" = "true" ]; then
  exit 0
fi
if git diff --name-only | grep -q '^src/' && ! git diff --name-only | grep -q 'CHANGELOG.md'; then
  jq -n '{hookSpecificOutput: {hookEventName: "Stop",
    additionalContext: "Du code a changé dans src/ sans entrée de changelog. Invoquez le skill changelog avant de terminer."}}'
fi
exit 0
```

Vérifiez toujours `stop_hook_active` : il vaut `true` quand Claude continue déjà à cause d'un hook `Stop`. Claude Code plafonne de toute façon à 8 relances consécutives.

## 4. Exécuter un skill dans une session séparée avec `claude -p`

En mode non interactif, les skills et commandes personnalisées fonctionnent : `claude -p "/nom arguments"` développe la commande puis l'exécute. Un hook peut donc lancer une seconde session, indépendante de la vôtre.

Exemple : une revue en arrière-plan après chaque `git commit` lancé par Claude.

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "if": "Bash(git commit *)",
            "async": true,
            "command": "claude -p '/revue-commit' --settings '{\"disableAllHooks\": true}' > \"$CLAUDE_PROJECT_DIR\"/.claude/derniere-revue.md 2>&1"
          }
        ]
      }
    ]
  }
}
```

Ce qui compte ici :

- **`if`** filtre sur la commande Bash elle-même, sans avoir à parser le JSON avec `jq` ;
- **`async: true`** lance le hook en arrière-plan : Claude continue de travailler. La sortie du hook lui est transmise au tour suivant ;
- **`--settings '{"disableAllHooks": true}'`** coupe les hooks dans la session enfant. Sans cela, la session `claude -p` charge les mêmes hooks de projet et peut se relancer elle-même ;
- **`/revue-commit`** est un skill du projet. Évitez `--bare` ici : ce mode ne charge ni les skills ni les commandes personnalisées.

### Le cas `SessionEnd`

Les hooks `SessionEnd` disposent par défaut de 1,5 seconde au total. Une revue ne tiendra jamais dans ce délai : lancez un processus complètement détaché.

```bash
nohup claude -p '/journal-decisions' --settings '{"disableAllHooks": true}' \
  > .claude/journal.log 2>&1 &
```

Attention : la session enfant ne voit pas votre conversation. Un skill qui dit « résumez la dernière décision prise dans cette conversation » ne fonctionnera pas. Donnez-lui une source qu'elle peut lire (le `git log`, un fichier de notes) ou passez le chemin du transcript, présent dans le JSON reçu par le hook (`transcript_path`).

## Pièges à connaître

1. **Coût** : chaque `claude -p` est une session complète, facturée en plus de la vôtre. Ne branchez jamais un `claude -p` sur un `PostToolUse` sans filtre `if` ou `matcher`.
2. **Permissions** : la session enfant applique ses propres règles. En `-p`, aucune demande de confirmation n'est possible. Pré-autorisez les outils nécessaires avec `--allowedTools` ou avec `allowed-tools` dans le skill.
3. **Sortie de `SessionStart`** : ce qu'un hook `SessionStart` écrit sur stdout part dans le contexte de Claude, pas dans votre terminal. Pour des rappels destinés à Claude, c'est parfait ; pour vous, utilisez plutôt `CLAUDE.md` ou la ligne de statut.
4. **Délais** : le délai par défaut d'un hook `command` est de 600 secondes, mais 30 secondes sur `UserPromptSubmit`. Un hook bloquant trop long fige la session.
5. **Mode `-p` du parent** : si votre session principale tourne elle-même en `-p`, les hooks `async` encore actifs à la fin sont tués. Détachez le processus s'il doit survivre.

Pour vérifier ce qui est configuré, `/hooks` ouvre la liste des hooks actifs et leur origine. Pour générer la configuration sans éditer le JSON à la main, le skill intégré `/update-config` modifie le bon fichier `settings.json` à partir d'une description.
