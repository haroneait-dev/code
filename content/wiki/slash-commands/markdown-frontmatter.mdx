Le bloc YAML en tête d'une commande personnalisée décide de ce qu'affiche le menu `/`, de qui peut la déclencher, des outils pré-autorisés et du modèle utilisé. Les mêmes champs valent pour un skill (`.claude/skills/<nom>/SKILL.md`) et pour l'ancien format (`.claude/commands/<nom>.md`), sauf `name` et `paths`, réservés aux skills. Cet article se concentre sur l'usage en commande ; la référence complète est dans [Frontmatter de SKILL.md](/wiki/skills/skill-md-frontmatter).

## Un exemple complet

`.claude/skills/revue-pr/SKILL.md` :

```md
---
description: Revue approfondie d'une pull request GitHub
argument-hint: <numéro de PR>
disable-model-invocation: true
allowed-tools: Read Grep Bash(gh pr diff *) Bash(gh pr view *)
model: opus
effort: high
---

Faites la revue de la PR #$ARGUMENTS.

1. Vérifiez que l'argument est un nombre, sinon arrêtez-vous.
2. Récupérez le diff avec `gh pr diff <numéro>` et le contexte avec `gh pr view <numéro>`.
3. Évaluez : correction (bugs, cas limites), sécurité (entrées non validées, secrets), tests manquants.

Rendez un rapport classé par gravité. Ne publiez aucun commentaire sur la PR.
```

Le diff est récupéré par Claude via l'outil Bash, pas par une injection `` !`…` `` : l'argument tapé n'est donc jamais exécuté tel quel dans un shell (voir [Bash injection](/wiki/slash-commands/bash-injection-securisee)). Les deux règles `Bash(gh pr …)` évitent les demandes de confirmation.

## Les champs, un par un

| Champ | Effet | Valeur par défaut |
| --- | --- | --- |
| `description` | Texte du menu `/` ; sert à Claude pour décider de charger le skill | Première ligne non vide du contenu |
| `argument-hint` | Indice affiché dans l'autocomplétion | Aucun |
| `arguments` | Noms des arguments positionnels (`$composant`, `$cible`) | Aucun |
| `disable-model-invocation` | `true` : seul vous pouvez lancer la commande | `false` |
| `user-invocable` | `false` : la commande disparaît du menu `/`, seul Claude l'utilise | `true` |
| `allowed-tools` | Outils pré-autorisés pendant le tour de l'invocation | Aucun |
| `disallowed-tools` | Outils retirés tant que la commande est active | Aucun |
| `model` | Modèle pour le reste du tour | Modèle de la session |
| `effort` | Niveau d'effort (`low` à `max`) | Celui de la session |
| `context` | `fork` : exécution dans un sous-agent isolé | Contexte principal |
| `agent` | Type de sous-agent avec `context: fork` | `general-purpose` |
| `hooks` | Hooks activés à l'invocation, jusqu'à la fin de la session | Aucun |
| `shell` | `bash` ou `powershell` pour les blocs `` !`…` `` | `bash` |
| `name`, `paths` | Nom de commande, activation par motif de fichiers (skills seulement) | Nom du dossier |

### `description`

Écrivez ce que fait la commande du point de vue de l'utilisateur, avec les mots qu'il emploierait. Placez l'usage principal en premier : la description et `when_to_use` réunis sont tronqués à 1 536 caractères dans la liste des skills.

- Bonne : `Revue approfondie d'une pull request GitHub`
- Mauvaise : `Lance gh pr diff puis appelle l'API` (décrit l'implémentation, pas le besoin)

### `argument-hint`

Suivez les conventions Unix : `<obligatoire>`, `[optionnel]`, `a|b|c` pour un choix.

```yaml
argument-hint: <numéro de PR>
argument-hint: "[fichier]"
argument-hint: <patch|minor|major>
```

Mettez entre guillemets une valeur qui commence par `[` ou `{` : sinon YAML la lit comme une liste ou un objet.

### `allowed-tools` : une autorisation, pas une restriction

C'est le champ le plus mal compris. Il **pré-autorise** les outils listés : Claude peut les utiliser sans vous demander confirmation, pendant le tour où la commande est invoquée. L'autorisation disparaît dès votre message suivant.

Il ne **restreint rien** : tous les autres outils restent disponibles et suivent vos règles de permission habituelles. Une commande avec `allowed-tools: Read Grep` peut toujours modifier un fichier si vous l'acceptez dans la demande de confirmation (ou si le mode `auto` l'accepte).

Syntaxe : liste séparée par des espaces ou des virgules, ou liste YAML. Les motifs suivent les règles de permission :

```yaml
allowed-tools: Read Grep Glob Bash(git log *) Bash(npm test *)
```

- `Bash(git log *)` couvre `git log` suivi de n'importe quoi. L'ancienne forme `Bash(git log:*)` est équivalente.
- Pour les fichiers, seuls les motifs `Edit(...)` et `Read(...)` sont vérifiés. `Write(tests/**)` est accepté mais jamais consulté : écrivez `Edit(tests/**)`.

### `disallowed-tools` : la vraie restriction

Pour empêcher une commande d'utiliser un outil, listez-le ici. L'outil est retiré tant que la commande est active, jusqu'à votre message suivant.

```yaml
disallowed-tools: Edit Write Bash
```

Pour une interdiction permanente, utilisez plutôt des règles `deny` dans `settings.json` : voir [Permissions et MCP](/wiki/slash-commands/mcp-permissions).

### `model` et `effort`

`model` accepte les mêmes valeurs que `/model` : un alias (`opus`, `sonnet`, `haiku`), un identifiant complet (`claude-opus-5-5`) ou `inherit`. Le changement vaut pour le reste du tour et n'est pas enregistré : la session reprend son modèle au prompt suivant.

```yaml
model: haiku     # tâche mécanique : rapide et peu coûteux
model: opus      # revue critique
effort: high     # raisonnement plus poussé sur cette commande
```

Un modèle exclu par la liste `availableModels` de votre organisation est ignoré sans erreur. Avec `context: fork`, `model` choisit le modèle du sous-agent.

### `disable-model-invocation` et `user-invocable`

| Frontmatter | Vous pouvez lancer | Claude peut lancer |
| --- | --- | --- |
| (rien) | Oui | Oui |
| `disable-model-invocation: true` | Oui | Non |
| `user-invocable: false` | Non | Oui |

Mettez `disable-model-invocation: true` sur toute commande avec effets de bord (déploiement, commit, envoi de message). Bonus : sa description ne charge plus le contexte de Claude.

### `context: fork`

La commande s'exécute dans un sous-agent qui ne voit pas votre conversation, en arrière-plan par défaut (`background: false` pour attendre son résultat). Réservez-le aux commandes qui contiennent une tâche complète. Voir [Skills et commandes](/wiki/slash-commands/skills-vs-slash).

## Patterns recommandés

**Lecture seule, sans confirmation** :

```yaml
---
description: Liste les TODO et FIXME du code
allowed-tools: Read Grep Glob
disallowed-tools: Edit Write
model: haiku
---
```

**Génération limitée aux tests** :

```yaml
---
description: Génère des tests unitaires pour un fichier
argument-hint: <fichier>
allowed-tools: Read Edit(tests/**) Bash(npm test *)
---
```

Ici, seules les écritures dans `tests/` passent sans confirmation. Une écriture ailleurs déclenche la demande habituelle.

## Erreurs fréquentes

- **Le `---` n'est pas en première ligne** : tout le fichier, marqueurs compris, est traité comme du contenu.
- **YAML invalide** : la commande reste disponible mais sans aucun champ (ni description, ni outils). Lancez `claude --debug` pour voir l'erreur, ou `claude plugin validate .claude/skills`.
- **Nom de champ mal écrit** : `allowedTools`, `disableModelInvocation` ou un champ inventé (`temperature`, `pre-prompt`) sont ignorés sans avertissement.
- **Croire qu'`allowed-tools` protège** : il ouvre des droits, il n'en ferme aucun.
- **Forcer `opus` partout** : réservez-le aux commandes où la qualité du raisonnement change le résultat.

Les valeurs booléennes acceptent `true`/`false`, mais aussi `yes`, `no`, `on`, `off`, `1` et `0`.
