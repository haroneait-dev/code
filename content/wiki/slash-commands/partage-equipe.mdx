Une commande utile devient vraiment rentable quand toute l'équipe s'en sert. Le chemin le plus simple est de commiter vos skills dans le dépôt : un `git pull` suffit pour que vos collègues les reçoivent. Pour partager un catalogue entre plusieurs dépôts, la solution officielle est un plugin publié dans une marketplace privée, que le projet peut activer automatiquement.

## Choisir le bon canal

| Besoin | Canal | Ce que voit l'utilisateur |
| --- | --- | --- |
| Commandes propres à un dépôt | `.claude/skills/` commité | `/deploy` |
| Catalogue commun à plusieurs dépôts | Plugin dans une marketplace privée | `/outils-equipe:deploy` |
| Commandes imposées à toute l'organisation | Skills gérés (managed settings) | `/deploy`, prioritaire sur tout |
| Commandes personnelles | `~/.claude/skills/` | `/deploy`, sur votre machine seulement |
| Cowork et sessions cloud | Skills activés sur le compte claude.ai | `/deploy` |

## 1. Dans le dépôt : `.claude/skills/` versionné

Les skills du projet sont faits pour être commités :

```bash
git add .claude/skills/
git commit -m "chore: ajoute les commandes /db-migrate et /revue-pr"
git push
```

Au prochain `git pull`, vos collègues ont les commandes, sans installation. Elles sont aussi chargées dans les sessions cloud, qui clonent le dépôt. L'ancien format `.claude/commands/` fonctionne de la même façon.

Structure type pour un dépôt avec une dizaine de commandes :

```text
.claude/
  skills/
    db-migrate/
      SKILL.md
      templates/table.sql      # fichier annexe lu à la demande
    revue-pr/
      SKILL.md
      checklist.md
    release/
      SKILL.md
      scripts/changelog.sh     # appelé via ${CLAUDE_SKILL_DIR}
  settings.json                # réglages partagés : permissions, hooks, plugins
```

Dans un monorepo, un skill placé dans `apps/web/.claude/skills/` est chargé dès que Claude travaille dans `apps/web/`.

### Ce qu'il ne faut pas commiter

- `.claude/settings.local.json` : vos réglages personnels. Claude Code l'ajoute au `.gitignore` quand il y écrit, vérifiez quand même.
- Les fichiers produits par vos hooks ou scripts (rapports, journaux).
- Tout secret : un skill est du texte lisible par tous. Voir [Secrets et skills](/wiki/skills/secrets-skills).

```gitignore
.claude/settings.local.json
.claude/*.log
.claude/rapports/
```

Les transcripts de session ne sont pas dans le dépôt : ils sont stockés dans `~/.claude/`.

## 2. Entre plusieurs dépôts : un plugin dans une marketplace privée

Les sous-modules git et les scripts de copie fonctionnent, mais un plugin est la solution prévue pour cet usage : versionné, mis à jour, activable par projet.

**Étape 1 : un dépôt de plugins.** Un dépôt `macorp/claude-plugins` contient le plugin et le fichier de marketplace :

```text
claude-plugins/
  .claude-plugin/
    marketplace.json
  outils-equipe/
    .claude-plugin/plugin.json
    skills/
      deploy/SKILL.md
      revue-pr/SKILL.md
```

`.claude-plugin/marketplace.json` :

```json
{
  "name": "macorp",
  "owner": { "name": "Équipe plateforme" },
  "plugins": [
    { "name": "outils-equipe", "source": "./outils-equipe" }
  ]
}
```

Vérifiez avant de pousser avec `claude plugin validate .`. Si le dépôt est privé, la marketplace l'est aussi : seuls ceux qui peuvent cloner le dépôt peuvent installer.

**Étape 2 : l'activer dans chaque projet.** Dans le `.claude/settings.json` commité du projet :

```json
{
  "extraKnownMarketplaces": {
    "macorp": {
      "source": { "source": "github", "repo": "macorp/claude-plugins" }
    }
  },
  "enabledPlugins": {
    "outils-equipe@macorp": true
  }
}
```

À l'ouverture du dépôt, après acceptation de la boîte de dialogue de confiance, Claude Code enregistre la marketplace et propose le plugin. Ces entrées sont ignorées dans un dossier non approuvé, en `claude -p` comme dans les sessions cloud.

Pour une installation manuelle :

```bash
claude plugin marketplace add macorp/claude-plugins
claude plugin install outils-equipe@macorp
```

Les skills d'un plugin sont toujours préfixés (`/outils-equipe:deploy`) : ils n'entrent jamais en conflit avec les skills du projet. Pour publier une nouvelle version, voir [Créer un plugin](/wiki/plugins/creer-plugin).

## 3. Pour toute l'organisation : skills gérés

Un administrateur peut déployer des skills dans le dossier `.claude/skills/` du répertoire des réglages gérés (par exemple `/etc/claude-code/` sous Linux). Ils sont chargés sur tous les postes concernés et passent avant les skills personnels et ceux des projets en cas de nom identique.

Les réglages gérés permettent aussi de pré-enregistrer la marketplace interne (`extraKnownMarketplaces`) et d'interdire les autres (`strictKnownMarketplaces`). Voir [settings.json](/wiki/cli/settings-json).

Pour Cowork et les sessions cloud, qui ne lisent pas `~/.claude/skills/`, l'organisation peut aussi fournir des skills via claude.ai : ils sont synchronisés dans les sessions des membres connectés avec leur compte.

## Conventions de nommage

Mettez-vous d'accord une fois et documentez la règle :

- **Préfixe de domaine** : `db-migrate`, `db-seed`, `pr-revue`, `pr-resume`. Taper `/db` filtre tout le domaine.
- **Verbe d'abord** : `creer-composant`, `lancer-tests`. Plus naturel à l'oral.
- **Évitez les noms des commandes intégrées** (`review`, `usage`, `init`) : votre skill remplacerait la commande intégrée pour toute l'équipe.

Le nom réservé `anthropic-skills` et un dossier nommé `synced` ne sont pas chargés.

## Documenter le catalogue

Le menu `/` affiche déjà la `description` et l'`argument-hint` de chaque commande : soignez-les, c'est la première documentation. Ajoutez une courte section dans `CLAUDE.md` :

```md
## Commandes du projet
- `/db-migrate <nom>` : crée une migration Supabase avec RLS
- `/revue-pr <numéro>` : revue d'une PR selon notre checklist
- `/release <patch|minor|major>` : changelog et version, sans push

Règles : toute commande à effets de bord a `disable-model-invocation: true`.
```

Pour un nouvel arrivant, `/team-onboarding` génère un guide de prise en main à partir de votre usage de Claude Code sur les 30 derniers jours.

## Qualité des commandes partagées

Une commande partagée mérite le soin d'une bibliothèque interne :

- [ ] `description` claire, formulée du point de vue de l'utilisateur
- [ ] `argument-hint` présent dès qu'il y a un argument
- [ ] `disable-model-invocation: true` sur toute action avec effets de bord
- [ ] `allowed-tools` précis (jamais `Bash` seul), et rappelez-vous qu'il pré-autorise sans rien interdire
- [ ] Aucun argument dans un bloc `` !`…` `` (voir [Bash injection](/wiki/slash-commands/bash-injection-securisee))
- [ ] Un mode `--dry-run` ou une confirmation avant toute action irréversible
- [ ] Testée dans une session neuve, sans le contexte qui a servi à l'écrire

Pour mesurer qu'une commande fait bien ce qu'on attend, `claude plugin eval` (pour un plugin) ou le plugin `skill-creator` comparent les résultats avec et sans le skill. Voir [Tester un skill](/wiki/skills/tester-skill).

## Sécurité : relire avant de lancer

Les `allowed-tools` et les hooks d'un skill de projet s'appliquent même dans un dossier que vous n'avez pas encore approuvé, y compris en `claude -p`. Dans un dépôt que vous ne connaissez pas, lisez `.claude/skills/` et `.claude/settings.json` avant de lancer Claude Code. Pour une exécution sans rien charger du dépôt, utilisez `claude --bare`.

## Cycle de vie d'une commande

1. Un développeur repère une procédure répétée.
2. Il crée le skill sur une branche dédiée et met à jour la section de `CLAUDE.md`.
3. Pull request avec un exemple d'utilisation dans la description.
4. Revue : utilité, sécurité (`allowed-tools`, blocs `!`), nommage.
5. Fusion : toute l'équipe l'a au prochain `git pull`.
6. Commande inutilisée : `/skill-doctor` aide à la repérer, supprimez-la et notez-le dans le changelog.
