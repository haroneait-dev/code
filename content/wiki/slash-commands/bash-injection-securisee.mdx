Une commande personnalisée qui reçoit des arguments et touche au shell pose la question classique de l'injection de commandes. Claude Code a plusieurs garde-fous, mais leur portée est souvent mal comprise : `allowed-tools` n'interdit rien, et les blocs `` !`…` `` s'exécutent sans demande de confirmation. Cet article distingue ce qui part réellement dans un shell et donne les règles pour écrire des commandes sûres.

## Deux chemins vers le shell

Dans une commande (skill ou fichier `.claude/commands/`), il existe deux façons très différentes d'exécuter du shell.

| | Instruction dans le texte | Injection `` !`…` `` |
| --- | --- | --- |
| Exemple | ``Lancez `npm test` `` | `` !`git diff HEAD` `` |
| Qui exécute | Claude, via l'outil Bash | Claude Code, avant que Claude lise le skill |
| Quand | Pendant la réponse | Au moment de l'invocation |
| Demande de confirmation | Oui, selon vos règles et votre mode | Jamais : autorisé ou invocation annulée |
| Claude peut refuser | Oui | Non, Claude ne voit que la sortie |

### Chemin 1 : le texte du prompt

`$ARGUMENTS`, `$0`, `$1` sont remplacés dans le **texte envoyé à Claude**, pas dans un shell. Si vous tapez `/grep-todo "fichier.txt; rm -rf ~"`, Claude lit cette chaîne. C'est lui qui décide ensuite d'appeler l'outil Bash, et cet appel passe par le système de permissions comme n'importe quel autre.

C'est une barrière réelle, mais pas une garantie : un modèle peut être trompé, notamment par du contenu lu dans un fichier ou une page web (injection de prompt).

### Chemin 2 : l'injection dynamique

Une ligne `` !`commande` `` (ou un bloc de code ouvert par ` ```! `) est exécutée par Claude Code **avant** l'envoi du skill à Claude. La sortie remplace la ligne.

```md
---
description: Résume les changements non commités
---

## Changements
!`git diff HEAD`

Résumez ces changements en trois points.
```

Ce mécanisme ne demande jamais de confirmation. Chaque commande injectée est vérifiée contre vos règles de permission :

- une règle `deny` correspondante annule toute l'invocation ;
- hors mode `auto`, une commande qui n'est pas explicitement autorisée (par vos règles ou par `allowed-tools`) annule aussi l'invocation ;
- en mode `auto`, le skill se charge avec une consigne demandant à Claude d'exécuter la commande lui-même, et cet appel passe par le classifieur.

## Règle n° 1 : jamais d'argument dans un bloc `!`

La documentation ne garantit pas que les arguments soient tenus à l'écart des commandes injectées. Ne prenez pas le risque : n'écrivez jamais ceci.

```md
<!-- À NE PAS FAIRE -->
Contenu du fichier : !`cat $ARGUMENTS`
```

Faites lire le fichier à Claude, qui passera par l'outil Read et ses permissions :

```md
Lisez le fichier $ARGUMENTS avec l'outil Read.
Refusez s'il est hors du projet (chemin absolu ou contenant `..`).
```

Les blocs `!` doivent contenir des commandes fixes, en lecture seule : `git status --short`, `git log --oneline -10`, `node --version`. Pour appeler un script livré avec le skill, utilisez `${CLAUDE_SKILL_DIR}`, qui pointe toujours vers le dossier du skill.

## Règle n° 2 : `allowed-tools` ouvre, il ne ferme pas

`allowed-tools` **pré-autorise** des outils pendant le tour de l'invocation. Il ne bloque aucun autre outil.

```yaml
allowed-tools: Bash(grep *)
```

Avec cette ligne, `grep` passe sans confirmation. Un `rm` reste possible : il déclenche simplement la demande de confirmation habituelle (ou l'évaluation du classifieur en mode `auto`). Pour interdire, utilisez :

- **`disallowed-tools`** dans le frontmatter, qui retire des outils tant que la commande est active ;
- **des règles `deny`** dans `settings.json`, qui s'appliquent partout et l'emportent sur toute autorisation.

```json
{
  "permissions": {
    "deny": ["Bash(rm -rf *)", "Bash(git push --force *)", "Bash(curl *)"]
  }
}
```

Une règle `deny` correspond à la commande telle qu'elle est écrite. Pour une protection qui ne dépend pas du texte de la commande, activez le [sandbox](/wiki/demarrer/permissions-sandbox) avec `/sandbox`.

Point à surveiller : `allowed-tools` d'un skill de projet s'applique même dans un dossier que vous n'avez jamais approuvé, y compris en `claude -p`. Relisez les `allowed-tools` des skills d'un dépôt cloné avant d'y lancer Claude Code.

## Ce que Claude Code fait pour vous

- **Commandes non analysables** : en mode par défaut, Claude Code demande confirmation pour une commande Bash qu'il ne sait pas décomposer entièrement, même si une règle comme `Bash(git *)` en autorise une partie.
- **Commandes réseau** : `curl` et `wget` ne sont jamais auto-approuvés par défaut.
- **Sous-commandes** : une règle `Bash(npm test *)` ne couvre pas `npm test && rm -rf build` : chaque partie est vérifiée.
- **Skills synchronisés depuis claude.ai** : leurs blocs `!` ne sont jamais exécutés sur votre machine.

## Une commande défensive complète

`.claude/skills/chercher/SKILL.md` :

```md
---
description: Cherche un motif dans un fichier du projet
argument-hint: <motif> <fichier>
arguments: [motif, fichier]
allowed-tools: Grep Read
disallowed-tools: Bash Edit Write
---

Cherchez le motif « $motif » dans le fichier « $fichier ».

Règles :
- Utilisez uniquement l'outil Grep, jamais le shell.
- Refusez si le fichier est hors du projet (chemin absolu, `..`).
- Si le motif ou le fichier est vide, demandez la valeur manquante.
```

Ici, le shell est retiré (`disallowed-tools: Bash`), la recherche passe par l'outil Grep qui n'interprète pas les caractères spéciaux du shell, et les deux outils utiles sont pré-autorisés.

## Ce que ces protections ne couvrent pas

- **Vos propres validations** : si vous acceptez une commande dangereuse dans la demande de confirmation, elle s'exécute.
- **Le contenu lu** : un fichier, une issue GitHub ou une page web peut contenir des instructions malveillantes. Méfiez-vous des commandes qui lisent du contenu externe puis agissent.
- **Les serveurs MCP** : un serveur compromis peut renvoyer du contenu piégé. Limitez-vous à des serveurs de confiance.
- **`bypassPermissions`** : dans ce mode, aucune confirmation n'est demandée. Réservez-le à un conteneur isolé.

## Checklist avant de partager une commande

- [ ] Aucun `$ARGUMENTS`, `$0` ou argument nommé dans un bloc `` !`…` ``
- [ ] Les blocs `!` sont fixes et en lecture seule
- [ ] `allowed-tools` est précis (jamais `Bash` seul ni `Bash(*)`)
- [ ] Les outils inutiles sont retirés avec `disallowed-tools`
- [ ] `disable-model-invocation: true` sur toute commande à effets de bord
- [ ] Testée avec des arguments hostiles : `; rm`, `$(…)`, backticks, `../../`

Pour automatiser l'interdiction d'une commande précise (même tapée à la main), un hook `UserPromptExpansion` peut bloquer l'expansion : voir [Hooks et commandes personnalisées](/wiki/slash-commands/slash-dans-hooks).
