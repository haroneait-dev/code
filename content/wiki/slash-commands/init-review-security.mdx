Trois commandes intégrées couvrent le début et la fin d'une tâche : `/init` prépare le projet, `/code-review` cherche les bugs dans vos changements et `/security-review` cherche les vulnérabilités. Depuis la v2.1.223, `/review` n'est plus une commande à part : c'est un alias de `/code-review`.

## `/init` : un CLAUDE.md de départ

`/init` analyse le dépôt et écrit un `CLAUDE.md` à la racine : stack, commandes de build et de test, conventions repérées. Ce fichier est chargé au début de chaque session.

```text
> /init
```

Deux options utiles :

- `CLAUDE_CODE_NEW_INIT=1 claude` lance un parcours interactif qui aborde aussi les skills, les hooks et les fichiers de mémoire personnels ;
- si `/init` trouve une configuration OpenAI Codex ou Gemini CLI, il propose de la reprendre avec `/import`.

Le fichier généré est un point de départ, pas un livrable. Relisez-le, supprimez ce que Claude peut déduire seul du code, et gardez les règles qui comptent. Pour l'affiner ensuite, utilisez `/memory`. Pour un audit des instructions devenues contradictoires ou obsolètes, `/doctor prompt-audit` (v2.1.283 et plus) passe en revue vos `CLAUDE.md` et vos skills.

Si le dépôt contient un `AGENTS.md` mais pas de `CLAUDE.md`, Claude Code lit `AGENTS.md`.

## `/code-review` : trouver les bugs avant de pousser

`/code-review` relit les commits de votre branche en avance sur l'amont, plus les changements non commités. Il cherche d'abord des erreurs de correction ; selon le modèle et l'effort, il signale aussi des nettoyages possibles.

```text
> /code-review                  # diff courant
> /code-review high 1234        # PR n°1234, effort élevé
> /code-review main...ma-branche
> /code-review --fix            # applique les corrections ensuite
> /code-review --comment 1234   # publie les remarques sur la PR
> /code-review ultra            # revue multi-agents dans le cloud
```

Les points à connaître :

- **Effort** : `low` et `medium` ne remontent que les constats les plus sûrs (peu de faux positifs) ; `high` à `max` élargissent la couverture. Sans niveau, la commande réutilise le dernier niveau que vous avez tapé.
- **Arrière-plan** : la revue tourne dans un sous-agent avec son propre contexte, vous continuez à travailler. Les résultats arrivent dans la conversation.
- **`--max-findings n|all|default`** (v2.1.288) : change le nombre maximal de constats.
- **`--fix` en arrière-plan** : ces modifications ne sont pas couvertes par les points de contrôle, `/rewind` ne les annule pas. Utilisez git.
- **`ultra`** (alias `/ultrareview`) : revue approfondie dans un bac à sable cloud. Trois exécutions gratuites sur Pro et Max, puis des crédits d'usage.

La revue suit votre `CLAUDE.md`. Le fichier `REVIEW.md`, lui, ne sert qu'à la revue automatique des PR sur GitHub (Code Review, offres Team et Enterprise), pas à la commande locale.

`/simplify` est complémentaire : quatre agents cherchent les doublons, la complexité inutile, l'inefficacité et les problèmes de niveau d'abstraction, puis appliquent les corrections. Il ne cherche pas de bugs.

## `/security-review` : les vulnérabilités du diff

`/security-review` analyse le diff entre votre branche et la branche par défaut de `origin` : injections, problèmes d'authentification, exposition de données, etc.

```text
> /security-review
```

Il faut un remote `origin`. Si la commande échoue avec une erreur `ambiguous argument`, la référence par défaut du remote manque, la page d'erreurs de la documentation donne la correction.

Sur un projet Next.js et Supabase, demandez-vous en lisant le rapport :

- chaque route API vérifie-t-elle le jeton de l'utilisateur ?
- la clé `SUPABASE_SERVICE_ROLE_KEY` reste-t-elle côté serveur ?
- les nouvelles tables ont-elles des politiques RLS ?
- une variable sensible est-elle exposée via un préfixe `NEXT_PUBLIC_` ?

Une revue automatique est une couche de défense parmi d'autres. Elle ne remplace ni les tests, ni une relecture humaine des parties critiques.

## Enchaîner les trois

Sur un projet que vous découvrez :

```text
> /init
> /memory            # relire et corriger le CLAUDE.md
```

Avant d'ouvrir une PR :

```text
> /diff
> /code-review
> /security-review
```

Pour automatiser la revue sur chaque PR, voir [Revue de code automatique](/wiki/workflows/code-review-auto).

## Ajouter vos propres règles

Les commandes personnalisées sont désormais des skills. Pour un audit maison, créez un skill avec un nom distinct, par exemple `.claude/skills/audit-secu/SKILL.md` :

```md
---
description: Audit sécurité propre à notre stack Next.js + Supabase
disable-model-invocation: true
allowed-tools: Read Grep Glob Bash(git diff *)
---

Examinez le diff courant (`git diff origin/main...HEAD`) et vérifiez, en plus des points habituels :

- aucun `dangerouslySetInnerHTML` sans assainissement ;
- chaque route sous `app/api/` vérifie le JWT Supabase ;
- aucune table créée sans politique RLS.

Classez les constats par gravité, avec fichier et ligne.
```

Un nom distinct évite les ambiguïtés. Un skill de projet nommé `code-review` remplace bien `/code-review`, mais l'alias `/review` continue de lancer la version intégrée, ce qui déroute l'équipe. Notez aussi que `allowed-tools` pré-autorise ces outils pendant le tour : il ne restreint pas les autres (voir [le frontmatter](/wiki/slash-commands/markdown-frontmatter)).
