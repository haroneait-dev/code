Deux commandes permettent d'ajuster Claude Code sans quitter la session : `/mcp` pour l'état et l'authentification des serveurs MCP, `/permissions` pour les règles qui décident de ce que Claude peut faire sans vous demander. Les deux s'utilisent même pendant que Claude travaille.

## `/mcp` : l'état de vos serveurs

Un serveur MCP (Model Context Protocol) expose des outils, des ressources et des prompts : GitHub, Supabase, Sentry, une base de données… `/mcp` ouvre la liste des serveurs configurés et leur état :

| Indicateur | Signification |
| --- | --- |
| `✔ Connected` | Serveur actif |
| `! Needs authentication` | Connexion OAuth à faire |
| `✘ Failed to connect` | Erreur, détail affiché |
| `⏸ Pending approval` | Serveur du projet (`.mcp.json`) en attente de votre accord |
| `⊘ Disabled for this project` | Désactivé localement |

Depuis cette liste, vous lancez l'authentification OAuth dans le navigateur et vous activez ou désactivez un serveur sans toucher à sa configuration.

Formes directes, utiles aussi en mode `-p` :

```text
> /mcp reconnect all        # relance tous les serveurs en échec ou à authentifier
> /mcp reconnect github
> /mcp disable sentry
> /mcp enable all
```

Depuis le terminal :

```bash
claude mcp list                 # serveurs et état de santé
claude mcp login sentry         # authentification OAuth
claude mcp logout sentry
claude mcp add --transport http github https://api.githubcopilot.com/mcp/
claude mcp add --transport stdio db -- npx -y @bytebase/dbhub --dsn "postgresql://..."
```

Où vit la configuration : `.mcp.json` à la racine pour un serveur partagé avec l'équipe (portée `project`), `~/.claude.json` pour vos serveurs personnels (portées `local` et `user`). Les serveurs MCP ne se déclarent pas dans `settings.json`.

Désactiver un serveur que vous n'utilisez pas allège le contexte : par défaut, seuls les noms d'outils sont chargés, mais chaque serveur ajoute ses instructions.

### Les prompts MCP deviennent des commandes

Un serveur peut exposer des prompts réutilisables. Le menu `/` les affiche sous la forme `/serveur:prompt (MCP)`, et vous pouvez aussi les lancer en tapant `/mcp__<serveur>__<prompt>`. Les arguments se passent séparés par des espaces (chaque argument est un seul mot) :

```text
> /mcp__github__list_prs
> /mcp__github__pr_review 456
> /mcp__jira__create_issue login-bug high
```

Dans le nom du serveur, tout caractère hors `A-Z`, `a-z`, `0-9`, `_` et `-` est remplacé par `_`. Le résultat du prompt est injecté directement dans la conversation.

## `/permissions` : les règles allow, ask, deny

`/permissions` ouvre une fenêtre qui liste toutes les règles avec le fichier de réglages dont chacune provient. Vous pouvez y ajouter ou retirer des règles, gérer les dossiers de travail et consulter les refus récents du mode `auto`. Un changement fait pendant que Claude travaille s'applique dès son prochain appel d'outil. L'alias est `/allowed-tools`.

### Syntaxe des règles

```json
{
  "permissions": {
    "allow": [
      "Bash(npm run *)",
      "Bash(git diff *)",
      "Edit(src/**)",
      "WebFetch(domain:code.claude.com)",
      "mcp__supabase__list_tables"
    ],
    "ask": ["Bash(git push *)"],
    "deny": [
      "Bash(rm -rf *)",
      "Read(./.env)",
      "Read(./.env.*)"
    ]
  }
}
```

Points de syntaxe :

- `Bash(npm run *)` : `*` remplace n'importe quel texte. L'espace avant `*` compte : `Bash(git diff*)` accepterait aussi `git diff-index`.
- L'ancienne forme `Bash(npm:*)` reste reconnue et équivaut à `Bash(npm *)`, mais seulement en fin de motif.
- Les commandes composées sont découpées : `npm test && git push` est vérifié sous-commande par sous-commande.
- `mcp__supabase` ou `mcp__supabase__*` couvrent tous les outils du serveur `supabase` ; `mcp__supabase__execute_sql` un seul outil.

### L'ordre d'évaluation

Les règles sont évaluées dans cet ordre : deny, puis ask, puis allow. La première qui correspond l'emporte, et une règle plus précise ne change rien à cet ordre. Conséquence : un `deny` sur `Bash(aws *)` bloque aussi `aws s3 ls` même si une règle allow le cite explicitement. On ne crée pas d'exception à un deny avec un allow.

Les règles sont appliquées par Claude Code, pas par le modèle : écrire « ne fais jamais de push » dans `CLAUDE.md` oriente Claude, mais seule une règle (ou un hook) l'empêche réellement.

## Les modes de permission

Les règles s'ajoutent au mode de la session. Depuis août 2026, le mode par défaut est `auto` : un classifieur examine les actions au lieu de vous interroger. Les autres modes : `default` (manuel), `acceptEdits`, `plan`, `dontAsk` et `bypassPermissions`. `Maj+Tab` les fait défiler. Voir [Modes de permission](/wiki/cli/permissions-modes).

## Coordonner MCP et permissions

Connecter un serveur ne pré-autorise pas ses outils. Pour un serveur de confiance en lecture seule, autorisez précisément ce qui ne modifie rien :

```json
{
  "permissions": {
    "allow": ["mcp__supabase__list_tables", "mcp__supabase__get_advisors"],
    "ask": ["mcp__supabase__execute_sql", "mcp__supabase__apply_migration"]
  }
}
```

C'est plus sûr que d'autoriser tout le serveur et plus rapide que de valider chaque appel.

## Bonnes pratiques

1. **Jamais de `Bash` ou `Bash(*)` en allow global** : préférez des préfixes ciblés. En mode `auto`, une entrée `Bash` nue est d'ailleurs ignorée.
2. **Séparer équipe et perso** : règles communes dans `.claude/settings.json` (versionné), préférences dans `.claude/settings.local.json` (non versionné).
3. **Préparer une tâche longue** : avant de laisser Claude travailler seul, ouvrez `/permissions` et autorisez ce dont il aura besoin.
4. **Faire le ménage** : relisez régulièrement la liste. La commande `/fewer-permission-prompts` propose aussi une liste d'autorisations en lecture seule tirée de vos sessions.
5. **Ne pas confondre règle et frontière de sécurité** : une règle Bash vise la commande telle que Claude l'écrit. Pour une garantie forte, ajoutez le [bac à sable](/wiki/demarrer/permissions-sandbox).
